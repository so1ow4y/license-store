# Модель данных

Реализация раздела 20 ТЗ. Источник истины — [`apps/api/prisma/schema.prisma`](../apps/api/prisma/schema.prisma);
здесь только то, что из схемы не видно: почему сделано именно так и какие
инварианты нельзя нарушать.

## Карта таблиц

| Домен | Таблицы |
|---|---|
| Identity | `users`, `oauth_accounts`, `roles`, `permissions`, `role_permissions`, `user_roles` |
| Сессии | `sessions`, `refresh_tokens`, `verification_tokens`, `api_keys`, `registration_keys` |
| Продукты | `products`, `product_versions`, `product_version_files`, `license_plans` |
| Лицензии | `licenses`, `devices`, `hwid_history` |
| Реселлеры | `resellers`, `reseller_transactions` |
| Биллинг | `orders`, `payments`, `digiseller_orders` |
| Контент | `files`, `news`, `news_translations` |
| Уведомления | `notifications`, `notification_templates` |
| Журналы | `login_history`*, `audit_logs`*, `anti_fraud_events`, `launcher_log_batches` |
| Система | `settings`, `locales`, `translations` |

`*` — партиционированы по месяцам.

Всего 35 таблиц против 23 сущностей в ТЗ. Разница — join-таблицы RBAC,
таблицы переводов и несколько сущностей, без которых требования ТЗ не
закрываются (см. ниже).

## Что добавлено догоняющей миграцией

Миграция `20260731143000_catchup_audit_gaps` закрыла пробелы, найденные при
сверке схемы с ТЗ. Существенное:

**Исправлен баг.** У `registration_keys.used_by_user_id` стоял `UNIQUE`.
Ограничение защищало не ключ от повторного использования (это делает `UNIQUE`
на `code` вместе с `used_at`), а пользователя от второй покупки по ключу —
активировать ключ он мог бы ровно один раз за всю жизнь аккаунта.

**`verification_tokens`** — одна таблица на подтверждение email, сброс пароля,
смену адреса и промежуточный шаг 2FA. Жизненный цикл у них общий, различается
только действие после успешной проверки. Плюс `users.two_factor_last_step`:
принимаем только TOTP-шаг строго больше сохранённого, иначе один и тот же код
проходит дважды в пределах окна.

**Версии ключа шифрования** рядом с каждым зашифрованным полем
(`two_factor_secret_key_ver`, `hwid_enc_key_ver`, `signing_secret_key_ver`).
Без них ротация `ENCRYPTION_KEY` требует остановки сервиса и перешифровки всех
записей разом; с ними — фоновая задача, читающая старой версией и пишущая новой.

**`product_version_files`** — манифест целостности релиза. SHA-256 на архив
отвечает на вопрос «скачалось без ошибок», но не на «не подменили ли файл после
установки». Флаг `is_critical` разделяет файлы, проверяемые при каждом запуске,
и те, что проверяются только после обновления: полная проверка дерева на каждом
старте заметно бьёт по времени запуска.

**`launcher_log_batches`** — приём логов с клиента. В БД только метаинформация,
сами логи в S3: объёмные, читаются редко и точечно.

**`licenses.revoked_at` / `revoked_reason`.** Отзыв и блокировка — разные
события: блокирует админ за нарушение, отзывает система при возврате средств.

**`notifications.recipient`.** Уведомление админу об антифроде некуда было
адресовать — был только `user_id`.

**`hwid_history.actor_label`** — подпись актора на момент действия, как в
`audit_logs`.

## Отклонения от ТЗ и их причины

**`Updates` отдельной таблицей не существует.** «Обновление» из п.12 — это
`product_versions` с `is_published = true`. Отдельная таблица дублировала бы
все поля версии и немедленно разъехалась бы с ней по содержимому. Лаунчер
спрашивает «есть ли версия новее моей» — это запрос к `product_versions`
по `version_code`, не к отдельной сущности.

**`CryptoPayments` отдельной таблицей не существует.** Раз Digiseller —
единственный платёжный канал, крипта это `payments.method = CRYPTO` внутри
обычной сделки площадки, а не самостоятельный провайдер со своим жизненным
циклом. Если когда-нибудь появится приём крипты напрямую, добавится
`PaymentProvider.CRYPTO_DIRECT` и таблица деталей — структура это переживёт.

**Добавлен `license_plans`.** В ТЗ сроки 1/7/30/90/180/lifetime перечислены
как фиксированный список. Захардкоженный enum означает миграцию БД ради
акции «14 дней со скидкой». Тариф — это данные: срок, цена, привязка к
`digiseller_product_id`. `duration_days = NULL` означает Lifetime.

**Добавлены `locales` + `translations` + `news_translations`.** П.19 требует
добавлять языки без изменения исходного кода. Это выполнимо, только если
строки лежат в БД.

**Добавлены `oauth_accounts`, `registration_keys`, `notification_templates`,
`reseller_transactions`, `anti_fraud_events`.** Каждая закрывает конкретный
пункт ТЗ (п.5-6 регистрация/авторизация, п.16 уведомления, п.9 баланс
реселлера, п.15 антифрод), который иначе пришлось бы держать в JSON-полях.

## Инварианты, которые нельзя нарушать

**1. `digiseller_orders.unique_code` — UNIQUE на уровне БД.**
Это единственная настоящая защита от двойной выдачи лицензии. Ретрай
вебхука, двойной клик пользователя, гонка двух воркеров — всё разбивается
о constraint. Погашение кода и создание лицензии обязаны идти **в одной
транзакции**:

```ts
await prisma.$transaction(async (tx) => {
  const claimed = await tx.digisellerOrder.updateMany({
    where: { uniqueCode: code, redeemedAt: null },   // ← условие в WHERE
    data:  { redeemedAt: new Date(), redeemedByUserId: userId },
  });
  if (claimed.count === 0) throw new AlreadyRedeemedError();
  await tx.license.create({ ... });
});
```

Проверка `redeemedAt: null` внутри `WHERE`, а не отдельным `SELECT` перед
`UPDATE` — иначе между чтением и записью пролезет вторая транзакция.

**2. `licenses.current_device_id` — UNIQUE.**
Одно устройство не может быть активной привязкой двух лицензий
одновременно. Смена привязки — всегда через запись в `hwid_history`,
никогда просто `UPDATE licenses`.

**3. HWID в открытом виде не покидает сервер.**
`devices.hwid_hash = HMAC-SHA256(disk_id, HWID_PEPPER)` — по нему идёт весь
поиск и сравнение. `devices.hwid_enc` — тот же Disk ID под AES-256-GCM,
только для ручного разбора админом. В API не отдаётся ни то, ни другое
(ТЗ п.7: «состав HWID пользователю не отображается»).

**`HWID_PEPPER` менять нельзя после запуска.** Смена превратит все
существующие привязки в мусор, и каждый пользователь получит «устройство не
совпадает». Ротация возможна только через двойной хеш с миграционным окном.

**4. Refresh-токены живут семьями.**
`refresh_tokens.family` общий для всей цепочки ротаций. Предъявление
токена, у которого уже проставлен `used_at`, означает кражу — гасим всю
семью, а не только предъявленный токен.

**5. Журналы не имеют внешних ключей.**
`audit_logs`, `login_history`, `hwid_history`, `anti_fraud_events` ссылаются
на акторов простыми UUID-колонками. Это сделано намеренно: удаление
пользователя не должно ни каскадно стирать журнал, ни блокироваться им.
Плюс `audit_logs.actor_label` хранит, **кем актор был на момент действия** —
если роль потом сменили, журнал остаётся правдивым.

**6. Баланс реселлера — вычисляемая величина с материализацией.**
`resellers.balance` и `reseller_transactions.balance_after` меняются только
вместе и только в одной транзакции. `balance_after` позволяет сверить
историю, не пересчитывая всю ленту с нуля.

## Стратегия индексов

Индексы поставлены под конкретные запросы, а не «на всякий случай»:

| Индекс | Обслуживает |
|---|---|
| `licenses(status, expires_at)` | крон истечения лицензий, дашборд «истекающие» |
| `licenses(user_id, status)` | кабинет пользователя |
| `licenses(reseller_id)` | панель реселлера |
| `devices(hwid_hash)` | горячий путь: проверка привязки при каждом запуске |
| `product_versions(product_id, channel, is_published, version_code DESC)` | «есть ли обновление» — покрывающий, одно чтение индекса |
| `login_history(ip, created_at DESC)` | антифрод: брутфорс с одного IP |
| `digiseller_orders(last_polled_at)` | воркер поллинга статусов сделок |

Поиск в админке (ТЗ п.8) — через GIN-индексы по триграммам:
`users_username_trgm`, `users_email_trgm`, `licenses_key_trgm`. Без них
`ILIKE '%текст%'` идёт последовательным сканом — на 10 000 пользователей это
сотни миллисекунд на каждый введённый символ. Приведение к `text` в определении
индекса обязательно: `username` и `email` имеют тип `citext`, а `gin_trgm_ops`
определён для `text`.

Три ограничения, которые Prisma выразить не умеет и которые живут прямо
в миграции:

| Объект | Что делает |
|---|---|
| `locales_single_default` | частичный уникальный индекс `WHERE is_default` — язык по умолчанию ровно один |
| `order_number_seq` + `next_order_number()` | генерирует `ORD-2026-000123` как `DEFAULT` колонки; сиквенс сквозной, без сброса по годам, номер глобально уникален |
| `PARTITION BY RANGE` на журналах | помесячные партиции, см. ниже |

## Партиционирование журналов

`login_history` и `audit_logs` — единственные таблицы, растущие от трафика,
а не от числа пользователей. Помесячные партиции ([`sql/01_partitioning.sql`](../apps/api/prisma/sql/01_partitioning.sql))
дают три вещи: `DROP TABLE` вместо `DELETE` при очистке, partition pruning
для запросов «за последнюю неделю» и `VACUUM` по частям.

Партиции создаются на 3 месяца вперёд функцией `create_monthly_partitions()`,
удаляются старше ретенции через `drop_old_partitions(90)`. Обе вызываются
кроном приложения раз в сутки. Есть `DEFAULT`-партиция — страховка от того,
что вставка с датой вне диапазона уронит бизнес-операцию.

Составной PK `(id, created_at)` — требование Postgres: ключ партиционирования
обязан входить в первичный ключ.

## Оценка объёма на целевых цифрах ТЗ

10 000 пользователей, 1000 онлайн, ретенция журналов 90 дней:

| Таблица | Строк | Объём с индексами |
|---|---|---|
| `users` | 10 000 | ~10 МБ |
| `licenses` | ~20 000 | ~20 МБ |
| `devices` | ~30 000 | ~25 МБ |
| `hwid_history` | ~50 000 / год | ~30 МБ |
| `orders` + `payments` + `digiseller_orders` | ~60 000 / год | ~80 МБ |
| `login_history` | ~5 000 / сутки | ~160 МБ за 90 дней |
| `audit_logs` | ~20 000 / сутки | ~900 МБ за 90 дней |
| **Итого** | | **~1.5–3 ГБ** |

То есть база при штатной работе — единицы гигабайт, и 200 ГБ NVMe из
расчёта по серверу уходят почти целиком в запас и WAL.

**Единственное, что может это сломать** — запись heartbeat'ов лаунчера в
Postgres. 1000 онлайн × раз в минуту = 1.44 млн строк в сутки, это на два
порядка больше всего остального вместе взятого. Heartbeat'ы живут в Redis
(`SETEX license:online:{id}`), в БД попадает только `licenses.last_check_at`
и то не чаще раза в 5 минут на лицензию.

## Что ещё не в схеме

Осознанно отложено до появления реальной потребности:

- **Тикеты поддержки** — в ТЗ нет, но при 10k пользователей появятся.
- **Промокоды и скидки** — `license_plans.price` пока плоская.
- **Реферальная программа** — `users.reseller_id` покрывает только привязку
  к реселлеру.
- **Read-реплика и шардирование** — на этих объёмах не нужны; схема им
  ничем не мешает.
