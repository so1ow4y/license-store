# Переход загрузчика на аутентификацию по ключу лицензии

## 1. Ключ в каждом запросе, без обмена на короткоживущий токен

**Решение.** Ключ предъявляется в **каждом** запросе `license/check` и `payload`. Никакого тикета, сессии, «ticket из check → payload» не вводится.

**Почему.**

Вариант «check возвращает короткоживущий тикет, payload ходит с ним» выглядит естественно ровно до момента, когда его сверяешь с уже принятыми решениями по payload:

1. **Он уже отвергнут в этом же проекте.** PAYLOAD-DESIGN §8, отвергнутый вариант (б): «Требовать успешного license/check через отметку в Redis — ложная гарантия (противник сделает check один раз) плюс состояние на горячем пути, ломающееся при рестарте Redis». Тикет — это ровно та же отметка, только с именем. Обоснование не изменилось ни на слово.
2. **Он ломает главное свойство payload.** §7.1 требует, чтобы лицензия и HWID проверялись **на каждый запрос**. Payload с тикетом проверяет не лицензию, а факт, что кто-то пять минут назад прошёл проверку. Резолвер `resolveForLauncher(allowFirstBind:false)` пришлось бы либо звать всё равно (тогда тикет ничего не экономит), либо не звать (тогда `LICENSE_BLOCKED`, выставленный между двумя запросами, не сработает).
3. **Тикет — второй предъявительский секрет, и он хуже ключа.** Ключ виден только в кабинете и привязан к железу через лицензию; тикет живёт в памяти процесса, к железу не привязан и по построению должен приниматься без HWID (иначе зачем он). Владелец отверг возражение про предъявительский документ на основании «ключ виден только в кабинете + привязка к железу» — тикет не обладает ни одним из этих двух свойств.
4. **Отзыв.** Сегодня отзыв лицензии доходит до работающего загрузчика за `recheckAfterSec = 300` с. С тикетом окно становится `TTL тикета` и перестаёт быть одной управляемой величиной.
5. **Экономии нет.** Разрешение ключа — это `license.findUnique({ where: { key } })`, одно попадание в UNIQUE-индекс. Сегодня на том же месте стоит `pickLicense`: `findFirst` по `(userId, productId, status, expiresAt)` плюс, на запасном пути, `findMany take 10`. Ключ **дешевле** того, что есть.

Два запроса на запуск (`check`, затем `payload`) и один `check` раз в 5 минут — это ~12 предъявлений ключа в час с машины по TLS+HMAC. Ключ при этом всё равно лежит на этой машине постоянно (иначе загрузчик не переживёт перезапуск), поэтому тикет не убирает секрет с машины — он добавляет второй.

**Что берётся от идеи токена.** Только одно: **отрицательный** кэш в Redis на нераспознанные ключи (`launcher:badkey:<hmac(key)>`, TTL 60 с), чтобы сканер не превращал каждую догадку в запрос к Postgres. Положительный кэш `key → licenseId` **не вводится**: он потребует инвалидации при удалении лицензии и не окупает одного индексного попадания.

## 2. Ключ едет в теле, полем `licenseKey`. Ни query, ни свой заголовок

**Решение.**

```
POST /api/v1/launcher/license/check   { productSlug, hwid, clientVersion, licenseKey }
POST /api/v1/launcher/payload         { productSlug, hwid, sessionKey,   licenseKey }
```

DTO: `@IsString @Matches(/^[A-Z0-9]{2,16}(-[ACDEFGHJKMNPQRTUVWXYZ2346789]{4}){4}$/) @MaxLength(64)`. Нормализация (upper-case, срезать пробелы) делается **на сервере после разбора** — подпись считается по сырым байтам тела, поэтому серверная нормализация подписи не касается.

**Почему тело, а не заголовок.**

Подпись покрывает `sha256(rawBody)` и **не покрывает произвольные заголовки**. Ключ в теле оказывается внутри HMAC: посредник не может подменить ключ, оставив подпись валидной, и переигранное тело нельзя перенацелить на другую лицензию. Ключ в заголовке `X-License-Key` был бы единственным параметром авторизации, **не входящим в подписанный канон**, — в системе, где §14 прямо признаёт рабочим сценарий с подставленным корневым сертификатом, это не мелочь.

Второй довод — логи. Имя поля `licenseKey` **уже** присутствует в `redact.paths` pino (`logger.module.ts:74`) и в `REDACTED_FIELDS` аудита (`audit.service.ts:99`) — оба списка писались как раз под ключ лицензии. Новый заголовок не покрыт ни `redact` (там перечислены `authorization`, `cookie`, `x-api-key`, `x-signature`), ни сериализатором. Сегодня он не утёк бы случайно (сериализатор — белый список), но безопасность держалась бы на том, что никто не расширит белый список.

**Почему категорически не query.** Дважды дисквалифицировано: (1) `pathOf()` режет query до подписи — параметр вне HMAC; (2) nginx пишет `$request_uri` целиком, и pino пишет `req.url`. Ключ оказался бы в access-логе, в строке `AllExceptionsFilter` (`${request.method} ${request.url} → ${status}`), в `error.log` и во внешнем сборщике логов — то есть в хранилище, доступ к которому шире доступа к БД. Это ровно тот класс утечки, из-за которого `licenses.service.ts:308-315` и `hwid.service.ts:177-181` намеренно пишут в лог `license.id`, а не `license.key`.

**Что фактически попадает в логи после правки**

| Источник | Что видно | Ключ виден? |
|---|---|---|
| nginx access (`json_combined`) | time, request_id, remote_addr, method, `$request_uri`, status, bytes, duration, upstream_time, User-Agent | **нет** (тело не логируется) |
| pino, автологирование запроса | id, method, url, User-Agent, X-Client-Version, ip, statusCode | **нет** (тело не логируется вовсе) |
| `AllExceptionsFilter` | `METHOD url → status CODE [requestId]` | **нет** |
| `payload_issues` | licenseId, deviceId, productId, hwidHash, ip, result | **нет** (по построению — только id) |
| `AuditInterceptor` | не вешается на launcher категорически | — |

**Дополнительные правила, которые надо зафиксировать в контракте, иначе они нарушаются одной строкой:**

- Ключ **никогда** не пишется в `payload_issues`, `launcher_log_batches`, `anti_fraud_events.details`, `hwid_history` — только `licenseId`.
- Ключ **никогда** не возвращается в ответе и не эхо-повторяется в теле ошибки.
- Имя поля обязано оставаться ровно `licenseKey` — от него зависят два уже существующих списка редактирования.
- `@ApiBearerAuth('jwt')` с методов снимается: после перехода это ложь в контракте.
- В `redact.paths` добавить `req.body.licenseKey` уже есть; добавить `req.headers["x-license-key"]` **не нужно** — заголовка не будет.

## 3. `/launcher/update` — без ключа вообще; `/launcher/logs` — ключ необязателен

### GET /launcher/update

**Решение.** `@Public()` (глобальный JWT снимается), `SignatureGuard` остаётся, `@RequireApiScope('launcher:update')` добавляется, **ключ лицензии не требуется и не принимается**.

**Почему.** Обработчик уже сегодня не берёт `@CurrentUser` — `update()` вызывает `this.launcher.checkUpdate(query.productSlug, query.clientVersion)` и всё. Пользователь ему не нужен ни для чего: он отвечает «есть ли версия новее и обязательна ли она», и этот ответ одинаков для всех.

Требовать здесь ключ значило бы либо принять его в query (см. п.2 — исключено), либо превратить GET в POST ради параметра, который ни на что не влияет. Хуже того: это создаёт тупик. Загрузчик с просроченной лицензией должен уметь узнать, что ему надо обновиться, — а по решению из PAYLOAD-DESIGN §17 (Д14) выхода из состояния 426 у клиента и так нет. Запирать ещё и диагностику за лицензией — прямая дорога к «не работает и не говорит почему».

Честно про раскрытие: эндпоинт становится доступным всякому, кто владеет ключом сборки и умеет подписывать. Раскрывает он номер версии опубликованной сборки и флаг `mandatory` — не секрет, и сегодня он раздаётся любому залогиненному по тому же ключу сборки. Регрессии нет.

### POST /launcher/logs

**Решение.** `licenseKey` — **необязательное** поле DTO. Есть и разрешается → строка пишется с `licenseId`, `userId = license.userId`, `deviceId = license.currentDeviceId`. Нет или не разрешается → строка пишется с NULL в этих колонках. Ответ **всегда 202**, независимо от исхода разрешения ключа.

**Почему.**

1. Схема это уже позволяет и, судя по всему, именно так и задумывалась: `launcher_log_batches.userId String?` с комментарием «Без FK: лог может прийти от клиента, чей аккаунт уже удалён», плюс существующие и **никогда не заполняемые** сегодня `licenseId` и `deviceId` (`ingestLog` пишет только `userId`, `kind`, `clientVersion`, `summary`, `ip`). То есть переход на ключ заодно даёт колонке `licenseId` смысл и включает уже объявленный индекс `@@index([licenseId])`.
2. Самый ценный отчёт — от загрузчика, который **не смог** аутентифицироваться: ключ отвергнут, конфиг повреждён, `HWID_MISMATCH`, `SIGNATURE_EXPIRED` из-за съехавших часов. Эндпоинт, требующий валидную лицензию, отказывает ровно тем отчётам, ради которых он существует.
3. **Всегда 202** — не косметика, а отсечка оракула. Если `/logs` различал бы «ключ принят» и «ключ неизвестен», он стал бы бесплатным и дешёвым проверятором ключей в обход всех счётчиков `check`/`payload`.

Цена: анонимная запись в БД. Компенсируется тем, что уже есть (`summary.slice(0, 512)`, зона `launcher_zone` 120 r/m по IP) плюс счётчиком по `apiKeyId + IP` из п.4. `ingestLog` меняет сигнатуру: `userId: string` → `userId?: string | null`, добавляются `licenseId`, `deviceId`.

## 4. Частота и перебор: считать по трём осям, ни одна из них — не «пользователь»

**Постановка.** 28¹⁶ ≈ 7,2·10²² ≈ 2⁷⁶,⁹ при CSPRNG-генерации — угадывание не является угрозой и обсуждению не подлежит. Реальных угроз три:
- **нагрузка**: дешёвый запрос, за которым стоит индексный поиск в Postgres и запись счётчиков;
- **проверка списков**: утёкшая выгрузка/скриншоты/перепроданные ключи — надо узнать, какие живы;
- **оракул**: возможность отличить «ключ существует» от «не существует» дешевле, чем стоит запрос.

**Решение — три счётчика, все в Redis, все ДО обращения к Postgres, где это возможно.**

**Ось 1 — источник, только ПРОВАЛЫ.** Ключ `lk:fail:<apiKeyId>:<ip>`, окно 10 мин, порог 10 → 429 `RATE_LIMITED` + `Retry-After` на этот источник, событие `AntiFraudEvent(RATE_LIMIT_EXCEEDED, HIGH)` ровно на пересечении порога (`INCR` атомарен — значение `порог+1` увидит ровно один запрос, тот же приём, что в `countIssue`).
Считаются **только** нераспознанные ключи. Успехи не считаются намеренно: за одним NAT сидят сотни легитимных машин, и общий счётчик там — самострел. То же рассуждение уже записано в PAYLOAD-DESIGN §20 про `launcher_zone` и NAT. У честной машины ровно один ключ, и она не промахивается никогда; у сканера нет ничего, кроме промахов. Это единственный признак, разделяющий их без ложных срабатываний.

**Ось 2 — ключ (через HMAC), любой исход.** Ключ `lk:seen:<hmac(key)>` — множество различных `hwidHash` и подсетей /24 за час. Это не защита от перебора, а **детектор шаринга**, который до сих пор строить было не на чем: сегодня один и тот же ключ, ходящий с двадцати машин, виден только косвенно через `payload_issues`. Порог → `AntiFraudEvent(HWID_CHANGE / CONCURRENT_SESSIONS, MEDIUM)`, отказа нет — отказ здесь ломал бы легитимный сброс привязки.

**Ось 3 — лицензия. Уже существует и продолжает работать без единой правки.** `payload:rate:<licenseId>`, мягкий 20/ч (выдаём + событие), жёсткий 60/ч (429 + `DENIED_RATE_LIMIT`). Лицензия по-прежнему разрешается — просто теперь по ключу, а не по `(userId, productId)`.

**Внешний рубеж** — зоны nginx `launcher_zone` и `payload_zone` по 120 r/m на `$binary_remote_addr` — остаётся как есть; в шаблоне прямо записано, что это «единственная защита от перебора по IP».

**Три обязательных детали, без которых схема ломается:**

1. **В Redis-ключ идёт `HMAC-SHA256(ключ, pepper)`, а не сам ключ.** Redis настроен `appendonly yes` и `allkeys-lru`. Класть предъявительский секрет в имя ключа Redis — это буквально повтор дефекта, из-за которого `signature.guard.ts:131-159` перестал кэшировать открытый `signingSecret`: «на диске накопились секреты подписи ВСЕХ сборок в открытом виде», срок жизни утечки — срок жизни AOF и его бэкапов.
2. **`ValidationPipe` — первый и самый дешёвый фильтр.** Регулярка по алфавиту (`ACDEFGHJKMNPQRTUVWXYZ2346789`, без B/I/L/O/S/0/1/5) убивает мусорный перебор в guard'е Nest, не доходя ни до Redis, ни до Postgres.
3. **Один код на всё нераспознанное.** Неизвестный ключ, ключ чужого продукта, синтаксически валидный мусор → **`404 LICENSE_KEY_INVALID`**, одинаково. Детальные коды (`LICENSE_EXPIRED`, `LICENSE_BLOCKED`, `LICENSE_REVOKED`) остаются только для **разрешённых** ключей — обоснование PAYLOAD-DESIGN §16 («детальный код сообщает противнику только факты о его собственной лицензии») сохраняет силу: чтобы увидеть `LICENSE_EXPIRED`, надо предъявить ключ, то есть уже им владеть.

**Что при этом не пишется в журнал — записываю честно, а не умалчиваю.** Запрос с нераспознанным ключом **не порождает строки в `payload_issues`**: лицензии нет, `licenseId`/`productId`/`deviceId` были бы NULL, а под этот исход нет значения в `PayloadIssueResult`. Он остаётся в счётчике оси 1 и, при пересечении порога, в `anti_fraud_events`. Это ровно тот же класс ограничения, что уже зафиксирован как Д29 («каждая попытка» точнее читать как «каждая попытка, дошедшая до проверки лицензии»), и он должен быть записан в контракте, а не обнаружен потом.

## 5. Что ломается при отказе от сессии — полный список

Разбор по каждому месту, где сегодня используется `userId` на пути загрузчика.

### Продолжает работать без изменений

| Механизм | Почему уцелел |
|---|---|
| **Привязка к устройству** | `bindOrVerify(licenseId, diskId, …)` — весь механизм на `licenseId`. Уникальность `licenseId_hwidHash`, `licenses.current_device_id`, `hwid_history` — ни одного обращения к сессии |
| **Лимит сбросов 3/жизнь и кулдаун 24 ч** | `licenses.hwid_reset_count`, `licenses.last_hwid_reset_at` — колонки лицензии |
| **Счётчики выдач payload** | `payload:rate:<licenseId>`, мягкий/жёсткий пороги |
| **Онлайн и `last_check_at`** | `license:online:<licenseId>`, `license:touch:<licenseId>` |
| **Однократность `sessionKey`** | `payload:sk:<sha256(sessionKey)>` — к пользователю не привязан |
| **`SignatureGuard` + `ApiScopeGuard`** | Отвечают на вопрос «наша ли сборка», к пользователю не относились никогда |
| **Отзыв/блокировка лицензии, блокировка устройства** | Читаются из строки лицензии при каждой проверке |
| **Уведомления** | Все идут от `license.userId` из крона и из кабинета. Путь загрузчика сегодня **не порождает ни одного уведомления** — терять нечего |
| **Аудит** | На launcher не вешается категорически |
| **Сброс привязки пользователем** | `resetBySelf` живёт в веб-кабинете (`hwid.controller`), кабинет остаётся с JWT |

### Ломается или меняет смысл

**5.1. Выбор лицензии `pickLicense(userId, productId)` — умирает. Это главное изменение поведения.**

Сегодня сервер сам решает, какая из лицензий пользователя обслуживает запуск: живая ACTIVE выигрывает, иначе `LICENSE_FALLBACK_ORDER` (PENDING → ACTIVE → EXPIRED → BLOCKED → REVOKED) с окном `LICENSE_CANDIDATES = 10`. Именно это правило **автоматически активирует купленное впрок продление**.

С ключом лицензия задана однозначно — той, что назвал ключ. Следствия:

- Человек, купивший продление, получает **новый ключ** и обязан вставить его в загрузчик. До этого момента он держит оплаченное продление и при этом видит `LICENSE_EXPIRED` по старому ключу. Сегодня переход был бесшовным.
- Вся логика `pickLicense`, `LICENSE_FALLBACK_ORDER`, `LICENSE_CANDIDATES` (≈60 строк с тремя абзацами обоснования, в которые уже один раз наступили через сортировку enum'а) на пути загрузчика становится **мёртвой**. Это, если оценивать честно, скорее выигрыш — но выигрыш ценой пункта выше.

**Смягчение, которое надо заложить сразу:** при `LICENSE_EXPIRED`/`LICENSE_REVOKED`, если у `license.userId` есть живая ACTIVE лицензия на тот же продукт, добавлять в тело ошибки флаг `renewalAvailable: true`. Загрузчик показывает «продление найдено в вашем кабинете, возьмите новый ключ там». **Новый ключ в ответе не отдаётся ни при каких условиях** — это нарушило бы правило владельца «ключ виден только в личном кабинете» и превратило бы просроченный ключ в способ добыть действующий.

**5.2. `license.userId` может быть NULL — новое состояние, недостижимое сегодня.**

`userId String?` с `onDelete: SetNull`. Сегодня JWT гарантировал наличие пользователя. После правки по ключу разрешается лицензия, у которой владельца может не быть: складская лицензия реселлера, не выданная никому, или лицензия удалённого аккаунта. Формулировка «сервер по ключу определяет и лицензию, и владельца» в этих случаях просто неверна.

**Решение:** `check` и `payload` требуют `license.userId !== null`, иначе `403 LICENSE_NOT_ASSIGNED`, «Ключ не привязан к аккаунту — активируйте его в личном кабинете». Без этой проверки складской ключ реселлера работает в загрузчике, ни разу не создав аккаунта, и никакой код это сегодня не запрещает.

**5.3. Журнал `payload_issues` — работает, но `userId` становится производным и может быть NULL.**

`ctx.userId` сегодня — единственное поле, заполняемое **до** резолвера (из JWT). После правки оно берётся из `license.userId`, то есть заполняется вместе с остальными через `trace`. Строки с неразрешённым ключом в журнал не попадают вовсе (см. п.4). Индекс `@@index([userId, createdAt])` сохраняет смысл, но перестаёт быть надёжным: NULL по нему не ищется.

**5.4. Антифрод — частично.**

Что уцелело: всё, что привязано к лицензии/устройству/IP (`SESSION_KEY_REUSED`, пороги выдач, `SIGNATURE_MISMATCH`, `REPLAY`). `anti_fraud_events.userId` уже nullable — миграция не нужна.

Что теряется: корреляция **«один пользователь — несколько лицензий»** и любые сигналы от сессии. `CONCURRENT_SESSIONS` в enum есть, производителя в коде нет — то есть сегодня не регрессирует ничего, но возможность реализовать этот сигнал на пути загрузчика закрывается. Взамен появляется ось 2 из п.4 (один ключ с многих HWID/подсетей), которая для шаринга содержательнее.

**5.5. Утрата оперативного рычага: «завершить все сессии» больше не останавливает загрузчик.**

Это самая недооценённая потеря, и её нельзя не назвать. `JwtAuthGuard` делает на каждый запрос `isSessionRevoked(payload.sid)` → `401 SESSION_REVOKED`, и на клиенте `RequiresReLogin()` на это реагирует. Сегодня отзыв сессий останавливает работающий загрузчик за время жизни access-токена.

После правки остаются рычаги: блокировка/отзыв лицензии (`LICENSE_BLOCKED`/`LICENSE_REVOKED` на следующей проверке, то есть ≤300 с), блокировка устройства (`DEVICE_BLOCKED`), сброс привязки, отзыв `X-Api-Key` сборки (мгновенно, через `DEL apikey:<prefix>`). Этого достаточно, но **набор другой**, и он лицензие-центричен: «заблокировать человека целиком одним действием» больше нельзя — надо заблокировать его лицензии. Если такая операция нужна, её надо завести явно как «заблокировать все лицензии пользователя».

**5.6. Коды на клиенте: `401` исчезает с пути загрузчика.**

`RequiresReLogin()` в `Api.h` сегодня реагирует на `401`/`SESSION_REVOKED` и на `LICENSE_REVOKED` стиранием сохранённых секретов. После правки `401` не вернётся никогда. Поведение «стереть сохранённый секрет» должно быть перевешено на новый `LICENSE_KEY_INVALID` — иначе загрузчик с отозванным ключом будет вечно долбиться сохранённым мусором.

**5.7. Ограничение попыток входа (`auth_zone` 10 r/m, Argon2) — с пути загрузчика уходит вместе с логином.**

Формально это выигрыш: загрузчик перестаёт быть источником нагрузки на Argon2 (и исчезает связка «всплеск запусков деградирует вход в систему через общий пул libuv», описанная в PAYLOAD-DESIGN §13). Но взамен появляется новая незащищённая поверхность — предъявление ключа, — и её закрывает только п.4. Пока счётчики из п.4 не написаны, переход **ухудшает** ситуацию с перебором, а не улучшает.

## 6. Совместимость: оба способа живут одновременно, различаются по наличию поля в теле, старый выключается отзывом ключа сборки

**Решение.**

Новый `LauncherIdentityGuard` вешается на класс `LauncherController` **после** `SignatureGuard`; методы получают `@Public()` (снимает глобальный `JwtAuthGuard`), но новый guard обязателен и **fail-closed**.

```
есть body.licenseKey            → режим KEY.   Разрешить ключ → request.licenseCtx = { licenseId, userId, productId }
нет ключа, есть Bearer          → режим LEGACY. Делегировать JwtAuthGuard.canActivate(ctx) → request.user
есть и ключ, и Bearer           → режим KEY, но с обязательной сверкой (ниже)
нет ни того, ни другого         → 401 AUTH_REQUIRED
```

`@Public()` здесь не «выключить защиту», а «выключить *чужую* защиту, поставив свою». В `auth.module.ts` записано прямо: «Обратный порядок означает, что забытый декоратор оставляет эндпоинт открытым». Поэтому новый guard регистрируется на классе рядом с `SignatureGuard`, а не на методах — забыть его на новом методе так же невозможно, как забыть подпись.

**Различение — по наличию поля в теле, и только.** Не по версии API, не по `X-Client-Version`, не по User-Agent: `X-Client-Version` полностью контролируется противником (это уже записано в PAYLOAD-DESIGN §17), и строить на нём выбор режима авторизации значит дать выбирать режим клиенту.

**Ключ + Bearer одновременно.** Принимается ключ, токен игнорируется, **но требуется совпадение**: `license.userId !== request.user.id` → `403 LICENSE_OWNER_MISMATCH` + `AntiFraudEvent`. Это единственная бесплатная проверка согласованности, доступная в переходный период, и ловит она ровно интересный случай — модифицированный клиент, залогиненный под своим аккаунтом и предъявляющий чужой ключ.

**Резолвер остаётся один.** `resolveForLauncher` получает дискриминированный параметр вместо `userId: string`:

```ts
subject: { by: 'key'; licenseId: string } | { by: 'user'; userId: string }
```

В первом случае `license.findUnique({ where: { id } })`, во втором — существующий `pickLicense`. Всё, что ниже (`assertUsable`, verify-only ветки, `bindOrVerify`, `trace`), не меняется ни на строку. Это прямое продолжение §7: два эндпоинта обязаны выбирать одну и ту же строку лицензии.

**Проверка продукта.** `productSlug` в теле **остаётся** — он входит в AAD (`PAYLOAD-DESIGN §5`), собираемый клиентом из отправленного, и его удаление сломало бы криптоконтракт и все векторы. Добавляется сверка: `license.productId !== product.id` → `403 LICENSE_PRODUCT_MISMATCH`. Продукт **не выводится из префикса ключа**: префикс — снимок `product.slug`, сделанный `generateLicenseKey` в момент выдачи, и после переименования продукта он молча разъедется.

**Как выключается старый режим.** Не датой и не флагом окружения, а тем механизмом, который уже работает:

1. Заводится scope `launcher:legacy-bearer`. `LauncherIdentityGuard` пускает в режим LEGACY только ключи сборки, у которых он есть.
2. Старые сборки в поле имеют `scopes = []`, что по переходному правилу `ApiScopeGuard` означает «все», — они продолжают работать. Fail-open уже введён сознательно и уже сопровождается WARN на старте.
3. Новые сборки выпускаются с явными scopes **без** `launcher:legacy-bearer`.
4. Когда телеметрия (`payload_issues.apiKeyId` + `launcher_log_batches.clientVersion`) покажет, что старая сборка вымерла, — отзывается её `X-Api-Key`. Это мгновенный, уже реализованный и покрытый смоуком рубеж (`revokedAt` → `DEL apikey:<prefix>` → `403 SIGNATURE_INVALID`).

**Известное препятствие, которое надо закрыть в этой же работе:** `ApiKeyService` умеет только create/list/revoke — **проставить scope существующему ключу нечем** (Д12). Пока метода нет, выйти из fail-open можно только выпуском нового ключа, то есть новой сборки всем пользователям. Пункт 3 без этого метода неисполним.

**Срок перехода — решение владельца, и его надо взять явно.** Пока LEGACY жив, логин и 2FA остаются частью поверхности загрузчика, то есть переход не даёт ничего из того, ради чего он делается. Незакрытый переходный режим — это не совместимость, это два способа войти навсегда.

## 7. Утечка ключа до первой привязки

**Проблема.** Ключ уезжает в письме (`digiseller.service.ts:987` кладёт `licenseKey` в payload уведомления) и виден в кабинете. Кто первым запустил загрузчик — того и `FIRST_BIND`, и покупатель получает `HWID_MISMATCH` **на своей покупке**. Сегодня вору нужны ещё и учётные данные аккаунта; после перехода — только ключ. Механика должна быть автоматической: любое решение, требующее звонка в поддержку, проваливает задачу по условию.

**Решение — четыре механизма. Первый и четвёртый обязательны, второй и третий вместе образуют выход из ситуации.**

### 7.1. Уведомление на FIRST_BIND (обязательно, самое дешёвое)

Сегодня уведомление уходит **на сброс** привязки (`hwid.service.ts:562-575`), но **не на первую привязку** — ветка `FIRST_BIND` пишет `hwid_history`, зовёт `licenses.activate` и логирует, и на этом всё. То есть событие, после которого лицензия становится непригодна для законного владельца, происходит **молча**.

Добавляется письмо владельцу (`license.userId`): продукт, время, страна/IP, и **ссылка на отзыв привязки** (7.2). Без него любая механика восстановления бесполезна: человек узнаёт о краже, только когда сам сядет запускать — возможно, через неделю.

**Ключ лицензии в это письмо не кладётся.** Отдельно отмечаю как дефект, который переход усугубляет: `hwid.service.ts:569` (`licenseKey: license.key`) и `digiseller.service.ts:987` кладут ключ в payload уведомления. Пока ключ был одним из двух факторов, это была неприятность. Когда он становится **единственным** удостоверением, каждое такое письмо — учётные данные открытым текстом в почтовом ящике, живущие вечно. В уведомлениях ключ надо заменить на последние 4 символа (`····-9877`) плюс название продукта; полный ключ — только в кабинете, как и решил владелец.

### 7.2. Оспаривание первой привязки из кабинета, не расходующее лимит

Внутри `N` дней (настройка `limits.hwid.first_bind_dispute_days`, по умолчанию 7) после `FIRST_BIND` владелец лицензии может из кабинета отменить эту привязку: `countsAgainstLimit: false`, новая причина `HwidEventReason.FIRST_BIND_DISPUTE`.

Механика уже есть — приватный `reset()` принимает `countsAgainstLimit`, а `adjustCounter` существует ровно как компенсация. Меняется узкая ветка: `resetBySelf` сегодня жёстко ставит `countsAgainstLimit: true` и проверяет кулдаун и лимит.

**Почему это работает и почему это ответ на возражение про предъявительский документ.** Отменить привязку может **только тот, кто входит в аккаунт, которому принадлежит лицензия** (`license.userId`) — то есть владелец в том смысле, в каком его определяет система. У вора есть ключ, но нет аккаунта. Получается ровно то разделение, ради которого владелец отклонил возражение: **ключ даёт payload, аккаунт даёт контроль над привязкой**. Ключ перестаёт быть полноценным предъявительским документом — он предъявительский только на чтение.

### 7.3. Ротация ключа тем же действием

Отмена оспоренной привязки **выдаёт новый ключ** той же строке лицензии; старый умирает немедленно (`licenses.key` UNIQUE, обновляется в той же транзакции).

**Без этого пункта 7.2 бесполезен**: вор сохраняет рабочий ключ и просто перепривязывается на следующий день, а честный владелец жжёт попытки в гонке, которую не выигрывает.

Ротация дёшева и безопасна, потому что проверено: **`licenses.key` ни на что не ссылается**. Журналы (`payload_issues`, `launcher_log_batches`, `hwid_history`, `anti_fraud_events`) хранят `licenseId`; Digiseller хранит `licenseId`; ключ фигурирует только как отображаемое значение. Внешним ключом он не является нигде.

Что при этом надо поправить (иначе разъедется): `digiseller.service` возвращает `licenseKey` в результате заказа, и карточки старых заказов покажут устаревшее значение — рендерить надо из строки лицензии, а не из снимка в заказе. И пользователю придётся вставить новый ключ в загрузчик — это цена, и она правильная: та же цена, что у смены пароля.

### 7.4. Окно автоматической первой привязки

`licenses.first_bind_open_until` (новая nullable-колонка, ставится в `issue()` как `issuedAt + M часов`, `M` — настройка, по умолчанию 24).

- Первая привязка **внутри** окна — автоматическая, ровно как сегодня. Честный покупатель, запускающий продукт в день покупки, не замечает ничего.
- Первая привязка **после** окна — требует, чтобы владелец нажал в кабинете «Разрешить привязку», что открывает окно на 15 минут.

**Почему окно, а не подтверждение всегда.** Подтверждение всегда — это лишний шаг для 100% честных покупателей ради сценария, который случается у единиц, и оно ломает основной путь «купил → скачал → запустил». Утёкший ключ, наоборот, почти всегда используется **позже** первого запуска покупателя: между утечкой и эксплуатацией стоит человек, который должен ключ заметить, скопировать и попробовать. Окно бьёт по этому зазору и стоит одной колонки и одного эндпоинта кабинета.

Отдельно: колонку `first_bind_open_until` нельзя ставить всем существующим лицензиям задним числом — иначе всякий, кто купил лицензию месяц назад и ещё не запускался, получит требование подтверждения без предупреждения. При миграции существующим строкам ставится NULL = «окно не применяется».

### Детекция сверху (не механика восстановления, но питает её)

`FIRST_BIND`, чей IP/страна расходятся со страной последнего входа владельца, → `AntiFraudEvent(NEW_COUNTRY | HWID_CHANGE, HIGH)`. Оба значения в enum уже есть. Это не блокирует ничего (`actionTaken: 'logged_only'`), но даёт поддержке список для проактивной проверки — при этом от пользователя по-прежнему не требуется никуда звонить.

Оракул «ключ существует» через общее с `/license/check` состояние.** Подтверждено: `/logs` инкрементил `lk:fail:` и не проверял порога, `/check` порог проверял — разница исходов читалась по тому, наступил ли отказ у своего заведомо рабочего ключа. `resolveForLog` при этом не фильтровал по `productId`, то есть оракул отвечал на «ключ жив вообще». Приём логов теперь **не трогает ось 1 ни порогом, ни учётом**: расход бюджета одинаков при любом исходе, пространства имён Redis у путей разные (`license-key.service.ts:311, 553`), `source` убран из сигнатуры `resolveForLog`, чтобы связь нельзя было восстановить случайной правкой. Заодно исчез усилитель «10 запросов в /logs кладут /check и /payload всему NAT».

**3. Терминальный 429 невиновному за общим IP.** Подтверждено: `assertSourceUnderThreshold` отказывает до разрешения ключа, ось фактически чистый IP (`apiKeyId` один на сборку), код 429 по приложению Б ТЗ повторять нельзя. Две правки:
- **Считаются РАЗЛИЧНЫЕ псевдонимы, а не попытки** (`license-key.service.ts:439`, множество вместо `INCR`). Десять нажатий «повторить» с одной опечаткой — один элемент; сканер по списку тратит элемент на догадку.
- **503 `SERVICE_UNAVAILABLE` + `Retry-After` вместо 429 `RATE_LIMITED`** (`license-key.service.ts:421`). Это ровно то решение, которое проект уже принял дважды в этом же модуле: `payload-admission.service.ts:18-21` и `limit_req_status 503` в `docker/nginx/snippets/lp-locations.conf:115-120`. Новой ветки у C++-клиента не появляется: `SERVICE_UNAVAILABLE` уже в контракте, и `@json503` в nginx отдаёт тот же код.

**4. Вечная блокировка источника: `INCR` и `EXPIRE` разными командами.** Подтверждено (дефект №26 из `docs/LIVE-RUN-AUDIT.md`, повторённый заново). Введены `addDistinct` (`license-key.service.ts:707`) и `bumpWindow` (`:755`): окно создаётся `SET ... EX ... NX` одной командой, а множества самовосстанавливаются — срок ставится и при `TTL = -1`, причём с обеих сторон, и на записи, и на чтении (`:395-406`). Тот же дефект был в оси 2 (`trackDistinct`) — вылечен тем же помощником. Префикс оси 1 сменён с `lk:fail:` на `lk:miss:`: старые записи в Redis — строки, `SCARD`/`SADD` по ним дали бы `WRONGTYPE` и молчаливый fail-open, у записей без TTL — навсегда.

**5. Сортировка утёкшей выгрузки шла полностью бесшумно.** Подтверждено: живой ключ промахом не является, счётчик не растёт, строки журнала нет, пороги оси 2 при одном HWID и одной подсети не пересекаются. Отказом это не лечится — за CGNAT честных ключей столько же. Добавлена **ось 1б, только наблюдение**: различные РАЗРЕШЁННЫЕ ключи с источника за час (`license-key.service.ts:464`, `lk:src:`, порог 25, настройка `limits.license_key.distinct_key_per_source_per_hour`), пишет одно событие антифрода `logged_only` на пересечении и не отказывает никогда. Ложное срабатывание за большим NAT возможно, признано в комментарии.

**6. `renewalAvailable` не срабатывал ровно в том случае, ради которого сделан.** Подтверждено: `licenses.service.ts:83-97` создаёт продление со `status: PENDING`, а `renewalHint` фильтровал по одному `ACTIVE`. Условие исправлено на `status: { in: [PENDING, ACTIVE] }` (`launcher.service.ts:522`), проверка «живая по дате» сохранена.

**7. Регулярка ключа разошлась с генератором.** Подтверждено: `SLUG_RE` продукта допускает дефисы и длину до 64, `generateLicenseKey` собирает ключ как `SLUG.toUpperCase() + четыре группы`, а `LICENSE_KEY_RE` требовала префикс `[A-Z0-9]{2,16}` без дефисов. Продукт `gta-5` дал бы ключи `GTA-5-…`, которые ValidationPipe отбивает голым 400 без текста в проде. Регулярка приведена к `SLUG_RE` (`dto/license-key.ts:58`), потолок длины держит прежний `MaxLength(64)` = ширина колонки.

Сопутствующее: `payload.service.ts:650` — `SERVICE_UNAVAILABLE` без `licenseId` больше не пишет строку в `payload_issues` (иначе сканер за порогом давал бы по INSERT на запрос); OpenAPI-описания в `launcher.controller.ts` приведены в соответствие; в `apps/api/prisma/seed.ts` добавлены две настройки и переписаны комментарии к порогу оси 1.

# ОТВЕРГ

- **«`LICENSE_NOT_ASSIGNED` — оракул складских ключей».** Различие 403/404 действительно есть, но привязать такую лицензию нельзя: `launcher.service.ts:209` отказывает до `bindOrVerify`. Схлопывание в общий 404 стоило бы живому покупателю реселлера внятного «активируйте ключ в кабинете» ради информации, которой у держателя утёкшей выгрузки и так нет применения.
- **«`resolveForLog` не фильтрует по `productId`» как отдельный дефект.** Фильтровать не по чему: продукт в теле отчёта не передаётся и передаваться не должен. После правок 1-2 наружу это не наблюдаемо.
- **«Счётчик промахов должен отвечать на проверку списков»** — заявление в шапке файла было неверным, а не код. Исправлено переписыванием заявления и добавлением оси 1б, а не усилением оси 1.
- **Отрицательный кэш на 60 с** — оставлен: он кэширует только фактически несуществующие ключи, риск ограничен минутой у ключа, выпущенного сразу после неудачной попытки.

# ОСТАЛОСЬ (подтверждено кодом, вне `launcher/`)

Маскировка идёт по имени свойства (`audit.service.ts:185`). **Наивная правка вредна**: `key` — имя поля и у настроек, и у шаблонов уведомлений, и добавление его в список ослепит аудит настроек. Правильная — проекция на месте вызова (`select`/явный объект вместо целой строки) во всех `audit.record` по лицензиям.
2. **Ключ в письмах и в `notifications.payload` открытым текстом**: `hwid.service.ts:565-574`, `digiseller.service.ts:987`, шаблон `prisma/seed.ts:400-403`. Посылка владельца «ключ виден только в личном кабинете» кодом не подтверждается; реселлер видит `key` целиком (`licenses.service.ts:393-400`, `include` без `select`).
3. **Перехват первой привязки.** Живой, выданный, ни разу не запущенный ключ достаётся тому, кто пришёл первым: `launcher.service.ts:301` → `hwid.service.ts:118-183` создаёт привязку и запускает оплаченный срок. Внутри `launcher/` не лечится — нужен либо второй фактор на первую привязку, либо, минимально, уведомление владельцу на `FIRST_BIND` (сегодня его нет; на `hwid.reset` — есть).
4. **Таблицы контракта в `docs/TZ-LAUNCHER.md` (строки 547-565 и 745-765) не тронуты**: в них жив `LICENSE_NOT_FOUND` и нет `LICENSE_KEY_INVALID`, `LICENSE_NOT_ASSIGNED`, `LICENSE_NOT_ACTIVATED`. Актуальное — в разделе ниже.

То же уже верно для 503 от `PayloadAdmissionService`. Трогать общий фильтр не стал: понижение уровня для 503 заглушило бы `STORAGE_UNAVAILABLE`, по которому как раз надо будить человека.

# ИТОГОВЫЙ КОНТРАКТ ДЛЯ C++-КЛИЕНТА

**Общее для всех четырёх методов.** База `/api/v1`. Обязательные заголовки на КАЖДЫЙ запрос (`SignatureGuard`):

```
X-Api-Key:    <префикс ключа сборки>
X-Timestamp:  <unix-время, секунды>          окно ±300 с (security.request_signature.window_sec)
X-Nonce:      <16 случайных байт, hex>       повтор в пределах окна = REPLAY
X-Signature:  hex(HMAC-SHA256(secret, canon)) нижний регистр
canon = METHOD "\n" path "\n" timestamp "\n" nonce "\n" hex(sha256(rawBody))
```
`path` — без query-строки; `rawBody` — байты на проводе (для GET пустая строка). Подпись покрывает тело целиком и ни одного заголовка, кроме этих четырёх. Ключ лицензии — только в ТЕЛЕ, нормализуется сервером (trim, удаление пробелов, верхний регистр).

Единая форма ЛЮБОЙ ошибки:
```json
{"statusCode":403,"code":"LICENSE_EXPIRED","message":"…","requestId":"…","timestamp":"…","details":{…}}
```
Ветвиться ТОЛЬКО по `code`. Поля сверх `code`/`message` приезжают внутри `details` (в частности `details.renewalAvailable: true`).

---

### 1. `POST /api/v1/launcher/license/check` → 200

Единственный метод, которому разрешено привязать устройство и запустить срок. Scope не требуется.

Запрос: `{"productSlug":"fc26","hwid":"WD-WCC4N1234567","clientVersion":"1.4.2","licenseKey":"FC26-3HJ4-XUND-ETAZ-9877"}`
`hwid` ≤128, нормализован клиентом; `clientVersion` строго `major.minor.patch`; `licenseKey` — `SLUG-XXXX-XXXX-XXXX-XXXX`, слаг может содержать дефисы, группы из алфавита `ACDEFGHJKMNPQRTUVWXYZ2346789`.

Ответ 200 + заголовок `X-Recheck-After: <сек>`:
```json
{"status":"ACTIVE","expiresAt":"2026-09-05T…Z|null","productName":"…","planName":"…",
 "update":{"available":true,"mandatory":false,"version":"1.5.0","versionCode":1005000}|null,
 "notice":null,"recheckAfterSec":300}
```

| code | HTTP | Повтор | Что делает клиент |
|---|---|---|---|
| `SIGNATURE_MISSING` / `SIGNATURE_INVALID` | 403 | нет | дефект сборки, остановиться |
| `SIGNATURE_EXPIRED` | 403 | да, после синхронизации часов | |
| `REPLAY` | 403 | да, с новым nonce | |
| `PRODUCT_NOT_FOUND` | 404 | нет | дефект сборки |
| **`LICENSE_KEY_INVALID`** | **404** | нет | «Ключ не найден. Проверьте ключ в личном кабинете» — один код на «нет такого», «чужой продукт» и «валидный мусор» |
| **`LICENSE_NOT_ASSIGNED`** | **403** | нет | «Ключ не привязан к аккаунту — активируйте его в кабинете» |
| `LICENSE_EXPIRED` | 403 | нет | ссылка на продление; при `details.renewalAvailable === true` — «продление найдено в кабинете, возьмите там новый ключ» |
| `LICENSE_BLOCKED` | 403 | нет | «обратитесь в поддержку» |
| `LICENSE_REVOKED` | 403 | нет | стереть секреты; `details.renewalAvailable` возможен |
| `HWID_MISMATCH` | 403 | нет | стереть секреты, предложить сброс привязки |
| `DEVICE_BLOCKED` | 403 | нет | «обратитесь в поддержку» |
| **`SERVICE_UNAVAILABLE`** | **503** | **да, экспоненциально, не раньше `Retry-After`** | временно; НЕ терминальный экран |
| `BAD_REQUEST` | 400 | нет | не прошла валидация тела; в проде без текста |

`LICENSE_NOT_FOUND` и `RATE_LIMITED` на этом эндпоинте больше не приходят.

---

### 2. `POST /api/v1/launcher/payload` → 200, `application/octet-stream`

Требует scope `launcher:payload`. Лицензия и HWID **проверяются, но не привязываются**: без предварительного `license/check` будет `LICENSE_NOT_BOUND`.

Запрос: `{"productSlug":"fc26","hwid":"…","sessionKey":"<hex>","licenseKey":"FC26-…"}`, тело ≤8 КБ. `sessionKey` обязан быть НОВЫМ на каждый запрос. Опционально `X-Client-Version` (заголовок, вне подписи).

Ответ 200: сырой шифротекст AES-256-GCM (ключ — HKDF-SHA256 от `sessionKey`), заголовки `X-Payload-Nonce`, `X-Payload-Tag`, `X-Payload-Sha256`, `X-Payload-Size`, `X-Payload-Version`, `Cache-Control: no-store`. Три последних входят в AAD вербатим.

| code | HTTP | Повтор |
|---|---|---|
| `SIGNATURE_*` / `REPLAY` | 403 | как выше |
| `API_KEY_SCOPE` | 403 | нет, дефект сборки |
| `SESSION_KEY_REUSED` | 400 | нет, дефект клиента |
| `PRODUCT_NOT_FOUND`, `LICENSE_KEY_INVALID` | 404 | нет |
| `LICENSE_NOT_ASSIGNED`, `LICENSE_EXPIRED`, `LICENSE_BLOCKED`, `LICENSE_REVOKED`, `DEVICE_BLOCKED`, `HWID_MISMATCH` | 403 | нет |
| `LICENSE_NOT_BOUND`, `LICENSE_NOT_ACTIVATED` | 403 | да — вызвать `license/check` и повторить |
| `PAYLOAD_NOT_READY` | 409 | да, с задержкой |
| `UPDATE_REQUIRED` | 426 | после обновления |
| `RATE_LIMITED` | 429 | **нет** — это порог выдач на ЛИЦЕНЗИЮ, единственный оставшийся 429 |
| `SERVICE_UNAVAILABLE`, `PAYLOAD_UNAVAILABLE`, `STORAGE_UNAVAILABLE`, `PAYLOAD_CORRUPT`, `ISSUE_NOT_RECORDED`, `DATABASE_UNAVAILABLE` | 503 | да, экспоненциально, `Retry-After` |

---

### 3. `GET /api/v1/launcher/update?productSlug=fc26&clientVersion=1.4.2` → 200

Требует scope `launcher:update`. Ключ лицензии не требуется и не принимается. Query в подпись не входит — `path` режется по `?`.
Ответ: `{"available":false,"mandatory":false,"version":null,"versionCode":null}`. Отказы: `SIGNATURE_*`, `API_KEY_SCOPE` (403), `PRODUCT_NOT_FOUND` (404).

---

### 4. `POST /api/v1/launcher/logs` → **202 всегда**

Scope не требуется. Тело: `{"kind":"crash|error|diagnostic|user_report","clientVersion":"1.4.2","summary":"…≤512","licenseKey":"…"}`; `licenseKey` НЕОБЯЗАТЕЛЕН. Ответ: `{"accepted":true}`.

Клиенту важно: ответ 202 не означает, что отчёт сохранён — при исчерпании бюджета источника он молча отбрасывается. Ветвиться по этому эндпоинту не на чем; отправлять отчёты пачками, а не в цикле. Секреты, `sessionKey`, содержимое payload и сырой Disk ID в `summary` класть нельзя — журнал читают люди.
