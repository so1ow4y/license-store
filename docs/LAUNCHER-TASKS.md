# Загрузчик — задание по итогам ревью

Составлено после разбора `Griloder/Platform/` (21 файл, ~1170 строк).
Ревью: шесть срезов кода, каждая находка перепроверена независимо,
43 сырых наблюдения → 8 подтверждённых дефектов, 8 отклонено как ложные.

**Что важно понимать про состояние.** Криптографическое ядро сделано
аккуратно и сходится с сервером по контрольным векторам побайтово.
Транспортный слой в текущем виде не отправит ни одного успешного запроса.
Это не противоречие: сломано ровно одно место, но оно на пути каждого запроса.

## Блок 0. Без этого не работает ничего

### 0.1. Путь: одно поле на две разные вещи

**Файл:** `Platform/Http.cpp:269` и `:279`

```cpp
const std::wstring wUrl = baseUrl_ + Widen(req.path) + Widen(req.query);   // :269
...
SignRequest(secret, upperMethod, req.path, req.body, ts, nonce, sig);      // :279
```

`req.path` используется и как суффикс URL, и как подписываемый путь.
При этом два комментария в коде противоречат друг другу:

- `Config.h:15` — «Base URL … Includes /api/v1 — endpoint paths in this codebase start at /auth/… or /launcher/…»
- `Http.h:34` — `path; // e.g. "/api/v1/launcher/license/check" — path we SIGN`

Третьего варианта нет, поле одно. Что получится:

| Что передать в `req.path` | URL | Подпись | Итог |
|---|---|---|---|
| `/api/v1/launcher/...` | `https://d/api/v1/api/v1/launcher/...` | верная | **404** |
| `/launcher/...` | верный | над укороченным путём | **403 SIGNATURE_INVALID** |

Сервер подписывает **абсолютный** путь, включая `/api/v1` — так в векторах,
так в `signature.service.ts`, так в ваших же прошедших тестах.

**Что сделать.** Развести понятия. Рекомендую вариант, где неоднозначности
не остаётся физически:

```cpp
// Config.h — база БЕЗ префикса пути
inline constexpr wchar_t kBaseOrigin[] = L"https://YOUR-DOMAIN";
inline constexpr char    kApiPrefix[]  = "/api/v1";

// HttpRequest.path — относительный: "/launcher/license/check"
// Абсолютный собирается один раз и идёт И в URL, И в подпись:
const std::string signPath = std::string(config::kApiPrefix) + req.path;
const std::wstring wUrl    = std::wstring(config::kBaseOrigin) + Widen(signPath) + Widen(req.query);
SignRequest(secret, upperMethod, signPath, req.body, ts, nonce, sig);
```

Одна переменная — одно значение, разойтись нечему.

**Тест, который это закрепит:** проверить, что подписанный путь буквально
равен пути из собранного URL. Он ловит регрессию мгновенно.

### 0.2. Подпись до входа — ошибка была в моём ТЗ

**Файл:** `Platform/Http.cpp:260`

```cpp
if (secret.empty()) { HttpResponse r; r.transportFailed = true; return r; }
```

Вы реализовали спецификацию буквально и уперлись в её противоречие:
§3.5 говорил «секрет выдаётся при первом входе», а Приложение А требовало
подписи для `/auth/login`. Подписать первый вход было нечем. **Это мой
недосмотр, не ваш.**

**Спецификация исправлена** — [TZ-LAUNCHER.md §3.5](TZ-LAUNCHER.md), ревизия 2:

> Секрет один и один на сборку продукта. `signing_secret` соответствует
> `X-Api-Key`, поставляется с загрузчиком и подписывает **все** запросы,
> включая вход. Посессионного секрета нет.

Что чем занимается:

| Механизм | Что доказывает |
|---|---|
| Подпись | запрос от нашей сборки, не воспроизведён |
| JWT | кто пользователь |
| HWID | на какой машине |

**Что сделать в коде:**

- Секрет берётся из `Config.h`, а не из ответа сервера.
- Убрать из `Http.h` комментарий про «signing secret comes from /auth/2fa/verify».
- `SetSigningSecret()` оставить — пригодится для ротации ключа без пересборки, — но начальное значение подставлять из конфигурации в конструкторе.

### 0.3. Пустой секрет маскируется под сетевую ошибку

Тот же `Http.cpp:260`: незаполненный конфиг возвращает `transportFailed`.
В строгом режиме (§6.2.1) верхний слой прочитает это как «сети нет» и
остановит работу с неверной причиной. Диагностика уедет в сторону.

**Что сделать.** Отдельный статус — `Status::ConfigNotSet` или подобный —
и проверка заполненности `kBaseOrigin` / `kApiKey` / `kSigningSecret`
**на старте процесса**, до первого запроса. Сейчас там `YOUR-DOMAIN`
и `lp_pk_PLACEHOLDER`, и сборка с забытым конфигом выглядит как сбой сети.

## Блок 1. Устойчивость

### 1.1. TokenManager залипает навсегда при исключении

**Файл:** `Platform/TokenManager.cpp:49-57`

```cpp
refreshing_ = true;
lk.unlock();
const bool ok = refresh_ ? refresh_(oldRefresh, newSnap) : false;  // ← бросит
lk.lock();
refreshing_ = false;                                                // ← не дойдём
```

`Refresher` — `std::function` без `noexcept`, внутри сетевой вызов и разбор
ответа. Любое исключение оставляет `refreshing_ == true` навсегда. Мьютекс
при этом свободен, поэтому все последующие вызовы `GetFreshAccessToken()`
уходят в `cv_.wait` и не просыпаются. Клиент виснет молча, без единого лога.

Обиднее всего, что класс написан ровно ради дисциплины «обновляет один
поток», и ломается именно она — причём не в сторону гонки, а в полную
остановку.

**Что сделать:**

```cpp
struct RefreshGuard {
    TokenManager* m;
    ~RefreshGuard() {
        std::lock_guard<std::mutex> lk(m->mu_);
        m->refreshing_ = false;
        m->cv_.notify_all();
    }
};
```

Взводится сразу после `refreshing_ = true`. Исключение пробрасывается
наверх, но менеджер остаётся рабочим. Плюс `try/catch` вокруг `refresh_`,
трактующий исключение как `ok == false`, — тогда сработает и штатная
очистка состояния.

### 1.2. Отказ ГСЧ даёт запрос без X-Nonce

**Файлы:** `Platform/Http.cpp:276`, `Nonce.cpp:22`, `Http.cpp:288`

`GenerateNonceHex()` возвращает пустую строку при сбое `BCryptGenRandom`.
Возврат не проверяется. Дальше подпись честно считается над каноникой
с пустым полем NONCE, а лямбда `add` глотает пустое значение:

```cpp
auto add = [&](const std::wstring& name, const std::wstring& value) {
    if (value.empty()) return;      // ← X-Nonce молча исчезает
```

На проводе — валидная `X-Signature` без `X-Nonce`. Сервер ответит
`MISSING_HEADERS`, цикл повторит это ещё дважды, а причина будет указывать
куда угодно, только не на генератор случайных чисел.

**Что сделать.** Проверять `nonce.empty()` сразу и возвращать фатальный
статус. Для обязательных заголовков завести `addRequired`, которая на пустом
значении не молчит.

### 1.3. Пересинхронизация времени тратит попытку

**Файл:** `Platform/Http.cpp:324-342`

Ветка `SIGNATURE_EXPIRED` заканчивается `syncedThisCall = true; continue;`
внутри `for (attempt = 1; attempt <= kMaxRetries; ...)`. Если 403 пришёл
на третьей попытке — например, две первые ушли на 503 с задержками, —
`continue` доводит `attempt` до 4, цикл кончается, наверх уходит тот же 403.
При этом сдвиг часов уже вычислен, и повтор прошёл бы успешно.

ТЗ §3.4 требует однократной синхронизации **и повтора**; сейчас повтор условный.

**Что сделать.** Считать времязависимый повтор отдельно от транспортных:
либо `--attempt; continue;`, либо вынести resync во внешний `do/while`
с собственным одноразовым флагом.

### 1.4. SecureZero объявлен, но не вызывается ни разу

**Файлы:** `Common.h:19` (объявление), `Dpapi.cpp:65,74,81-84`, `Http.cpp:250-257`

Функция введена с комментарием про «wipe secrets contract» и не используется
нигде. В открытом виде остаются:

- `UnprotectString` — промежуточный `std::vector<uint8_t>` с расшифрованным секретом просто выходит из области видимости;
- `Unprotect` — копия из `out.pbData`, затем `LocalFree` без затирания;
- `ProtectString` — копия plaintext в `bytes`;
- `HttpClient::Send` — копии `signingSecret_` и `accessToken_` в локальные `std::string` на каждый запрос.

ТЗ §10 требует, чтобы секреты не лежали открыто, §7.2.5 — затирать буферы
после использования. При падении с дампом или уходе страницы в своп секрет
уезжает на диск.

**Что сделать.** Вызывать `SecureZero` перед выходом из `Protect`/`Unprotect`
и перед `LocalFree`. Для секретов в `HttpClient` — тип-обёртка со стирающим
деструктором вместо голого `std::string`.

### 1.5. Тело ответа читается без предела

**Файл:** `Platform/Http.cpp:218-230`

Цикл наращивает вектор до конца потока без лимита. На своей машине
пользователь может подставить корневой сертификат и отдать клиенту
бесконечный ответ — процесс съест память и упадёт.

**Что сделать.** Лимит в `Config.h` (для JSON-ответов хватит 1–2 МБ),
при превышении — обрыв и отдельный статус. Отдельный лимит понадобится
для payload, когда дойдём до него.

### 1.6. Content-Type не подставляется по умолчанию

**Файл:** `Platform/Http.cpp:299`

§2.1 требует заголовок при наличии тела. Сейчас он берётся только из
`req.contentType`, и забывчивость вызывающего кода превратится в 400/415
при формально валидной подписи.

**Что сделать.** При непустом теле и пустом `contentType` подставлять
`application/json; charset=utf-8`.

## Что отклонено как ложные находки

Чтобы не тратить время на несуществующие проблемы:

| Подозрение | Почему не проблема |
|---|---|
| Чтение за буфером в `HwId.cpp:100` | `std::string` гарантирует NUL по индексу `size()`, смещение проверено на `>= hdr.Size` |
| Нормализация Disk ID расходится с сервером | серийники из `STORAGE_DEVICE_DESCRIPTOR` — ASCII; сервер всё равно нормализует присланное перед хешированием |
| Утечки `HINTERNET` в `DoOneRequest` | проверено построчно: каждый ранний выход закрывает ровно открытые хендлы |
| Backoff должен быть 1/2/4 с, а не 1/2 | при трёх попытках пауз ровно две; 4 с была бы паузой перед несуществующей четвёртой |
| Сравнение секретов не за постоянное время | в `Platform/` нет ни одного сравнения секрета — подпись только вычисляется |
| Знаковость `char` в `Hex`/`NormalizeDiskId` | сравнения с ASCII-литералами; при отрицательном `char` условия не выполняются, байт проходит насквозь — верное поведение |
| Хеш пустого тела неверен | `Sha.h:21` содержит `e3b0c442…b855`, совпадает с сервером |
| Query не входит в подпись | так и требуется по §3.1 |

## Что сделано хорошо

Не для вежливости — эти решения стоит сохранить при рефакторинге.

**Volume → PhysicalDriveN через `IOCTL_STORAGE_GET_DEVICE_NUMBER.**
Неочевидно и правильно: при динамических дисках, Storage Spaces и вендорских
RAID буква диска не говорит ничего о том, какой накопитель за ней стоит.

**ASCII-only приведение регистра в подписи.** `toupper` зависит от локали
и способен задеть байты UTF-8 — здесь этого избежали сознательно.

**Кириллица в тесте задана escape-последовательностями UTF-8.** Исходник,
сохранённый в CP1251, дал бы другие байты и «загадочно» расходящуюся подпись.

**`Rfc7231ToUnix` имбьютит `std::locale::classic()`** перед `std::get_time`.
Без этого разбор `Sun`/`Nov` ломался бы именно на русской локали — то есть
у целевой аудитории, и незаметно.

**Заголовки ответа нормализуются в нижний регистр** — поиск `date`
и `x-recheck-after` не зависит от того, как их написал сервер или прокси.

**Проверка сертификата не отключена**, и это зафиксировано комментарием
ровно там, где обычно и появляется `WINHTTP_OPTION_SECURITY_FLAGS`.

**HMAC через `BCRYPT_ALG_HANDLE_HMAC_FLAG`**, а не самодельная обвязка
ipad/opad, и `NTSTATUS` проверяется у каждого вызова BCrypt.

**Fail-hard в `HwId`** без подстановки MAC, MachineGuid или имени машины —
прямое требование §4.3, и его легко нарушить «чтобы работало».
