# Свой почтовый сервер

## Проект

# Свой почтовый сервер для pxcheats.com — проект перехода

## Итог решения в трёх строках

Один свой образ postfix, **три контейнера** из него и рядом: `postfix-out` (внутренний, без опубликованных портов — сегодняшняя проверенная отправка), `postfix-mx` (публичный, порты 25 и 587), `opendkim` (единственное место, где лежит закрытый ключ). Разделение не ради красоты: контейнер, торчащий в интернет, **не содержит ни одной директивы, разрешающей релей по IP**, поэтому открытым релеем он не может стать даже при ошибке в сети докера. Переход разбит на три независимо откатываемых шага, между которыми — живая проверка доставки в Gmail.

```
API (nodemailer, SMTP_HOST=postfix, порт 25, без auth)
      │  внутренняя сеть compose, наружу не опубликована
      ▼
 postfix-out ──milter──► opendkim ◄──milter── postfix-mx
      │                  (ключ DKIM)              ▲   │
      ▼                                      25 ──┘   │ 587 (TLS+AUTH)
  интернет (MX получателя)              интернет ──────┘
                                             │
                                    support@/dmarc@/postmaster@
                                             ▼
                                  kotenkovgrigorij64@gmail.com
```

## 1. Свой образ, а не гнутый чужой

**Решение: свой образ на `debian:bookworm-slim`, конфиги — файлы в репозитории, при старте ничего не генерируется.**

Обоснование — по убыванию веса:

**Чужой образ перегенерирует main.cf при каждом старте.** Это не мелкое неудобство, а несовместимость с задачей. Приём почты — это `virtual_alias_domains`, `virtual_alias_maps`, пустой `mydestination`, `postscreen` в master.cf, служба `submission` со своим набором `-o`-переопределений, SASL. Ни одно из этих полей у образа-отправителя не выведено в переменные. Значит, любой путь «догнуть» сводится к тому, чтобы после его entrypoint дописать `postconf -e ...` — то есть завести свой entrypoint, который правит чужой сгенерированный файл. Вы всё равно сопровождаете конфигурацию, но делаете это вслепую: не видите итог целиком, и каждое обновление базового образа может переписать под вами строку, о которой вы не знали.

**`image: boky/postfix:latest` в `C:/Users/user/work/kwork/license-platform/docker-compose.prod.yml` — уже сейчас угроза работающей отправке.** Проверенная живая доставка проверена для того образа, который скачался в тот день. Следующий `docker compose pull` или пересоздание на чистой машине притащит другой. Свой образ с базой, приколоченной по digest, убирает этот класс сюрпризов насовсем.

**master.cf от чужого образа всё равно придётся заменить целиком.** Submission и postscreen живут именно там, а не в main.cf. Переопределять весь master.cf, оставляя чужой main.cf, — худший из миров.

**Стоимость сопровождения своего образа честно мала.** Dockerfile — это `apt-get install -y postfix postfix-pcre libsasl2-modules sasl2-bin ca-certificates`, `COPY` трёх конфигов и entrypoint строк на двадцать. Синтаксис main.cf стабилен уже полтора десятка лет; директивы, которые тут используются, не менялись со времён postfix 2.10. Обновление безопасности = пересборка на свежей базе, то есть строчка в deploy.

**Почему Debian, а не Alpine.** Пакет postfix в Debian — эталонная сборка, на которой написана вся документация и все ответы в интернете; SASL-модули, PCRE-таблицы, `opendkim-tools` ставятся штатно и совпадают по путям с любым руководством. Alpine даст экономию ~40 МБ образа на диске (не памяти) и musl-сборку, из-за особенностей которой отладка ночью в проде обходится дороже, чем эти 40 МБ.

**Что берём из чужого образа.** Ничего кроме опыта: перед выкладкой снимаем с работающего контейнера `postconf -n` и `postconf -M` и используем как эталон — новый main.cf обязан покрывать всё, что там есть, по смыслу (см. раздел 2).

**opendkim — отдельным контейнером, не вторым процессом в образе postfix.**
- Если opendkim падает, docker его перезапустит; процесс, запущенный из entrypoint рядом с `postfix start-fg`, умрёт молча, и письма пойдут неподписанными — ровно та тихая поломка, которую комментарии в compose уже описывают как самую дорогую.
- Закрытый ключ монтируется **только** в контейнер opendkim. Публичный `postfix-mx`, который принимает соединения от кого угодно, ключа не видит вовсе.
- Оба postfix ходят к одному opendkim через `inet:opendkim:8891` — одна конфигурация подписи, а не две.
- Цена: ~12–15 МБ RSS.

**Ловушка milter, которую надо знать заранее.** opendkim *подписывает* только письма от клиентов из `InternalHosts`/`ExternalIgnoreList`; для всех прочих он *проверяет* чужие подписи. Milter получает IP **исходного SMTP-клиента**, а не postfix. Поэтому:
- письмо от API (адрес из подсети compose) → внутренний → подписывается;
- письмо из интернета на порт 25 → внешний → только проверяется, нашей подписи не получит (это правильно: пересылаемый спам не должен уезжать в Gmail с нашей репутацией);
- письмо из Gmail через submission → подписывается, потому что milter к порту 587 подключается явно.

`InternalHosts` с подсетью compose релея не даёт — opendkim вообще не участвует в решении «кому доставлять».

## 2. Как не сломать отправку

Главный принцип: **замена образа и открытие порта 25 — это два разных изменения, разнесённых во времени, каждое со своей проверкой и своим откатом.** Если сделать их одним заходом и Gmail начнёт ругаться, вы не будете знать, что виновато.

### Снять эталон ДО всего (на работающей системе)

```bash
docker inspect --format '{{.Image}}' lp-postfix   # точный digest — путь отката
docker exec lp-postfix postconf -n  > /root/mail-baseline-main.txt
docker exec lp-postfix postconf -M  > /root/mail-baseline-master.txt
docker exec lp-postfix postconf -d | grep -E 'mail_version'
docker exec lp-postfix postqueue -p                # должно быть «Mail queue is empty»
```

`postconf -n` — это и есть «что на самом деле настроено» у работающего отправителя. Новый main.cf сверяется с ним построчно: любое расхождение должно быть осознанным, а не случайным.

Плюс зафиксировать снаружи:
- письмо в Gmail → «Показать оригинал»: сохранить, что там `spf=pass`, `dkim=pass header.i=@pxcheats.com header.s=mail`, `dmarc=pass`;
- `dig +short mail._domainkey.pxcheats.com TXT` — записать значение, чтобы потом сравнить побайтно;
- `docker exec lp-opendkim opendkim-testkey -d pxcheats.com -s mail -vvv` (после появления контейнера) — «key OK» означает, что закрытый на сервере и открытый в DNS сходятся.

### Что именно нельзя трогать

| Параметр | Значение сейчас | Почему нельзя менять в этом же изменении |
|---|---|---|
| Имя сервиса в compose | `postfix` | `mail.service.ts:60`: `internalRelay = !env.SMTP_HOST.includes('.')`. Точка в имени включит проверку TLS-сертификата, и API перестанет отправлять с ошибкой «self-signed certificate». Имя обязано остаться без точки. |
| `SMTP_PORT` / `SMTP_SECURE` | 25 / false | Проверенный путь. |
| `myhostname` (HELO) | `pxcheats.com` | Совпадает с тем, что видел Gmail. Переезд на `mail.pxcheats.com` формально правильнее (совпадает с MX и A), но это отдельное изменение с отдельной живой проверкой. |
| DKIM: селектор `mail`, домен `pxcheats.com`, тот же файл ключа | — | Меняется только владелец процесса-подписанта, не ключ. |
| `DKIM_DOMAIN` / `DKIM_SELECTOR` в `.env.production` | не заданы | Именно поэтому nodemailer **не** подписывает и подписант один. Если их когда-нибудь задать, на письме окажутся две подписи одного селектора. |

Отдельная находка: в `.env.production` **есть** `DKIM_PRIVATE_KEY`, но нет `DKIM_DOMAIN` и `DKIM_SELECTOR`. Сейчас это безвредно (в `mail.service.ts` подпись включается только при всех трёх), но это заряженное ружьё: достаточно кому-то «дозаполнить» переменные, и появится вторая подпись. Ключ из `.env.production` **удалить** — он там ничего не делает, а его наличие подсказывает неверное действие. Ключ живёт в `.secrets/dkim-private.pem`, и только там.

### Порядок и проверки

**Шаг A — заменить отправителя, портов не открывать.**
Собрать свой образ, поднять `postfix-out` (то же имя сервиса `postfix`) + `opendkim`. `ports` не появляется. ufw не трогается.

Проверить после:
1. `docker exec lp-postfix postconf -n | diff - /root/mail-baseline-main.txt` — глазами по каждой строке.
2. `docker logs lp-api | grep 'SMTP-соединение проверено'` — это встроенный канарейка-тест: `onModuleInit` в `mail.service.ts` делает `transport.verify()` на старте. Перезапустить API и убедиться, что строка есть, а не `SMTP недоступен на старте`.
3. Живое письмо: регистрация тестового пользователя → письмо приходит в Gmail.
4. В журнале: `DKIM-Signature field added (s=mail, d=pxcheats.com)` и `status=sent ... 250 2.0.0 OK`.
5. В Gmail «Показать оригинал»: `spf=pass`, `dkim=pass`, `dmarc=pass` — сверить с эталоном из «до».
6. `postqueue -p` пуст.

Откат: вернуть `image: boky/postfix@sha256:<эталон>` и `docker compose up -d postfix`. Старый образ **не удалять** (`docker image prune` до конца перехода не запускать).

**Шаг B — приём.** Добавить `postfix-mx`, опубликовать `0.0.0.0:25:25`, открыть ufw 25, положить таблицу алиасов. `postfix-out` не трогается вообще — это и есть главная гарантия сохранности отправки.

Проверить: внешний тест релея (раздел 4), приход письма на support@, и **повторно** живую отправку платформы — просто чтобы убедиться, что вы ничего не задели.

**Шаг C — submission 587.** Отдельно, после расширения сертификата.

### Постоянная защита от регресса

Положить в репозиторий `scripts/mail-check.sh`: он делает `postconf -n` на обоих контейнерах, гоняет внешний тест релея через swaks, дёргает `opendkim-testkey` и печатает вердикт. Запускать после каждого деплоя, затрагивающего почту. Работающую отправку ломают не при переходе — её ломают через полгода правкой «на глазок».

## 3. Устройство приёма

**Какие домены принимаем.** Ровно один — `pxcheats.com`, и не как «локальный», а как виртуальный алиас-домен:

```
mydestination =                      # ПУСТО. Локальной доставки нет вовсе.
local_recipient_maps =               # пусто следом
mydomain = pxcheats.com
myorigin = $mydomain
virtual_alias_domains = pxcheats.com
virtual_alias_maps = hash:/etc/postfix/virtual
relay_domains =                      # ПУСТО. Мы никому не резервный MX.
```

Пустой `mydestination` — не экономия, а решение: в системе нет ни одного локального почтового ящика, значит нечего переполнять, нечего бэкапить, некуда доставлять по ошибке, и нет пути «письмо превратилось в команду локальной доставки».

**Куда деваем письма.** Никуда не кладём — сразу пересылаем. `/etc/postfix/virtual`:

```
support@pxcheats.com      kotenkovgrigorij64@gmail.com
dmarc@pxcheats.com        kotenkovgrigorij64@gmail.com
postmaster@pxcheats.com   kotenkovgrigorij64@gmail.com
abuse@pxcheats.com        kotenkovgrigorij64@gmail.com
```

`postmaster@` и `abuse@` — не прихоть: RFC 5321 требует первый, RFC 2142 второй, и системы репутации проверяют их существование. Отсутствие postmaster@ у домена с опубликованным MX — минус к доверию бесплатно и на ровном месте.

Никакого `@pxcheats.com` (catch-all) — это ровно то, чего ждут переборщики адресов.

Сообщения **не модифицируются**: ни футеров, ни фильтров содержимого, ни переписывания заголовков. Причина техническая: при пересылке в Gmail SPF гарантированно не сойдётся (письмо идёт с нашего IP от чужого отправителя), и единственное, что спасает пересланное письмо от спам-папки, — **уцелевшая исходная подпись DKIM отправителя**. Любая правка тела или заголовков её ломает. Поэтому: без SRS на старте (это отдельный демон postsrsd; вводить только если пойдут отказы), без спам-фильтра.

**Почему не ставим rspamd/spamassassin.** Конечный получатель — Gmail. Его фильтр лучше всего, что можно поднять на одном ядре, а rspamd съест 100–200 МБ, которых нет. Наша задача — не пропускать мусор в очередь (postscreen делает это за копейки), а не сортировать его.

**Почта на несуществующие адреса: отказ 550 в момент RCPT TO, никогда не «принять и отбить».**

```
smtpd_reject_unlisted_recipient = yes    # по умолчанию, но пишем явно
unknown_address_reject_code = 550
soft_bounce = no
```

Принять письмо, а потом сгенерировать отлуп, — это backscatter: адрес отправителя у ботов подделан, отлуп уходит невиновному, и мы оказываемся в чёрных списках как источник спама. Отказ на этапе RCPT перекладывает всю ответственность на отправителя и не стоит нам ни байта очереди.

**Боты начнут перебирать адреса в первый же день.** Против этого — `postscreen` перед smtpd:

```
postscreen_greet_action = enforce        # проверка «заговорил раньше баннера»
postscreen_pipelining_enable = yes
postscreen_pipelining_action = enforce
postscreen_non_smtp_command_enable = yes
postscreen_bare_newline_enable = yes
postscreen_access_list = permit_mynetworks
```

Тест на преждевременное приветствие отсеивает большинство спам-ботов **без единого обращения наружу** — они не умеют ждать баннер. Всё это делает один процесс postscreen, не форкая smtpd, что на одном ядре критично.

DNSBL (Spamhaus) сознательно **не включаем на старте**: это внешняя зависимость, требующая собственного резолвера (Spamhaus блокирует запросы от 8.8.8.8, и настройка тихо перестаёт работать), плюс лишний DNS-round-trip на каждое соединение. Место под него в конфиге предусмотреть комментарием, включить — если объём мусора реально станет мешать.

Greylisting не ставим: он задерживает всю легитимную почту ради проблемы, которой у нас на этих объёмах нет.

Плюс дешёвые ограничители перебора:

```
smtpd_helo_required = yes
disable_vrfy_command = yes               # VRFY — штатный инструмент перебора адресов
smtpd_hard_error_limit = 5
smtpd_junk_command_limit = 3
smtpd_error_sleep_time = 5s
smtpd_recipient_limit = 20
smtpd_timeout = 30s
message_size_limit = 10485760
```

**DNS-довесок.** Раз появился `dmarc@`, стоит дописать в `_dmarc`: `v=DMARC1; p=none; rua=mailto:dmarc@pxcheats.com`. Отчёты — ежедневный XML в архиве, отсюда и отдельный адрес.

## 4. Как не стать открытым релеем

### Структурная защита: у публичного контейнера нет разрешения релея вообще

Ключевое решение: `postfix-mx` (тот, у которого опубликованы порты) имеет

```
mynetworks_style = host
mynetworks = 127.0.0.0/8 [::1]/128
smtpd_relay_restrictions = permit_sasl_authenticated, reject_unauth_destination
```

и на порту 25 SASL выключен (`-o smtpd_sasl_auth_enable=no`). То есть на публичном порту **не остаётся ни одного `permit_*`** — только `reject_unauth_destination`. Релеить он не может ни для кого, независимо от того, какой IP-адрес ему покажется исходным.

**Зачем это нужно — конкретная ловушка докера.** Docker публикует порты в обход ufw, и при части конфигураций (userland-proxy, IPv6 без ip6tables) входящее соединение приходит в контейнер **с адреса шлюза docker-сети**, то есть изнутри `172.x.0.0/16`. Если бы в публичном контейнере стояло `permit_mynetworks` с подсетью compose — весь интернет оказался бы «своей сетью», и это открытый релей мирового масштаба, работающий ровно с той минуты, как опубликован порт. Разнесение ролей делает эту ошибку невозможной: `permit_mynetworks` живёт только в `postfix-out`, у которого портов наружу нет.

Дополнительно порт публикуем как `"0.0.0.0:25:25"` — только IPv4. AAAA у `mail.pxcheats.com` нет, входящих по IPv6 не будет, а IPv6-путь докера — как раз тот, где адрес источника теряется чаще всего.

### Директивы и что каждая делает

**Разрешение релея (главное):**

| Директива | Что делает |
|---|---|
| `smtpd_relay_restrictions = permit_sasl_authenticated, reject_unauth_destination` | Единственный параметр, который с postfix 2.10 решает «релеить или нет», и он проверяется **раньше** `smtpd_recipient_restrictions`. `reject_unauth_destination` отказывает 554, если получатель не в `mydestination`, `virtual_alias_domains`, `virtual_mailbox_domains` или `relay_domains`. Опасна не «неправильная» настройка, а **пустая**: `smtpd_relay_restrictions =` отключает проверку целиком и делает открытый релей одной строкой. |
| `mynetworks = 127.0.0.0/8 [::1]/128` (публичный) / точная подсеть compose (внутренний) | Список источников, которым релей разрешён без пароля. Задаём **явным списком**. |
| `mynetworks_style = host` | Страховка на случай, если `mynetworks` кто-то сотрёт. По умолчанию postfix берёт `subnet` и считает своей **всю подсеть сетевого интерфейса** — на хостинге это /24 соседей-арендаторов, и вы релеите для них. Это самый частый способ стать открытым релеем случайно. |
| `relay_domains =` (пусто) | По умолчанию равно `$mydestination`. Пустое означает: мы не принимаем почту «для дальнейшей передачи» ни одному домену. |
| `mydestination =` (пусто) | Нет локальных получателей — нечего перепутать. |

**Закрытие обходных путей адресации** (классические трюки обхода `reject_unauth_destination`):

| Директива | Что делает |
|---|---|
| `allow_untrusted_routing = no` | Запрещает адреса вида `user@remote@pxcheats.com` и маршрутизацию от источника `@remote:user@pxcheats.com` — адрес выглядит нашим, а доставка уходит наружу. Значение по умолчанию верное, пишем явно. |
| `allow_percent_hack = no` | Убивает `user%gmail.com@pxcheats.com` — исторический синтаксис, который postfix иначе перепишет в `user@gmail.com` **после** проверок. |
| `swap_bangpath = no` | То же для UUCP-нотации `gmail.com!user@pxcheats.com`. |
| `smtpd_authorized_xclient_hosts =` (пусто) | XCLIENT позволяет клиенту объявить себя другим IP-адресом. Пустой список — никому не позволено; заполнение этого поля обнуляет все защиты выше. `smtpd_authorized_xforward_hosts` — тоже пусто. |

**Аутентификация:**

| Директива | Что делает |
|---|---|
| `smtpd_sasl_auth_enable = no` в main.cf, `yes` только у службы `submission` в master.cf | На публичном порту 25 аутентификации нет вообще: нечего подбирать и нечем открыть релей украденным паролем. |
| `smtpd_tls_auth_only = yes` | AUTH не предлагается, пока не поднят TLS. Пароль никогда не идёт открытым текстом. |
| `smtpd_sender_login_maps` + `reject_sender_login_mismatch` (на 587) | Аутентифицированный пользователь может писать только от своего адреса. Без этого владелец учётки support@ мог бы отправлять от `noreply@` — и, что важнее, любой, кто украдёт пароль, отправлял бы от чего угодно с нашей подписью DKIM. |
| `smtpd_client_auth_rate_limit = 10` | Ограничение попыток входа с одного адреса в минуту. Заменяет возню с fail2ban, который в docker-логи json-file смотреть не умеет без отдельного файла. |

**Гигиена отправителя (не про релей, но про то же семейство):**

```
smtpd_helo_restrictions    = permit_mynetworks, reject_invalid_helo_hostname,
                             reject_non_fqdn_helo_hostname
smtpd_sender_restrictions  = permit_mynetworks, reject_non_fqdn_sender,
                             reject_unknown_sender_domain
smtpd_recipient_restrictions = permit_mynetworks, permit_sasl_authenticated,
```

### Как проверить снаружи

Обязательно **с чужой машины** — не с сервера и не из контейнера, иначе вы проверяете `permit_mynetworks`, а не защиту.

```bash
# 1. Классический релей: чужой отправитель, чужой получатель.
swaks --server mail.pxcheats.com --from probe@example.org --to проверка@gmail.com
#    ОЖИДАЕМ на RCPT TO: 554 5.7.1 ... Relay access denied

# 2. Пустой отправитель (обход наивных фильтров).
swaks --server mail.pxcheats.com --from "" --to проверка@gmail.com
#    ОЖИДАЕМ: тот же 554

# 3. Процентный трюк.
swaks --server mail.pxcheats.com --from probe@example.org \
      --to 'проверка%gmail.com@pxcheats.com'
#    ОЖИДАЕМ: 550 User unknown in virtual alias table

# 4. Двойной адрес / маршрут от источника.
swaks --server mail.pxcheats.com --to 'проверка@gmail.com@pxcheats.com'
swaks --server mail.pxcheats.com --to '@pxcheats.com:проверка@gmail.com'
#    ОЖИДАЕМ: отказ

# 5. Bang-path.
swaks --server mail.pxcheats.com --to 'gmail.com!проверка@pxcheats.com'
#    ОЖИДАЕМ: отказ

# 6. Несуществующий свой адрес.
swaks --server mail.pxcheats.com --to noreply-нет-такого@pxcheats.com
#    ОЖИДАЕМ: 550 ... User unknown  (именно на RCPT, не отлуп потом)

# 7. AUTH не должен предлагаться на 25.
openssl s_client -starttls smtp -connect mail.pxcheats.com:25 -crlf
EHLO probe.example.org
#    В ответе НЕ ДОЛЖНО быть строки 250-AUTH

# 8. VRFY закрыт.
#    VRFY support   →  502 5.5.1 VRFY command is disabled
```

**Положительный контроль — обязателен.** Легко «защититься» до неработающего сервера. С той же чужой машины:

```bash
swaks --server mail.pxcheats.com --from probe@example.org --to support@pxcheats.com
#    ОЖИДАЕМ 250, и письмо приходит в Gmail
```

и изнутри — отправка платформы продолжает работать (раздел 2).

**Внешние сервисы как второе мнение:** `mxtoolbox.com/diagnostic.aspx` (тест открытого релея, баннер, обратная запись) и open-relay-тест на `multirbl.valli.org`. Они проверяют только 25, поэтому пункты 1–8 руками всё равно нужны.

Прогонять этот список **после каждого** изменения почтового конфига, не только один раз при запуске. Открытым релеем становятся не в день установки.

## 5. Submission 587

**Механизм паролей: Cyrus SASL с базой `sasldb2`, читаемой самим smtpd. Без dovecot, без saslauthd, без отдельного демона.**

Обоснование: dovecot — это полноценный IMAP-сервер (40+ МБ и своя поверхность атаки) ради одной учётной записи, которой не нужен почтовый ящик. `saslauthd` — лишний процесс без выигрыша. Плагин `auxprop`/`sasldb` работает внутри процесса smtpd: ноль памяти, ноль демонов.

```
# main.cf
smtpd_sasl_type = cyrus
smtpd_sasl_path = smtpd
smtpd_sasl_local_domain = $mydomain
smtpd_sasl_security_options = noanonymous
smtpd_tls_auth_only = yes
```
```
# /etc/postfix/sasl/smtpd.conf
pwcheck_method: auxprop
auxprop_plugin: sasldb
mech_list: PLAIN LOGIN
```

`PLAIN`/`LOGIN` — потому что Gmail «Отправлять как» умеет именно их, а `smtpd_tls_auth_only=yes` не даёт им прозвучать до TLS.

**Где хранить пароль. Решение: не хранить файл `sasldb2` как артефакт вообще.** Пароль лежит одной строкой в `.env.production` (файл уже на сервере, уже 600, уже копируется отдельным шагом deploy.sh), а entrypoint контейнера при каждом старте создаёт базу заново во временной файловой системе:

```
SUBMISSION_USER=support
SUBMISSION_PASSWORD=<32+ случайных символа из gen-secrets>
```
```sh
# entrypoint, до запуска postfix
echo "$SUBMISSION_PASSWORD" | saslpasswd2 -p -c -u "$MAIL_DOMAIN" -f /run/sasldb2 "$SUBMISSION_USER"
chown postfix:postfix /run/sasldb2 && chmod 600 /run/sasldb2
```

Почему так: `sasldb2` — двоичный файл, из которого пароль **восстанавливается** (это не хранилище хешей). Заводить второй секретный артефакт рядом с DKIM-ключом, следить за его правами, копированием и бэкапом — накладные расходы без выигрыша: секретность всё равно определяется `.env.production`. `/run` — tmpfs, на диск база не попадает никогда. Смена пароля = правка одной строки и перезапуск контейнера.

Честный минус: пароль в открытом виде в `.env.production`. Он там и так соседствует с паролями Postgres, Redis и MinIO — модель угроз не меняется.

**Ограничение прав учётки:**
```
smtpd_sender_login_maps = hash:/etc/postfix/sender_login
# support@pxcheats.com    support@pxcheats.com
```
плюс `reject_sender_login_mismatch` в цепочке 587. Украденный пароль support@ не даст отправлять от `noreply@` с нашей подписью.

**Сертификат: берём существующий Let's Encrypt, но его придётся расширить.**

Сейчас `entrypoint` сервиса `certbot` в `docker-compose.prod.yml` выпускает сертификат на `-d $CERTBOT_DOMAIN -d s3.$CERTBOT_DOMAIN`, то есть **`mail.pxcheats.com` в нём нет**. Gmail при настройке «Отправлять как» подключается к указанному хосту и проверяет имя в сертификате — с текущим набором проверка не пройдёт.

Решение: дописать `-d mail.$${CERTBOT_DOMAIN}` в ту же строку. Certbot увидит изменившийся набор имён и перевыпустит, несмотря на `--keep-until-expiring`. **Отступ в свёрнутом блоке `>` править предельно аккуратно** — в файле уже есть большой комментарий о том, как неровный отступ однажды превратил `--non-interactive` в отдельную команду.

Монтируем `./docker/nginx/certs` в `postfix-mx` только на чтение.

**Ловушка прав на ключ, которую надо решить в entrypoint.** certbot кладёт `privkey.pem` как root с режимом 600. nginx читает его мастер-процессом от root и потому не замечает проблемы. У postfix TLS-ключ читает **дочерний процесс smtpd от пользователя postfix**, и он получит «Permission denied» — соединение будет рваться на STARTTLS, а в журнале окажется невнятное. Поэтому entrypoint копирует пару в `/etc/postfix/certs/`, ставит владельца `postfix` и режим 400, и уже оттуда её читает конфиг.

**Продление.** Строка cron из deploy.sh (`/etc/cron.d/lp-certbot`) после certbot перезагружает nginx. К ней добавляется `docker compose ... exec -T postfix-mx sh -c 'cp ... && postfix reload'` — чтобы обновлённый ключ попал в контейнер и перечитался.

**Если сертификата ещё нет** (первый деплой, домен не разошёлся) — entrypoint обязан поднять postfix **без TLS на 587**, а не падать в цикл перезапуска. Это ровно та логика, что уже реализована в `docker/nginx/entrypoint.d/25-tls-optional.envsh`; повторить её принцип.

**master.cf, служба submission:**

```
submission inet n - n - - smtpd
  -o syslog_name=postfix/submission
  -o smtpd_tls_security_level=encrypt        # TLS обязателен, не «по возможности»
  -o smtpd_sasl_auth_enable=yes
  -o smtpd_tls_auth_only=yes
  -o smtpd_client_restrictions=permit_sasl_authenticated,reject
  -o smtpd_relay_restrictions=permit_sasl_authenticated,reject
  -o smtpd_recipient_restrictions=permit_sasl_authenticated,reject
  -o smtpd_sender_restrictions=reject_sender_login_mismatch,permit_sasl_authenticated,reject
  -o smtpd_milters=inet:opendkim:8891        # подписываем ТОЛЬКО здесь и в postfix-out
  -o milter_default_action=tempfail          # opendkim умер → письмо ждёт, а не уходит без подписи
  -o cleanup_service_name=submission-cleanup
```

`milter_default_action=tempfail`, а не `accept`, — сознательно: неподписанное письмо, ушедшее «успешно», обнаруживается через недели по жалобам на спам; отложенное письмо обнаруживается через минуту.

**Порядок ввода.** Это шаг C, отдельно от приёма. Приоритет ниже: без него вы читаете почту и отвечаете со своего Gmail-адреса — неудобно, но работает. С ним — отвечаете от support@. Но проектировать надо сразу вместе: `master.cf`, разделение ролей контейнеров и SAN сертификата — общие для 25 и 587, переделывать потом дороже, чем предусмотреть сейчас.

Приятный побочный эффект: Gmail при настройке «Отправлять как» шлёт код подтверждения на `support@pxcheats.com` — то есть шаг C автоматически перепроверяет шаг B.

**ufw:** `ufw allow 25/tcp`, `ufw allow 587/tcp` — добавить в deploy.sh на шаге почты, как там уже сделано с портом 9000 для MinIO. Помня оговорку из `server-setup.sh`: ufw для опубликованных docker-портов декоративен, настоящий контроль — наличие или отсутствие `ports:` в compose.

## 6. Ресурсы

**Память в покое.** Postfix — это набор коротких процессов, а не резидент:

| Контейнер | Реально в покое | Лимит |
|---|---|---|
| `postfix-out` (master + qmgr + pickup) | 12–20 МБ | 64m |
| `postfix-mx` (+ postscreen) | 18–28 МБ | 80m |
| `opendkim` | 10–15 МБ | 32m |
| **Итого** | **40–60 МБ** | **176m** |

Сейчас один `lp-postfix` с лимитом 96m. Прирост лимитов +80 МБ, прирост фактического расхода ~+25 МБ.

**Честное замечание про бюджет.** Комментарий в `docker-compose.prod.yml` расписывает раскладку на 1392 МБ из ~1400 свободных, и `postfix: 96m` был добавлен уже поверх неё — то есть сумма лимитов уже около 1490 МБ. Со 176m она станет ~1570 МБ. Это не приговор: лимиты — потолки, а не резервирование, суммарный фактический расход останется в районе 900–1000 МБ, и своп на 2 ГБ из `server-setup.sh` существует ровно для таких пиков. Но держать это в голове стоит, и после запуска один раз посмотреть `docker stats --no-stream` под нагрузкой.

**Что происходит при потоке спама — и что его реально ограничивает.** `mem_limit` тут не защита: он не мешает postfix форкнуть сотню процессов, он просто убивает контейнер, когда они не влезут. Ограничивают форки эти директивы:

```
default_process_limit = 20                   # вместо 100
                                             # postfix форкает по smtpd на соединение, ~4 МБ каждый.
                                             # 100 × 4 МБ = 400 МБ — половина свободной памяти сервера.
                                             # 20 × 4 = 80 МБ, и это верхний потолок.
smtpd_client_connection_count_limit = 4      # одновременных соединений с одного адреса
smtpd_client_connection_rate_limit = 20      # новых соединений с адреса в минуту
smtpd_client_recipient_rate_limit = 20       # получателей с адреса в минуту
anvil_rate_time_unit = 60s
smtpd_timeout = 30s                          # вместо 300s: медленное соединение держит процесс
in_flow_delay = 1s
```

Плюс `postscreen`: он принимает шторм соединений **одним процессом** и отдаёт настоящему smtpd только тех, кто прошёл проверку на преждевременное приветствие. На одном ядре это разница между «в журнале много строк» и «сервер лёг».

**Диск.** Ничего не копится: неизвестные адреса отвергаются на RCPT (в очередь не попадают), известные — сразу пересылаются в Gmail. Очередь непуста только пока Gmail недоступен. Ограничители:

```
maximal_queue_lifetime = 1d      # вместо 5d
bounce_queue_lifetime = 1d
queue_minfree = 104857600        # 100 МБ: не принимать, если места меньше
notify_classes = resource, software   # не заваливать postmaster отчётами об отказах
```

**Отдельно: очередь должна пережить деплой.** Сейчас у `lp-postfix` `/var/spool/postfix` — слой контейнера, и `docker compose up -d --force-recreate` во время выкладки **теряет неотправленные письма**. Дать обоим postfix по именованному тому под спул. Это улучшение и для сегодняшней отправки тоже.

**Журналы.** postfix пишет в stdout (`maillog_file = /dev/stdout`, postfix ≥3.4, через postlogd), docker пишет json-file. При потоке спама ротация ускоряется — поднять `max-size` до 20m у `postfix-mx`; у `postfix-out` текущих 10m×3 достаточно.

**CPU.** Одно ядро. Дороже всего рукопожатие TLS; отказ на RCPT стоит доли миллисекунды. Именно поэтому DNSBL не включаем сразу — сетевой round-trip на каждое соединение здесь дороже, чем локальные проверки postscreen.

Предложенное `reject_non_fqdn_recipient` я поставил, однако **опираться на него не стал**: в разборе адреса у postfix есть ветка «формы, которые мы не умеем» — адрес в квадратных скобках она пропускает как DUNNO. Проверить это здесь, без запущенного postfix, я не могу, а фикс, который может оказаться пустым, хуже отсутствующего.

Детерминированное закрытие — в самой причине: было `local_recipient_maps =`, и это читается как «локальных получателей нет», а у postfix означает ровно обратное — «не проверять, принимать всех». Теперь обе роли получают **существующую и пустую по содержимому** карту `hash:/etc/postfix/local_recipients` (собирается в `entrypoint.sh` для обеих ролей). Не находится никто → 550 на RCPT TO, ни байта очереди, ни одного отлупа. `reject_non_fqdn_recipient` остался вторым слоем.

**1.3 `out`: не было `smtpd_sender_restrictions` — подтвердилось.** Добавил `reject_non_fqdn_sender, check_sender_access inline:{<домен>=OK}, reject`; строка пересобирается под реальный `MAIL_DOMAIN` в entrypoint, там же самопроверка, что postfix понимает `inline:{}`.

**Частично отверг** сопутствующее утверждение: opendkim подписал бы **не всё**. В `opendkim.conf` простая форма `Domain/Selector/KeyFile`, поэтому письмо от чужого домена подписи `d=pxcheats.com` не получило бы. Релей изнутри при этом был настоящий — его и закрыл.

## 2. Поломка отправки — закрыто

**2.1 `tempfail` + пять попыток за 25 секунд = письмо исчезает навсегда.** Подтвердилось полностью (`notification.processor.ts`: TICK 5 с, без пауз, `FAILED` терминален, возврата в `PENDING` нет нигде).
Чинил не `tempfail` (он правильный), а то, что делало его смертельным — `apps/api/src/modules/notifications/notification.processor.ts`:
- лестница пауз `RETRY_BACKOFF_MS` = 0, 1 мин, 5, 15, 30 мин, 1, 2, 4 ч → восемь попыток примерно за восемь часов;
- `failedAt` теперь пишется при **каждой** неудаче и служит отметкой «когда пробовали» (миграцию ради `nextAttemptAt` не заводил — поле уже есть, смысл для строк `FAILED` не изменился);
- постоянный отказ `5xx` уводит в `FAILED` сразу, не тратя восемь попыток на «такого ящика нет».

**2.2 У отправителя не было тома под очередь.** Подтвердилось, и обоснование «повторятся из notifications» неверно: `SENT` ставится в момент ответа `250`. Добавил том `postfix_out_spool:/var/spool/postfix`.

**2.3 `condition: service_healthy` на однострочнике `/dev/tcp`.** Обе роли переведены на `service_started`. При `tempfail` «не стартовать вовсе» строго хуже, чем «стартовать и подождать подписанта»; сам healthcheck оставил (аргумент про разброс апплетов busybox верный), но отнял у него право не пускать почту.

**2.4 `deploy.sh` объявлял «Готово» при мёртвой почте.** Провал `mail-check.sh` теперь ставит флаг, печатает красный блок **в самом конце** и возвращает код 1. Платформа при этом не откатывается.

**2.5 `verify()` ничего не доказывает — согласен, чинить нечем.** Убрал ложную строку в журнале: вместо «SMTP-соединение проверено» теперь «SMTP отвечает на EHLO — это ещё не проверка отправки», с разбором почему.

**2.6 HELO не с чем сверить.** В дереве не чинится: свидетельство живёт только в работающем контейнере. Вынес в шаг 0 плана — снять **до** первого `up -d`.

## 3. Спам и нагрузка

**3.1 Обратное рассеивание при пересылке — подтвердилось, закрыл переписыванием конверта.** `sender_canonical_classes = envelope_sender` (только конверт!) + `sender_canonical_maps = regexp:/etc/postfix/sender_canonical`, шаблон `docker/mail/conf/sender_canonical.template`, адрес `forward@` добавлен в `virtual.template`. Отлуп от Gmail возвращается нам, а не подделанному отправителю. Исходная подпись DKIM не страдает: конверт в подпись не входит, заголовки не трогаются.
**Осознанная цена:** пересланное письмо теперь проходит SPF как наше, и пересланный себе же спам Google засчитывает нашему домену. Считаю это меньшим злом, чем Backscatterer.org/UCEPROTECT, из которых выходят месяцами вместе с отправкой платформы. Откат — закомментировать две строки.
Отдельный демон `postsrsd` **отверг**: обратный разбор адреса при пересылке в один ящик не нужен никому.

**3.2 Очередь на общем разделе.** `queue_minfree = 1073741824` (было умолчание ~15 МБ, то есть «защита» срабатывает уже после того, как Postgres перестал писать WAL). Плюс в `mail-check.sh` появились счётчик писем в очереди (≥100 — это `[БЕДА]`, а не `[?]`) и проверка свободного места на `/var/lib/docker`.

**3.3 Троттлинг Gmail.** `smtp_destination_concurrency_limit = 2` (было умолчание 20).

**3.4 `mem_limit` против `default_process_limit`.** У mx: лимит процессов 20 → 8, память 96m → 128m.

**3.5 `message_size_limit = 10 МБ` при 25 у Gmail — оставил как есть.** Это осознанный компромисс автора, а не дефект; менять его без разговора о том, что мы готовы принимать, неправильно.

### Шаг 6. Убедиться, что открытого релея нет — ТОЛЬКО С ЧУЖОЙ МАШИНЫ

С сервера это бессмысленно: соединение придёт с адреса, который может оказаться «своим».

```
# 1. Классический релей
swaks --server mail.pxcheats.com --from probe@example.org --to проверка@gmail.com
#    ждём 554 5.7.1 Relay access denied на RCPT

# 2. Пустой отправитель
swaks --server mail.pxcheats.com --from "" --to проверка@gmail.com          # тот же 554

# 3. Обходы адресации
swaks --server mail.pxcheats.com --to 'проверка%gmail.com@pxcheats.com'
swaks --server mail.pxcheats.com --to 'проверка@gmail.com@pxcheats.com'
swaks --server mail.pxcheats.com --to '@pxcheats.com:проверка@gmail.com'
swaks --server mail.pxcheats.com --to 'gmail.com!проверка@pxcheats.com'     # отказ на каждый

# 4. Несуществующий адрес
swaks --server mail.pxcheats.com --to нет-такого@pxcheats.com               # 550 НА RCPT, не отлупом

# 5. НОВОЕ — адрес-литерал
swaks --server mail.pxcheats.com --from probe@example.org --to 'foo@[127.0.0.1]'
#    ждём 5xx на RCPT. 250 здесь = дыра открыта заново

# 6. НОВОЕ — DSN не объявляется
printf 'EHLO probe.example.org\r\nQUIT\r\n' | nc mail.pxcheats.com 25
#    в ответе НЕ ДОЛЖНО быть строки 250-DSN
```

Проверки 5 и 6 — те самые, которых не было: получатель в них **наш**, релея нет, а письмо постороннему всё равно уходило.

**Контроль результата, а не только кодов ответа:** возьмите ящик, который **не** является `MAIL_FORWARD_TO`, подставьте его в `--from` проверок 1, 5 и 6 и убедитесь, что через 10-15 минут туда не пришло ничего, включая папку «Спам». Отсутствие письма — это и есть доказательство.

**Проверка пересылки и обратного адреса:** с домена, которым вы владеете, напишите на `support@pxcheats.com`. В Gmail владельца письмо должно прийти с `Return-Path: forward@pxcheats.com`, с уцелевшей исходной подписью DKIM отправителя и неизменённым `From:`.

### Шаг 7. Через сутки

```
docker exec lp-postfix postqueue -p; docker exec lp-postfix-mx postqueue -p
bash scripts/mail-check.sh
```
Плюс разовая проверка `77.221.154.85` в списках (mxtoolbox blacklist / Backscatterer). Растущая очередь у отправителя — почти всегда недоступный opendkim; у приёмника — придержанная Google пересылка.

### Откат по частям

- Переписывание конверта: закомментировать `sender_canonical_classes` и `sender_canonical_maps` в `conf/mx/main.cf` → пересоздать `postfix-mx`.
- Ограничение отправителя: убрать `smtpd_sender_restrictions` из `conf/out/main.cf` и строку `postconf -e "smtpd_sender_restrictions=..."` из `entrypoint.sh`.
- `milter_default_action = tempfail` возвращать в `accept` **только вместе** с откатом лестницы пауз в обработчике: по отдельности это опять «письма исчезают за 25 секунд».
