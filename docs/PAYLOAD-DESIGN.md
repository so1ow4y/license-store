## Сводка

Эндпоинт добавляется четвёртым методом LauncherController и потому автоматически получает SignatureGuard с класса и глобальные JwtAuthGuard/PermissionsGuard (проверено: launcher.controller.ts:24, auth.module.ts:52-58). Архитектура: payload — ОТДЕЛЬНАЯ сущность PayloadBuild в ОТДЕЛЬНОМ приватном бакете S3_BUCKET_PAYLOADS, потому что единственный слот артефакта у ProductVersion (fileId) занят дистрибутивом §8, а publish() требует fileId+sha256 (versions.service.ts:329-334) — на общей строке новый payload нельзя выкатить, не выпустив новый exe. Байты читаются новым StorageService.getObjectBuffer, кладутся в LRU В ПАМЯТИ ПРОЦЕССА (не в Redis: RDB/AOF пишут на диск, allkeys-lru выселяет непредсказуемо) с single-flight, чтобы 500 одновременных запусков дали 1 GET, а не 500. Проверка лицензии и HWID переиспользуется через вынесенный LauncherService.resolveForLauncher(); payload работает в режиме verify-only и НИКОГДА не привязывает устройство и не запускает отсчёт срока лицензии. Ключ AES-256 выводится HKDF-SHA256 из клиентского sessionKey с СОЛЬЮ, РАВНОЙ СЕРВЕРНОМУ IV, — это конструктивно исключает повтор пары (ключ, IV) даже у сломанного клиента и не требует новых заголовков. AAD покрывает все заголовки X-Payload-* кроме Nonce/Tag, поэтому «двойная проверка целостности» §7.2.3 перестаёт быть декорацией. Каждая попытка, включая отказы, пишется строкой в payload_issues — сегодня в базе после выдачи не остаётся ничего, и антифрод по главному по ценности эндпоинту работать не на чем. Шифрование — асинхронное (webcrypto.subtle), чтобы 3 МБ не блокировали event loop и не рушили бюджет 150 мс у проверки лицензии. Отдельный location в nginx с proxy_buffering off — сейчас многомегабайтный ответ уезжает во временный ФАЙЛ nginx, то есть payload физически оказывается на диске сервера. На клиенте главное: кап 2 МиБ зашит литералом в Send() (Http.cpp:389) и переопределить его нечем — без правки транспорта эндпоинт не работает вообще.

### 2. Куда в модели данных ложится payload: поле у ProductVersion или отдельная сущность

**Выбор.** Отдельная аддитивная модель PayloadBuild. ProductVersion не трогается ни одним полем.

model PayloadBuild {
  id String @id @db.Uuid
  productId String @map("product_id") @db.Uuid
  product Product @relation(fields:[productId], references:[id], onDelete: Cascade)
  version String @db.VarChar(32)
  versionCode Int @map("version_code")
  channel ReleaseChannel @default(STABLE)
  fileId String? @map("file_id") @db.Uuid
  file File? @relation("PayloadFile", fields:[fileId], references:[id], onDelete: Restrict)
  /// Неизменяемый снимок по образцу ProductVersion.sha256: эталон должен пережить перезалив объекта.
  /// Это хеш ОТКРЫТОГО содержимого — ровно то, что уходит в X-Payload-Sha256.
  sha256 String? @db.Char(64)
  size BigInt? @map("size_bytes")
  minLauncherVersionCode Int? @map("min_launcher_version_code")
  isPublished Boolean @default(false) @map("is_published")
  publishedAt DateTime? @map("published_at") @db.Timestamptz(3)
  createdById String @map("created_by_id") @db.Uuid
  createdAt DateTime @default(now()) @map("created_at") @db.Timestamptz(3)
  updatedAt DateTime @updatedAt @map("updated_at") @db.Timestamptz(3)
  @@unique([productId, version])
  @@index([productId, channel, isPublished, versionCode(sort: Desc)])
  @@map("payload_builds")
}

В File добавляется обратная связь payloadBuilds PayloadBuild[] @relation("PayloadFile"), в Product — payloadBuilds PayloadBuild[].

**Почему.** Проверено лично: слот артефакта у версии ровно один (schema.prisma:578-584), и он занят дистрибутивом §8 — buildReleaseKey кладёт объект под releases/<slug>/<version> (storage.service.ts:198-201), publish() отказывает без fileId+sha256 (versions.service.ts:329-334), checkUpdate() возвращает именно этот sha256/size (versions.service.ts:435-442). Решающий довод против варианта «добавить ProductVersion.payloadFileId»: publish() ТРЕБУЕТ fileId релиза, поэтому строка версии с одним только payload'ом опубликована быть не может — новый payload нельзя выпустить, не выпустив новый exe и не заставив всех переустановиться. Отдельная таблица разводит две независимо релизящиеся вещи в МОДЕЛИ, а не в комментарии, и делает реализуемыми PAYLOAD_NOT_READY (§7.3) и UPDATE_REQUIRED (порог едет вместе с payload'ом в одной строке).

**Отвергнуто.** (а) Переиспользовать ProductVersion.fileId — склеивает §7 и §8 в одном объекте, после чего тот же файл становится кандидатом на presigned/CDN, что §7.1 прямо запрещает. (б) ProductVersion.payloadFileId — миграция дешевле, но не решает связанность осей и упирается в publish(). (в) ProductVersionFile — у него обязателен path («путь относительно корня установки», schema.prisma:609), а payload на диске не появляется никогда: запись была бы ложью в ключевой колонке.

### 3. Нужен ли отдельный бакет под payload

**Выбор.** Да: S3_BUCKET_PAYLOADS (значение по умолчанию 'payloads'). Добавляется в env.schema.ts рядом с S3_BUCKET_RELEASES, в .env.example, в minio-init (mc mb --ignore-existing lp/payloads — БЕЗ mc anonymous set). В StorageService появляется readonly bucketPayloads и жёсткая отбивка в createDownloadUrl: if (bucket === this.bucketPayloads) throw new InternalServerErrorException('presigned-ссылки на payload запрещены (ТЗ §7.1)'). Ключ строится новым buildPayloadKey(slug, version, filename) → payloads/<slug>/<version>/<safe>. File.isPublic для payload принудительно false.

**Почему.** Запрет на presigned сейчас живёт в КОММЕНТАРИИ (storage.service.ts:120-126), а createDownloadUrl принимает произвольный бакет. Пока объекты лежат в одном бакете с релизами, ничто не мешает будущему вызывающему выдать ссылку на payload — и это обнаружится утечкой, а не ревью. Отдельный бакет превращает пожелание в проверяемый инвариант ценой одной переменной окружения и одной строки в minio-init. Дополнительно: releases по §8 предполагается фронтить CDN, и смешивать в одном бакете объекты с противоположной политикой доступа нельзя.

**Отвергнуто.** Префикс payloads/ внутри существующего releases (вариант 1): дешевле, но защищает ровно настолько, насколько никто не вызовет createDownloadUrl с этим ключом — проверено грепом, что у createDownloadUrl сегодня НОЛЬ вызывающих, то есть это свойство кода, а не модели, и первый же новый вызывающий его снимет.

### 4. Как выводится эфемерный ключ AES-256 из клиентского sessionKey (точная спецификация)

**Выбор.** HKDF-SHA256 (RFC 5869, Extract+Expand), выход 32 байта:
  IKM  = hex_decode(body.sessionKey)         // ровно 32 байта
  salt = IV, 12 байт, сгенерированные СЕРВЕРОМ через randomBytes(12) и отданные в X-Payload-Nonce
  info = ASCII "lp/payload/v1"               // 13 байт, фиксированная константа, без переменных частей
  L    = 32
Развёрнуто: PRK = HMAC-SHA256(key=IV(12), msg=sessionKeyBytes(32)); OKM = HMAC-SHA256(key=PRK, msg=info || 0x01), берутся все 32 байта — при L = длине хеша Expand это РОВНО одна итерация.
Сервер: await promisify(crypto.hkdf)('sha256', ikm, iv, INFO, 32) → ArrayBuffer, обёртка Buffer.from обязательна. Node в проекте >=22 (проверено: apps/api/package.json engines), hkdf доступен.
Клиент: два вызова уже существующего HmacSha256 (Sha.cpp:45), ноль циклов.

**Почему.** Соль = IV даёт свойство, которого не даёт ни одна альтернатива: IV генерирует СЕРВЕР, поэтому клиент, нарушивший §7.2.1 и переиспользовавший sessionKey, физически не может вызвать повтор пары (ключ, IV). Повтор (ключ, IV) в GCM — не «ослабление», а полная потеря стойкости вплоть до раскрытия ключа аутентификации; ровно это уже записано в комментарии crypto.service.ts:76-77. Соль при этом уже на проводе — новый заголовок не нужен, а в §7 свободных заголовков нет (X-Payload-Nonce занят под IV). HKDF, а не голый HMAC — ради ОПУБЛИКОВАННЫХ векторов RFC 5869: расхождение KDF между Node и C++ проявляется исключительно как провал GCM-тега, состояние без всякой диагностики, и с RFC-векторами отладка сводится к прогону test_hkdf.cpp, а не к бинарному поиску по двум реализациям. L=32 выбрано в том числе чтобы Expand был одной итерацией — минимум мест разойтись.

**Отвергнуто.** (а) salt = X-Signature (вариант 2): привязывает ключ к запросу, но требует протащить подпись из Http.cpp в Api-слой (проверено: SignedRequest sig — локальная переменная внутри Send, HttpResponse поля под неё не имеет, Http.h:48-65), и порождает реальный баг-генератор — при ретрае подпись пересчитывается (Http.cpp:337), и надо взять именно ту, что дала ответ. Выигрыша при этом нет: привязка ответа к запросу УЖЕ обеспечена свежим sessionKey — записанный ответ на чужой запрос не расшифруется, потому что ключ выводится из sessionKey, которого у нападающего нет. Всё остальное связывание дешевле сделать в AAD. (б) Голый SHA-256(sessionKey) — нет публичных векторов и нет разделения доменов. (в) ECDH P-256 (план WORK_LOG.md:83) — §7.1 требует «ключ, производный от sessionKey», обмена публичными ключами в контракте нет, а против владельца машины ECDH всё равно не спасает. (г) productSlug в info (вариант 3) — то же связывание дешевле и виднее делается в AAD; каждый переменный байт в info это лишний способ разойтись.

### 5. Что идёт в AAD у AES-256-GCM

**Выбор.** AAD = байты ASCII-строки, поля через ОДИН 0x0A, без завершающего перевода строки — тот же разделитель, что в каноне подписи (SignatureService.buildPayload, signature.service.ts:74):

  lp/payload/v1 \n <productSlug> \n <X-Payload-Sha256> \n <X-Payload-Size> \n <X-Payload-Version>

Канонизация значений фиксируется буквально: sha256 — 64 hex НИЖНЕГО регистра; size — десятичное без ведущих нулей и без пробелов; version — строка вида 1.2.0 как в PayloadBuild.version; productSlug — байт в байт то, что клиент прислал в теле (сервер нашёл продукт через findUnique по slug, то есть точное совпадение гарантировано, иначе был бы 404).
ИНВАРИАНТ КОНТРАКТА, который надо записать одной фразой: КАЖДЫЙ заголовок X-Payload-* покрыт тегом, кроме Nonce и Tag — их GCM связывает сам.
Клиент ОБЯЗАН обрезать значение заголовка с ОБЕИХ сторон перед сборкой AAD (сейчас Http.cpp:241-243 режет только слева — см. правку клиента).

**Почему.** §7 про AAD молчит, но вопрос содержательный. Без AAD заголовки X-Payload-Sha256 и X-Payload-Size лежат ВНЕ AEAD и не аутентифицированы ничем, кроме TLS, — а ТЗ §14 прямо признаёт сценарий с подставленным корневым сертификатом рабочим. Активный посредник переворачивает дайджест, не умея расшифровать тело: клиент успешно расшифрует, провалит сверку sha256, по §7.2.3 остановится, покажет «повреждённые данные» и отправит отчёт — то есть получится отказ в обслуживании, выглядящий как НАША ошибка, с тикетом в поддержку на каждого пострадавшего. С AAD это чистый провал тега с правильным диагнозом. Разделитель \n взят потому, что на C++ каноническую строку через \n уже собирает оттестированный Signature.cpp — новой поверхности для расхождения не появляется. X-Payload-Version включена, чтобы отчёт о сбое по §9 ссылался на аутентичный номер сборки.

**Отвергнуто.** (а) Пустой AAD — заголовки целостности остаются неаутентифицированными, «двойная проверка» §7.2.3 превращается в декорацию. (б) X-Signature в AAD (вариант 2) — та же плата, что и в KDF: протаскивание подписи через транспорт и ретрай-ловушка, при нулевом дополнительном выигрыше. (в) licenseId / deviceId / requestId / timestamp в AAD — клиент их не знает и AAD не соберёт; жёсткое правило: в AAD входит ТОЛЬКО то, что клиент способен восстановить из отправленного и полученного. (г) Схема table.column:rowId из CryptoService.buildAad (crypto.service.ts:206-208) — она про привязку к строке БД, здесь нужна привязка к ОТВЕТУ. (д) Разделитель '|' (вариант 1) — вводит второе соглашение о канонических строках рядом с уже существующим \n.

### 6. Формат и валидация sessionKey; что делать с повторным sessionKey

**Выбор.** DTO: @Matches(/^[0-9a-f]{64}$/) — ровно 64 символа hex НИЖНЕГО регистра. Нарушение → 400 (глобальный ValidationPipe, whitelist + forbidNonWhitelisted уже включены, main.ts:147-162), повтор клиенту запрещён.
Дополнительно: SET NX EX <window> по ключу payload:sk:<sha256(sessionKey)>; попадание → 400 SESSION_KEY_REUSED + AntiFraudEvent severity CRITICAL.
Полный DTO (src/modules/launcher/dto/payload.dto.ts) — ровно три поля по §7, clientVersion в теле НЕТ:
  productSlug: @IsString @Matches(/^[a-z0-9][a-z0-9._-]{0,63}$/)
  hwid:        @IsString @IsNotEmpty @MaxLength(128)
  sessionKey:  @IsString @Matches(/^[0-9a-f]{64}$/)

**Почему.** Верхний регистр не принимаем, потому что расхождение регистра — ровно тот класс расхождений, который в этой системе уже стоил транспортного слоя (docs/SIGNATURE-VECTORS.md отстал от §3.5 ревизии 2). Одно представление — одно правило на C++. Проверка повтора sessionKey ловит не противника (он тривиально рандомизирует), а НАШ собственный отказ: если в сборке загрузчика sessionKey окажется статическим (забыли вызвать GenRandom, закешировали, отладочная константа уехала в релиз), один перехваченный ключ расшифровывает все будущие ответы этой сборки — катастрофа, которую иначе никто не заметит, потому что всё продолжает работать. Стоимость обнаружения — один SET NX. Регулярка на productSlug добавлена в том числе для того, чтобы символы-разделители AAD (\n) физически не могли попасть в поле.

**Отвергнуто.** Принимать любой регистр и нормализовать на сервере — технически безразлично (KDF работает с декодированными байтами), но два допустимых представления в контракте однажды разойдутся в векторах и тестах. Не проверять повтор — цена нулевая, а пропущенный статический ключ необнаружим.

### 7. Как переиспользуется проверка лицензии и HWID из license/check

**Выбор.** Из LauncherService.check() выносится метод (строки 69-116 переезжают без изменения логики):

  async resolveForLauncher(params: {
    userId: string; productSlug: string; diskId: string;
    clientVersion?: string; ip?: string; country?: string;
    allowFirstBind: boolean; touchDevice: boolean;
  }): Promise<{ product: { id: string; name: string }; license: LicenseWithPlanAndDevice; bind: HwidCheckResult }>

Внутри ровно та же последовательность: product.findUnique по slug → 404 PRODUCT_NOT_FOUND; license.findFirst с тем же where и тем же orderBy → 404 LICENSE_NOT_FOUND; assertUsable(license); при allowFirstBind=false и license.currentDeviceId === null → 403 LICENSE_NOT_BOUND ДО обращения к HwidService; hwid.bindOrVerify(license.id, diskId, ctx, { allowFirstBind, touch: touchDevice }); маппинг bind.reason в 403 DEVICE_BLOCKED / HWID_MISMATCH / LICENSE_NOT_BOUND.
check() зовёт с { allowFirstBind: true, touchDevice: true } — поведение сохраняется побайтово. payload() зовёт с { allowFirstBind: false, touchDevice: false }.

**Почему.** Дублировать цепочку нельзя по содержательной причине, а не из эстетики: where и orderBy живут инлайном, и при первой же правке два эндпоинта выберут РАЗНЫЕ строки лицензии — пользователь получит ACTIVE от license/check и отказ от payload в одну секунду, и диагностировать это будет некому. Перенос без изменения логики сохраняет порядок отказов, коды и запросы к БД, поэтому scripts/smoke-launcher.ps1 остаётся зелёным. Проверка currentDeviceId === null делается на УЖЕ прочитанной строке (check() и так делает include: { currentDevice: true }, launcher.service.ts:87) — ноль дополнительных запросов, и типичный отказ не доходит до второго чтения лицензии внутри bindOrVerify.

**Отвергнуто.** (а) Звать check() и выбрасывать результат — тянет markOnline, touchLastCheck и updateInfo (ещё 1-2 запроса в product_versions), которых payload'у не нужно, и привязывает устройство. (б) Копия цепочки внутри payload() — ровно то расхождение, которого мы избегаем. (в) Делать assertUsable публичным и собирать цепочку в контроллере — логика уедет в слой транспорта.

### 8. Должен ли payload вызывать bindOrVerify «как есть», то есть привязывать устройство и активировать лицензию

**Выбор.** НЕТ. payload работает строго в режиме verify-only. В HwidService.bindOrVerify добавляется НЕОБЯЗАТЕЛЬНЫЙ последний параметр opts?: { allowFirstBind?: boolean; touch?: boolean } со значениями по умолчанию true/true — существующий вызывающий не меняется ни на символ. При allowFirstBind=false и !license.currentDeviceId метод возвращает { ok:false, reason:'NOT_BOUND' } и НЕ создаёт ничего: ни device, ни записи hwid_history, ни вызова licenses.activate. При touch=false пропускается await prisma.device.update ветки совпадения.
В HwidCheckResult.reason добавляется значение 'NOT_BOUND'. Наружу: 403 LICENSE_NOT_BOUND, message «Сначала выполните проверку лицензии».
Порядок фиксируется в контракте: сначала POST /launcher/license/check (привязывает, активирует, запускает срок), затем POST /launcher/payload (только сверяет).

**Почему.** Проверено дословно: bindOrVerify при currentDeviceId == null не проверяет, а СОЗДАЁТ — заводит device, пишет FIRST_BIND и вызывает licenses.activate с комментарием «Срок начинается здесь и только здесь» (hwid.service.ts:79-132). Запрос на выдачу ДАННЫХ, который стартует оплаченный срок лицензии, — побочный эффект в чтении и одновременно рычаг: противник управляет порядком собственных запросов и может сжечь чужой срок или активировать лицензию, которую человек ещё не собирался начинать. Отдельно: §7.1 требует, чтобы лицензия и HWID ПРОВЕРЯЛИСЬ на каждый запрос — проверялись, а не привязывались; иначе payload проверяет привязку, которую сам секунду назад и создал. Параметр в HwidService, а не только предпроверка на прочитанной строке, нужен чтобы гарантия была структурной: между двумя чтениями лицензии возможен конкурентный сброс привязки, и без параметра bindOrVerify всё равно ушёл бы в ветку первой привязки. touch=false убирает второй UPDATE той же строки devices за один запуск (проверено: hwid.service.ts:146 делает await device.update на КАЖДОЙ успешной сверке, вопреки комментарию рядом «без ожидания»).
Отдельный код LICENSE_NOT_BOUND, а не HWID_MISMATCH: на клиенте RequiresReLogin() (Api.h:150-151) на HWID_MISMATCH стирает сохранённые секреты и предлагает сброс привязки — вредный совет для ситуации «просто ещё не вызвали license/check».

**Отвергнуто.** (а) Вызывать как есть (вариант 1) — payload запускает отсчёт срока лицензии; в боевой последовательности этого не случится, но контрактом порядок не закреплён и модифицированный клиент активирует лицензию через чёрный ход. (б) Требовать успешного license/check через отметку в Redis — ложная гарантия (противник сделает check один раз) плюс состояние на горячем пути, ломающееся при рестарте Redis. (в) Схлопывать NOT_BOUND в HWID_MISMATCH (вариант 3) — заставит пользователя жечь лимит сбросов привязки (по умолчанию 3 на лицензию), гоняясь за проблемой, которую сброс не решает.

### 9. Чинить ли попутно выбор лицензии: REVOKED вне фильтра и сортировку PENDING перед ACTIVE

**Выбор.** РАЗДЕЛИТЬ. REVOKED добавляется в where-фильтр findFirst — чинится сейчас, вместе с payload. Сортировка orderBy [{status:'asc'},{expiresAt:'desc'}] НЕ трогается — выносится владельцу как бизнес-вопрос.

**Почему.** REVOKED: проверено, что ветка assertUsable для REVOKED (launcher.service.ts:212-217) недостижима, потому что REVOKED не входит в where (строка 82), и отозванная за чарджбек лицензия отдаёт 404 LICENSE_NOT_FOUND вместо 403 LICENSE_REVOKED из приложения Б. Разница не косметическая: на клиенте RequiresReLogin() на LICENSE_REVOKED стирает сохранённые секреты, а на 404 не делает ничего. Регрессии нет: enum сортируется по порядку объявления (schema.prisma:65-71), REVOKED объявлен последним, поэтому при наличии живой лицензии она по-прежнему выигрывает.
Сортировка: правка (взять findMany take 5 и предпочесть лицензию, привязанную к этому устройству) МЕНЯЕТ поведение license/check в сценарии «купил продление» и потому является бизнес-решением. Расхождения между эндпоинтами она при этом не устраняет — его и нет: оба ходят через один resolveForLauncher и выберут одну и ту же строку по определению.

**Отвергнуто.** Чинить сортировку заодно (вариант 2) — меняет поведение самого горячего проверенного пути ради проблемы, которой в связке двух эндпоинтов не возникает. Не чинить REVOKED (вариант 1) — оставляет недостижимым код ошибки, на который клиент реагирует стиранием секретов.

### 10. Откуда берётся X-Payload-Sha256: из БД или пересчитывается по прочитанным байтам

**Выбор.** ОБА, в разных ролях. В заголовок уходит PayloadBuild.sha256 — неизменяемый снимок, посчитанный сервером на шаге confirm-upload. Пересчёт по прочитанным байтам делается ОДИН РАЗ ПРИ ЗАПОЛНЕНИИ КЭША (не на каждый запрос) и сверяется с PayloadBuild.sha256: расхождение → 503 PAYLOAD_CORRUPT, запись в лог уровня ERROR, тело НЕ отдаётся, запись кэша не создаётся.

**Почему.** Если сервер хеширует то, что сам же прочитал, и это же отдаёт заголовком, клиентская сверка §7.2.3 не может провалиться никогда и превращается в декорацию — а §11.3 отдельно запрещает игнорировать несовпадение SHA-256, то есть считает эту проверку рабочей. Эталон обязан приходить из БД. При этом отдавать клиенту подменённые байты и рассчитывать, что он их отвергнет, — плохой размен: пользователь увидит «повреждённые данные» и пойдёт в поддержку. Серверная сверка при заполнении кэша ловит подмену объекта в хранилище раньше и бесплатно (хеш считается тем же проходом, что и чтение, данные уже в кэше процессора). Это не теоретический сценарий: проверено, что confirmUpload релиза не проверяет isPublished и принимает произвольный objectKey из тела (versions.service.ts:193-214) — тот же класс дефекта в новом коде мы не повторяем, но защита на выдаче нужна в любом случае.
503, а не 409: PAYLOAD_NOT_READY по §7.3 означает «версия ещё не опубликована», и клиент будет ждать вечно; 503 по §2.3 повторяем с экспоненциальной задержкой и алертится как наша авария.

**Отвергнуто.** Только пересчёт (самоподтверждающаяся проверка). Только БД без сверки (вариант 1) — подменённый объект уезжает клиенту и выглядит как наша ошибка у каждого пользователя. Отдельная колонка payload_sha256 у ProductVersion — дубль File.sha256, который однажды разъедется.

### 11. Как читаются байты из хранилища — новый метод StorageService

**Выбор.** Добавляется приватный помощник и один публичный метод; computeSha256 в v1 НЕ переписывается:

  private async readObject(bucket: string, objectKey: string, maxBytes: number): Promise<{ body: Buffer; size: number; sha256: string; contentType: string | null }>
  async getObjectBuffer(bucket: string, objectKey: string, opts: { maxBytes: number }): Promise<{ body: Buffer; size: number; sha256: string; contentType: string | null }>

Порядок в readObject: head() → null → NotFoundException; meta.size > maxBytes → бросить ДО скачивания; GetObjectCommand → for await по Readable с накоплением чанков, БЕГУЩИМ счётчиком (оборвать и бросить прямо в процессе чтения, ContentLength от хранилища не доверенный сам по себе) и одновременным createHash('sha256'); финал — Buffer.concat(chunks, total).
Константа MAX_PAYLOAD_PLAINTEXT_BYTES = 8 * 1024 * 1024 (лимит тела ответа из §12), НЕ MAX_HASHABLE_BYTES = 512 МиБ.
getObjectStream НЕ добавляется.

**Почему.** Проверено: наружу StorageService отдаёт только presigned-ссылки, метаданные и готовый дайджест (storage.service.ts:96-201) — байты в computeSha256 проходят через процесс и выбрасываются (строки 178-182). Читать нечем, метод надо добавлять. Лимит проверяется дважды, потому что ContentLength приходит от MinIO. Подсчёт sha256 тем же проходом бесплатен и даёт запись кэша с готовым дайджестом без второго обхода 3 МБ. 8 МиБ, а не 512 МиБ: ошибка публикации (залили дистрибутив вместо payload'а) иначе превращается в отказ обслуживания на шифровании. Константа, а не настройка в БД: значение обязано совпадать с клиентским kMaxPayloadResponseBytes, а настройку из БД клиент не читает — расхождение стало бы бесшумным. getObjectStream не добавляется, потому что стриминг для payload невозможен по контракту (тег в заголовке) — плодить неиспользуемый публичный метод значит повторить судьбу createDownloadUrl, у которого проверено ноль вызывающих.

**Отвергнуто.** Presigned URL — запрещено §7.1 и предупреждением в самом коде. Переписать computeSha256 поверх readObject сразу (вариант 3) — красивее и это правильный следующий шаг, но computeSha256 покрыт scripts/smoke-products.ps1, и рефакторинг проверенного пути в одной правке с новым эндпоинтом делает диф неаудируемым; помечается отдельной задачей. Отдавать base64 в JSON — +33% к трафику и 4-мегабайтная строка в сериализатор Fastify.

### 12. Кэшировать ли байты payload'а между запросами

**Выбор.** ДА — LRU В ПАМЯТИ ПРОЦЕССА, ключ payloadBuildId, значение — ОТКРЫТЫЙ Buffer. Отдельный провайдер src/modules/launcher/payload-cache.service.ts:

  async get(build: PublishedPayloadBuild): Promise<Buffer>
  async invalidate(buildId: string): Promise<void>

Обязателен single-flight: Map хранит не Buffer, а Promise<Entry>, поэтому N одновременных промахов дают РОВНО ОДИН GET в хранилище. Ограничение по СУММАРНЫМ БАЙТАМ (64 МиБ по умолчанию), а не по числу записей. TTL 10 минут как страховка. Инвалидация — канал Redis pub/sub 'payload:invalidate' по образцу уже работающего 'settings:invalidate' (settings.service.ts:24-30, отдельное соединение через client.duplicate()); публикуется на publish/unpublish сборки. Кэшируется ТОЛЬКО открытый текст; шифротекст не кэшируется НИКОГДА.

**Почему.** Ответ уникален на каждый запрос, но БАЙТЫ — нет: вся уникальность живёт в слое AES-GCM (эфемерный ключ + свежий IV), а открытый текст одинаков для всех пользователей одной опубликованной сборки, и сборка неизменяема по определению. В стационарном режиме кэш почти не нужен (payload запрашивается раз на ЗАПУСК: 1000 онлайн × ~3 запуска ≈ 0.03 rps), и здесь вариант 1 прав. Но он считает только стационар: при 500 одновременных запусках (вечерний пик, восстановление после аварии) без single-flight в MinIO уходит 500 параллельных GET одного объекта и одновременно живёт 500 буферов открытого текста — ~300 МБ при 600 КБ и ~1.5 ГБ на потолке 3 МБ. Стоимость страховки — около 40 строк. Ограничение по байтам, а не по числу записей, потому что «LRU на 100 записей» при потолке 3 МБ это 300 МБ RSS, о которых никто не думал. Шифротекст не кэшируется потому, что это немедленно создало бы повтор пары (ключ, IV).

**Отвергнуто.** Не кэшировать вовсе (вариант 1) — верно для стационара и неверно для всплеска, а всплеск и есть режим, в котором сервис падает. Кэш в Redis — три возражения: RDB/AOF кладут самый ценный актив на диск сервера (то, что §7 требует не делать на клиенте), round-trip 600 КБ–3 МБ на каждый промах возвращает убираемую латентность, и allkeys-lru (документировано в redis.service.ts:16-18) делает выселение непредсказуемым.

### 13. Где живёт шифрование ответа и почему существующий CryptoService.encrypt не подходит

**Выбор.** Существующий encrypt не подходит: он работает со строками utf8, использует СЕРВЕРНУЮ связку ключей и заворачивает результат в конверт v<ver>.<iv>.<tag>.<ct> (crypto.service.ts:69-91), тогда как §7 требует эфемерного ключа от клиентского sessionKey, сырых байт в теле и тега ОТДЕЛЬНЫМ заголовком. Добавляется ОДИН новый метод в тот же CryptoService, существующие не трогаются:

  async sealForSession(plaintext: Buffer, sessionKeyHex: string, aad: Buffer): Promise<{ iv: Buffer; tag: Buffer; ciphertext: Buffer }>

Внутри: iv = randomBytes(IV_LENGTH=12); key = HKDF по спецификации выше (await promisify(crypto.hkdf)); шифрование через webcrypto.subtle — subtle.importKey('raw', key, 'AES-GCM', false, ['encrypt']) и subtle.encrypt({ name:'AES-GCM', iv, additionalData: aad, tagLength: 128 }, k, plaintext); subtle отдаёт ciphertext||tag одним буфером, тег отрезается как subarray(len-16) без копирования. Переиспользуются существующие константы IV_LENGTH / TAG_LENGTH.
В docker-compose и README фиксируется UV_THREADPOOL_SIZE=16.

**Почему.** Криптография в проекте живёт в common/crypto — класть AES в LauncherService значило бы завести второй дом. Асинхронный путь (subtle + crypto.hkdf), а не синхронные createCipheriv/hkdfSync: на потолке 3 МБ синхронный cipher.update блокирует event loop на 1–3 мс, и при 500 запусках это до полутора секунд заблокированного цикла — саморазрушение p99 всего API, включая проверку лицензии с бюджетом 150 мс. Проектировать надо под потолок, а не под сегодняшние 600 КБ. UV_THREADPOOL_SIZE обязателен и обязателен к документированию: @node-rs/argon2 при логине уходит на тот же пул из 4 потоков по умолчанию, и без подъёма всплеск запусков будет незаметно деградировать ВХОД В СИСТЕМУ — связь между этими двумя явлениями без метрик по стадиям не находит никто.

**Отвергнуто.** Обобщать существующий encrypt() параметром «ключ снаружи» — это метод, которым зашифрованы hwid_enc, two_factor_secret_enc и signing_secret_enc; цена ошибки несопоставима с выигрышем. Отдельный PayloadCryptoService — новый класс ради пятнадцати строк. Синхронный createCipheriv — оставляется как переключатель на случай, если бенчмарк покажет, что планирование job'а дороже блокировки на реальных 600 КБ.

### 14. Нужен ли контроль допуска по памяти (admission control)

**Выбор.** ДА, по БАЙТАМ, а не по числу запросов. Новый провайдер payload-admission.service.ts:

  async acquire(bytes: number, waitMs = 500): Promise<() => void>   // бросает ServiceUnavailableException при исчерпании

Бюджет PAYLOAD_INFLIGHT_BYTES_MAX = 128 МиБ (настройка limits.payload.inflight_bytes_max). Резервация делается ПОСЛЕ чтения строки PayloadBuild (размер известен из БД, хранилище трогать не надо) и ПЕРЕД чтением/шифрованием. Освобождение — по событию 'close' на reply.raw, а НЕ по возврату из send(). Переполнение → короткое ожидание в очереди ≤500 мс, затем 503 SERVICE_UNAVAILABLE + Retry-After.

**Почему.** Потоковая отдача невозможна не из-за удобства, а из-за контракта: GCM-тег уезжает заголовком X-Payload-Tag, а тег известен только после final(), заголовки же уходят до тела. То есть §7 жёстко предписывает буферизацию, и единственный оставшийся рычаг — ЧИСЛО одновременных буферов. По байтам, а не по числу запросов: 200 запросов по 600 КБ и 200 по 3 МБ различаются в пять раз, и один и тот же числовой лимит означал бы разное потребление. Освобождение по 'close' критично: клиентский таймаут приёма 15 с (Config.h:48), значит медленный клиент держит шифротекст в буферах сокета все 15 секунд, и бюджет, освобождённый раньше, врёт ровно в момент пиковой нагрузки.
503, а не 429: по §2.3 и приложению Б RATE_LIMITED повторять ЗАПРЕЩЕНО, то есть 429 на всплеске нагрузки превращает обычный перезапуск загрузчика в тупик; 503 повторяем с экспоненциальной задержкой — ровно нужная семантика.

**Отвергнуто.** Ничего не делать (вариант 1) — при 500 одновременных запусках на потолке 3 МБ контейнер убивают по OOM. Ограничение по числу одновременных запросов — см. выше. 429 на backpressure — невозвратный код на временную перегрузку.

### 15. Полный список заголовков успешного ответа

**Выбор.** 200, Content-Type: application/octet-stream (ставится ЯВНО), Content-Length (Fastify ставит сам для Buffer, chunked не используется).
  Cache-Control: no-store
  Pragma: no-cache
  X-Payload-Sha256: 64 hex нижнего регистра — SHA-256 РАСШИФРОВАННОГО содержимого, из PayloadBuild.sha256
  X-Payload-Size:   десятичное число байт открытого текста, из PayloadBuild.size
  X-Payload-Version: версия сборки payload'а, напр. 1.2.0
  X-Payload-Nonce:  24 hex — 12 байт IV, свежие на каждый ответ
  X-Payload-Tag:    32 hex — 16 байт GCM-тега
  X-Request-Id:     req.id (uuid v7, genReqId в main.ts:43)
Всё в hex нижнего регистра; base64 в контракте не появляется. Тег ОТДЕЛЬНЫМ заголовком, а не приклеен к телу. X-Content-Type-Options: nosniff уже ставится глобально @fastify/helmet — дублировать не нужно. Заголовки ставятся ТОЛЬКО непосредственно перед send, после всей способной упасть работы.

**Почему.** Hex везде — потому что HexDecode на клиенте уже есть (Hex.cpp:25), а модуля Base64 нет вовсе; вводить второй кодек ради четырёх заголовков значит писать и тестировать лишний файл (это же и есть ответ на открытый вопрос клиента). X-Request-Id нужен именно здесь: успешный ответ не имеет JSON-тела, поэтому при исходе «расшифровалось, но sha256 не сошёлся» клиенту нечего указать в отчёте по §9, а поддержке нечего искать. Content-Length равен длине открытого текста (GCM не меняет длину) — размер payload'а виден на проводе всегда; новой информации против X-Payload-Size это не даёт, но зафиксировать надо, чтобы никто не считал длину секретом. Заголовки ставятся последними, чтобы исключение до send прошло через AllExceptionsFilter и получило нормальную JSON-форму.

**Отвергнуто.** Тег последними 16 байтами тела — §7 фиксирует отдельный заголовок, и на C++ это разные ветки кода. Base64 для nonce/tag — см. выше. X-Payload-Version без покрытия тегом — инвариант «все X-Payload-* аутентифицированы» дороже одной строки конкатенации.

### 16. Полный список кодов ошибок и их статусов

**Выбор.** 400 BAD_REQUEST (ValidationPipe: формат sessionKey/productSlug/hwid, лишнее поле — forbidNonWhitelisted), 400 SESSION_KEY_REUSED, 400 INVALID_CLIENT_VERSION не используется (см. решение об UPDATE_REQUIRED).
401 UNAUTHORIZED / SESSION_REVOKED — JwtAuthGuard, срабатывает РАНЬШЕ подписи.
403 SIGNATURE_MISSING / SIGNATURE_INVALID / SIGNATURE_EXPIRED / REPLAY — SignatureGuard.
403 API_KEY_SCOPE — ключ сборки без scope launcher:payload.
404 PRODUCT_NOT_FOUND, 404 LICENSE_NOT_FOUND.
403 LICENSE_EXPIRED / LICENSE_BLOCKED / LICENSE_REVOKED / LICENSE_NOT_BOUND / DEVICE_BLOCKED / HWID_MISMATCH.
409 PAYLOAD_NOT_READY — нет опубликованной сборки в канале, либо у сборки нет файла, либо файл помечен удалённым.
426 UPDATE_REQUIRED.
429 RATE_LIMITED + Retry-After — только жёсткий потолок злоупотребления.
503 SERVICE_UNAVAILABLE + Retry-After — исчерпание байтового бюджета, недоступность хранилища; 503 PAYLOAD_CORRUPT — байты в хранилище разошлись с эталонным sha256.
В контракте записывается: LICENSE_INVALID из §7.3 — это ИМЯ СЕМЕЙСТВА, а не код на проводе; клиент обязан любой незнакомый 403 трактовать как общий экран «лицензия недействительна». Тело любой ошибки — единый конверт AllExceptionsFilter, то есть Content-Type ответа зависит от исхода: octet-stream при 200, application/json при любой ошибке.

**Почему.** Детальные коды, а не схлопнутый LICENSE_INVALID, по трём причинам. (1) Резолвер общий с license/check и бросает готовые HttpException — схлопывание потребовало бы слоя-переводчика, существующего только чтобы терять информацию. (2) Приложение Б ТЗ — документ, по которому реально пишется клиент — перечисляет детальные коды без привязки к эндпоинту, и Api.h:104-110 уже ветвится ровно по ним. (3) Пользователю нужен экран «продлить» против «обратитесь в поддержку» независимо от того, какой эндпоинт заметил проблему; проверка на утечку пройдена — детальный код сообщает противнику только факты о его собственной лицензии, которые он секунду назад получил от license/check по §6.1. Смена Content-Type между 200 и 4xx записывается в контракт явно: это то, обо что спотыкается клиент, переставший разбирать JSON на бинарном эндпоинте (в C++ сделано правильно — Outcome() конвертит тело в строку только для НЕ-2xx, Api.cpp:188-190). PAYLOAD_CORRUPT вынесен в 503, а не 409, потому что это наша авария, а не состояние публикации.

**Отвергнуто.** Буквальный §7.3 (одна строка LICENSE_INVALID) — платим UX за секретность, которой нет. Отдавать оба набора (детальный code + LICENSE_INVALID в details) — два источника правды в одном теле ошибки. 401 вместо 403 на подписи — не рассматривается, зафиксировано комментарием signature.guard.ts:201-208.

### 17. Как вычисляется UPDATE_REQUIRED (426), если в теле §7 нет clientVersion

**Выбор.** Источник версии клиента — обязательный заголовок X-Client-Version (§2.1), парсится существующей формулой major*1_000_000 + minor*1_000 + patch по regex ^(\d{1,3})\.(\d{1,3})\.(\d{1,4})$ (та же, что в launcher.service.ts:252-254). Порог — PayloadBuild.minLauncherVersionCode ТОЙ сборки, чей payload выдаётся (она уже прочитана на шаге 409). Правило: порог NULL → проверки нет; версия клиента ниже порога → 426 UPDATE_REQUIRED; порог задан, а заголовок отсутствует или не парсится → тоже 426.
В документации записывается прямо: 426 — механизм СОВМЕСТИМОСТИ, а не мера безопасности.
Отдельно отмечено: в сиде есть неиспользуемая настройка api.launcher_min_version_code = 0 (prisma/seed.ts:239, проверено грепом — не читается нигде) — это естественное место для ПЛАТФОРМЕННОГО пола версии, отдельного от порога конкретной сборки; в v1 не задействуется.

**Почему.** §7.3 требует этого кода, а поле minLauncherVersionCode пишется в versions.service.ts:104 и не читается НИГДЕ во всём src (проверено грепом) — реализовывать 426 сегодня не на чем. Привязка порога к ВЫДАВАЕМОЙ сборке — единственный неарбитрарный ответ на вопрос «по какой версии брать порог»: порог едет вместе с payload'ом в одной строке. Отказ при непарсящемся заголовке нужен потому, что гейт, выключаемый удалением заголовка, — не гейт; легальный клиент этого не увидит, X-Client-Version отправляется через addRequired (Http.cpp:359), то есть запрос без него вообще не уходит. Честность про безопасность обязательна: X-Client-Version полностью контролируется противником, он пошлёт 999.999.9999 и обойдёт 426 за секунду. Настоящий жёсткий рубеж уже существует и ничего не стоит — отзыв X-Api-Key сборки (revokedAt → 403 SIGNATURE_INVALID, signature.guard.ts:66-68), то есть форс-обновление это операция в админке.

**Отвергнуто.** Добавить clientVersion в тело — расходится с §7, требует правки подписи на клиенте и ничего не решает (тело тоже контролируется клиентом). Брать порог у последней опубликованной версии ПРОДУКТА — у продукта и payload'а разные оси, порог поехал бы при каждом релизе игры. 400 при непарсящейся версии — клиент не поймёт, что делать, а 426 сообщает ровно нужное действие.

### 18. Ограничивать ли scopes ключа сборки

**Выбор.** ДА, payload — первый эндпоинт, который их читает. Создаются decorators/require-api-scope.decorator.ts (@RequireApiScope('launcher:payload')) и guards/api-scope.guard.ts — крошечный guard, читающий request.apiKey.scopes и метаданные; вешается на метод payload после SignatureGuard. Отказ → 403 API_KEY_SCOPE. Переходное правило: ПУСТОЙ массив scopes = «все», плюс WARN на старте со списком ключей с пустыми scopes. Сид проставляет ключу сборки явные scopes. api_keys.ip_whitelist для клиентских сборок НЕ применяется и помечается в схеме как «для серверных ключей».

**Почему.** Проверено грепом по всему src: request.apiKey.scopes записывается в signature.guard.ts:93 и не читается ни разу. То есть сегодня ЛЮБОЙ валидный ключ сборки подписывает любой эндпоинт, и утёкший ключ сборки продукта А открывает payload продукта Б. Секрет подписи извлекаем из бинарника — это признано данностью в комментарии самого guard'а (строки 19-22), значит утечка ключа не гипотеза, а вопрос времени; scope ограничивает радиус поражения и позволяет отозвать точечно. Поле, которое заполняется и не проверяется, вдобавок создаёт иллюзию ограничения при ревью. Fail-open на пустых scopes сознателен и временен: иначе правка одномоментно ломает все существующие сборки.

**Отвергнуто.** Оставить как есть (вариант 1). Считать пустой scopes как «ничего» — ломает всех существующих. Проверять scope внутри сервиса — решение о допуске должно приниматься до входа в бизнес-логику.

### 19. Вести ли журнал выдач и как писать при недоступности БД

**Выбор.** ДА, отдельная append-only модель:

model PayloadIssue {

Запись — ПРЯМОЙ INSERT в Postgres, без Redis Stream. Строка пишется на КАЖДУЮ попытку, включая отказы, и ДО reply.send. Для result=ISSUED запись fail-closed (не удалось записать → 503, тело не отдаётся); для строк-отказов best-effort (catch + warn), чтобы сбой журнала не превращал чистый 403 в 500. Ретенция — по умолчанию 180 дней, значение выносится владельцу. Партиционирование не нужно. Маршрут НЕ помечается @Audit.

**Почему.** Обещание §7.1 («повторно запросить нельзя без валидной подписи и лицензии») верно для одиночного запроса и никак не мешает шарингу: одна лицензия, двадцать человек по очереди, у каждого своя валидная сессия и валидная подпись. Отличить это от нормальной работы можно ТОЛЬКО считая выдачи в разрезе лицензии/HWID/IP за окно, а данных для такого счёта в базе нет вообще — проверено, что после выдачи не остаётся ни строки. Отказы обязаны попадать в журнал наравне с успехами: тот, кому двести раз отказали по HWID_MISMATCH, — самая интересная строка в таблице. Прямой INSERT, а не Redis Stream с воркером: объём ~3 тыс. строк в сутки (два порядка ниже heartbeat-потока, который справедливо не пишут в БД), а fail-closed не добавляет НОВОГО режима отказа — проверка лицензии и так требует Postgres, потому что заявленный Redis-кэш license:check: не существует (CHECK_CACHE_PREFIX используется только в invalidate(), launcher.service.ts:189-191, и сам invalidate() не вызывается нигде). @Audit нельзя вешать категорически: AuditInterceptor пишет request.body целиком, а REDACTED_FIELDS (проверено, audit.service.ts:27-51) не содержит ни sessionKey, ни hwid — журнал, который хранится годами и читается людьми, мгновенно стал бы утечкой секрета сессии и Disk ID.

**Отвергнуто.** Не вести журнал (вариант 1) — эндпоинт главный по ценности, а следов от него ноль, и антифрод из п.15 ТЗ строить не на чем. Redis Stream + воркер (вариант 2) — целый новый компонент со своими режимами отказа ради нагрузки, которую Postgres не замечает. Только счётчик в Redis — по счётчику нельзя провести расследование и нечего предъявить в споре о чарджбеке, а Redis настроен на allkeys-lru. Писать в audit_logs — таблица акторно-центрична, партиционирована и предназначена для админских действий.

### 20. Нужен ли rate limit и 429

**Выбор.** Трёхуровнево. (1) Перегрузка по памяти — 503 + Retry-After (admission control, см. выше), НЕ 429. (2) Мягкий порог, по умолчанию limits.payload.soft_per_license_per_hour = 20, счётчик INCR+EXPIRE в Redis: ВЫДАЁМ, но пишем AntiFraudEvent типа RATE_LIMIT_EXCEEDED (тип уже есть в enum, schema.prisma:185) с details.endpoint='payload'. (3) Жёсткий потолок limits.payload.hard_per_license_per_hour = 60 → 429 RATE_LIMITED + Retry-After и строка DENIED_RATE_LIMIT в журнале. Оба значения — настройки, не константы. Плюс отдельная зона nginx под payload.

**Почему.** 429 по §2.3 и приложению Б повторять ЗАПРЕЩЕНО. Значит любой порог, способный сработать на нормальном поведении (перезапуск загрузчика, падение игры, второе окно), превращается в тупик, из которого пользователь не выйдет сам — это хуже, чем пропущенный шаринг. 20/час уже выше любого нормального сценария, но ниже перебора, поэтому там правильная реакция — наблюдать. 60/час уже недвусмысленно. Новое значение в enum AntiFraudType не заводится: RATE_LIMIT_EXCEEDED существует и подходит, а миграция enum лишняя. Параллельные запросы НЕ сериализуются локом: два окна после падения — легитимный сценарий, а нонс-риска параллельность не создаёт по построению (у каждого запроса свой sessionKey и свой серверный IV).

**Отвергнуто.** Никакого лимита (вариант 1) — п.15 ТЗ прямо требует детектировать «слишком частые запросы» и «повторные запросы». Жёсткий лимит без мягкого уровня — невозвратность 429 при неизвестных реальных цифрах. Полагаться только на nginx — зона launcher_zone 120 r/m считает всех за одним NAT одним пользователем и делит бюджет с проверкой лицензии. Лок на licenseId в Redis — добавляет отказ там, где его не было.

### 21. Что делать с nginx, который сейчас кладёт payload на диск

**Выбор.** В docker/nginx/templates/default.conf.template добавляется НОВАЯ зона и НОВЫЙ location, размещённый НЕПОСРЕДСТВЕННО ПЕРЕД общим location ~ ^/api/v\d+/launcher/ :

  limit_req_zone $binary_remote_addr zone=payload_zone:10m rate=30r/m;   # рядом с существующими зонами

  location ~ ^/api/v\d+/launcher/payload$ {
      limit_req zone=payload_zone burst=5 nodelay;
      proxy_buffering off;
      proxy_max_temp_file_size 0;
      gzip off;
      proxy_read_timeout 60s;
      proxy_pass http://api_upstream;
  }

limit_req обязателен к повторению: директивы из соседнего location не наследуются, а на уровне server их нет. Регулярный location, а не location = : покрывает будущие версии API одним правилом; регулярные проверяются в порядке объявления, поэтому размещение выше общего решает всё.
Отдельно: error_page 429 = @json429 с внутренним location, отдающим тело в форме ApiErrorBody, — иначе nginx отдаёт HTML, и клиентский ParseErrorEnvelope (Http.cpp:420) доложит «неизвестная ошибка», то есть сработавший лимит будет выглядеть как поломка сервера.
В докладной записке фиксируется отдельно: комментарий в шаблоне «В приложении есть свой rate limit» — НЕПРАВДА (проверено: @nestjs/throttler в зависимостях нет, троттлинга в src нет); строку надо поправить.

**Почему.** Проверено: у location ~ ^/api/v\d+/launcher/ (строки 100-104 шаблона) нет ни proxy_buffering off, ни proxy_max_temp_file_size 0. При дефолтных proxy_buffers ответ в 600 КБ–3 МБ уезжает во ВРЕМЕННЫЙ ФАЙЛ nginx, то есть payload физически оказывается на диске нашего сервера — ровно то, что §7 и §11.3 запрещают на клиенте, просто на другом конце провода, и §7.1 требует «ответ не кэшируется ничем: ни CDN, ни прокси». Это самый неприятный класс нарушения — незаметный, обнаруживаемый только осмотром /var/cache/nginx. gzip off формально избыточен (octet-stream не входит в gzip_types, строка 75), но ставится явно, чтобы будущее расширение списка не включило сжатие шифротекста. 60s вместо 30s — 3 МБ по узкому каналу.

**Отвергнуто.** Отключить буферизацию для всего /launcher/ — ухудшает поведение под медленными клиентами на дешёвых JSON-ответах проверки лицензии, где она полезна. Ничего не делать и понадеяться на Cache-Control — no-store управляет кэшем, а не временными файлами буферизации.

### 22. Как отдавать бинарь из NestJS+Fastify и что с CORS

**Выбор.** Контроллер: @Post('payload') @HttpCode(HttpStatus.OK) @RequireApiScope('launcher:payload'), параметр @Res() reply БЕЗ passthrough, обработчик возвращает void и сам делает reply.type('application/octet-stream').headers({...}).send(ciphertext). @Audit НЕ вешается. Освобождение байтового бюджета — reply.raw.once('close', release).
CORS в main.ts: в allowedHeaders добавляется 'X-Nonce' (сейчас его там НЕТ, проверено — строки 122-131, браузерный клиент не сможет подписаться), добавляется exposedHeaders: ['X-Payload-Sha256','X-Payload-Size','X-Payload-Version','X-Payload-Nonce','X-Payload-Tag','X-Recheck-After','X-Request-Id'].

**Почему.** Явный Content-Type до send гарантирует, что сериализатор Fastify не тронет Buffer. Не-passthrough @Res отключает участие Nest в формировании ответа — здесь это плюс: единственный глобальный интерцептор в проекте (AuditInterceptor) именно тот, которого сюда пускать нельзя. Content-Length для Buffer Fastify ставит сам, то есть без chunked encoding, и клиент может зарезервировать вектор по content-length заранее — что как раз и предлагается сделать на стороне C++. CORS: для C++-загрузчика безразлично (Origin не шлётся), но любой браузерный тестовый стенд не увидит X-Payload-* и не сможет подписать запрос — и обнаружится это в самый неудобный момент.

**Отвергнуто.** @Res({passthrough:true}) + return buffer (вариант 1) — работает, но оставляет формирование ответа Nest-адаптеру там, где нам нужен полный контроль над заголовками и порядком. StreamableFile — стриминг невозможен по контракту (тег в заголовке).

По умолчанию заложено 180. (б) Кто читает журнал в админке: хватает существующей группы прав или нужно новое право (напр. payload.issues.read), и видит ли реселлер выдачи своих клиентов. (в) Подтвердить fail-closed для ISSUED: при недоступности Postgres выдача останавливается. Сегодня это не новый режим отказа (проверка лицензии и так требует БД), но если Redis-кэш проверки когда-нибудь доделают, payload останется единственным, кто падает вместе с БД.

**Почему.** Ретенция и права — политика, а не код. Fail-closed — сознательный размен между «выдать без следа» и «остановить пользователя», и его должен подтвердить владелец.

**Отвергнуто.** Выбрать ретенцию по аналогии молча: срок жизни доказательства в финансовом споре не техническая величина.

### 34. ВЛАДЕЛЬЦУ — 7. Пороги лимитов, поведение при обрыве и mandatory-обновлении

**Выбор.** Требуется ответ человека по трём пунктам. (а) Стартовые пороги выдач на лицензию в час (заложены 20 мягкий / 60 жёсткий) — они прямо задают, когда обычный перезапуск загрузчика упрётся в невозвратный 429. (б) Что делать при обрыве соединения на середине отдачи: клиент payload не получил, но по §2.3 повторять не-5xx нельзя. Заложено: GetPayload делает один повтор с НОВЫМ sessionKey; надо подтвердить, как это уживается с лимитом и с антифродом, который увидит две выдачи подряд. (в) Отдавать ли payload, когда доступно ОБЯЗАТЕЛЬНОЕ обновление (update.mandatory=true), но версия ещё не ниже minLauncherVersionCode: формально UPDATE_REQUIRED не наступил, а работать пользователю по §8 нельзя.

**Почему.** Все три — про то, что увидит живой пользователь в неудачный момент, и ни одно не выводится из кода.

**Отвергнуто.** Ставить жёсткий лимит сразу — при неизвестных реальных цифрах ломает легитимный рестарт. Тихо отдавать payload при mandatory-обновлении — расходится с §8.

### 35. ВЛАДЕЛЬЦУ — 8. Шифровать ли payload в хранилище (at rest)

**Выбор.** Требуется ответ человека. Заложено: хранится ОТКРЫТЫМ текстом в приватном бакете, шифрование at rest — средствами хранилища (SSE), не приложением. Тогда PayloadBuild.sha256 и есть хеш открытого содержимого для X-Payload-Sha256. Если владелец потребует шифрования ключом приложения, потребуются отдельная колонка версии ключа по образцу hwid_enc_key_ver и разделение sha256 шифротекста и открытого текста — иначе ротация ключа потребует остановки сервиса.

**Почему.** Сервер обязан держать открытый текст в памяти, чтобы зашифровать его под sessionKey, поэтому шифрование at rest защищает только от компрометации хранилища, а не от компрометации API. Это размен, который выбирает владелец.

**Отвергнуто.** Шифровать ключом приложения по умолчанию — усложняет ротацию и требует второй колонки хеша ради выигрыша, которого владелец, возможно, не просил.

### Д1. [КРИТИЧНО] [авторизация] Лицензия в статусе PENDING, у которой выставлена привязка, проходит все проверки payload и даёт бессрочную выдачу: срок никогда не начинается, expiresAt остаётся NULL, а verify-only payload по построению не может это исправить.

**Сценарий.** Пользователь купил лицензию (issue() → PENDING, expiresAt=NULL, currentDeviceId=NULL), но ещё ни разу не запускал загрузчик и написал в поддержку «не стартует». Саппорт применяет штатную операцию ТЗ п.7 — ручную установку привязки (HwidService.setManually). Она пишет currentDeviceId, но НЕ вызывает licenses.activate. То же самое даёт связка block → unblock: unblock восстанавливает PENDING при activatedAt=NULL, currentDeviceId при блокировке не снимается.

**Правка.** В resolveForLauncher для payload требовать status === ACTIVE явно (verify-only путь не может активировать, значит PENDING обязан быть отказом — отдельный код, напр. Параллельно — либо setManually должен вызывать licenses.activate в той же транзакции, либо assertUsable должен получить явную ветку PENDING. Пока не сделано, состояние «PENDING + bound» вообще не должно быть достижимо.

**Доказательство.** launcher.service.ts:204-234 — assertUsable проверяет BLOCKED/REVOKED/EXPIRED, ветки PENDING нет; launcher.service.ts:227 — `license.expiresAt !== null && license.expiresAt.getTime() < Date.now()`; hwid.service.ts:255-308 — setManually делает license.update({currentDeviceId}) и licenses.activate не зовёт; licenses.service.ts:108-131 — срок ставится ТОЛЬКО в activate(); licenses.service.ts:258-263 — unblock восстанавливает PENDING при activatedAt=NULL. hwid.service.ts:612-630 — loadLicense отбивает только REVOKED, PENDING проходит.

### Д2. [КРИТИЧНО] [эксплуатация] У S3Client нет ни одного таймаута, а single-flight хранит Promise — зависшее хранилище выводит эндпоинт из строя навсегда, а не на время аварии.

**Сценарий.** MinIO/R2 принимает TCP-соединение, но перестаёт отвечать (сетевой раздел, зависший узел, переполненный диск). Лидер single-flight вызывает head()+GetObject и висит без предела; его Promise лежит в Map. Все последующие запросы этой сборки await'ят ровно этот промис — и после восстановления хранилища тоже, потому что он никогда не резолвится и никогда не отклоняется. Payload по этой сборке мёртв до перезапуска процесса, при этом /health/ready зелёный. Зеркальный вариант: если промис всё-таки отклонится, а запись из Map не удалить в finally, все будущие запросы получат вечный 503 из закэшированного rejected-промиса.

**Правка.** Задать requestHandler с connectionTimeout (2-3 с) и requestTimeout (10-15 с) при создании S3Client; в getObjectBuffer добавить общий дедлайн через AbortController на GetObjectCommand и на цикл чтения тела (таймаут запроса у smithy не покрывает чтение стрима); в payload-cache обернуть заполнение Promise.race с дедлайном и обязательно удалять запись из Map в finally при любом исходе, кроме успеха.

**Доказательство.** storage.service.ts:67-75 — S3Client создаётся без requestHandler, то есть с дефолтами @smithy/node-http-handler, где DEFAULT_REQUEST_TIMEOUT = 0 (node_modules/@smithy/node-http-handler/dist-cjs/index.js:208) и connectionTimeout не задан. FastifyAdapter (main.ts:38-51) задаёт только genReqId/trustProxy/bodyLimit — requestTimeout Fastify остаётся 0. Проект добавляет getObjectBuffer поверх этого же клиента и явно фиксирует «Map хранит не Buffer, а Promise<Entry>».

### Д3. [КРИТИЧНО] [эксплуатация] Байтовый бюджет admission control протекает при обрыве соединения: release по once('close') не сработает, если сокет закрылся до подписки на событие.

**Сценарий.** Клиент отваливается по своему 15-секундному таймауту, пока сервер ждёт в очереди single-flight или читает 3 МБ из хранилища. Node уничтожает сокет, reply.raw испускает 'close' в этот момент. Обработчик доходит до участка перед send, вешает once('close') — событие уже произошло и больше не повторится, release не вызывается никогда. Каждый оборванный запуск съедает 3 МБ из 128 МиБ навсегда: после ~43 обрывов acquire() отвергает всё, и весь продукт получает 503 SERVICE_UNAVAILABLE до перезапуска процесса. Утечка максимальна ровно на пике и на плохих каналах, то есть тогда, когда бюджет и нужен.

**Правка.** Вешать слушатель немедленно после acquire, до любой асинхронной работы; сделать release идемпотентным (флаг released) и вызывать его и из 'close', и из finally обработчика; сразу после подписки проверить reply.raw.destroyed / writableEnded и освободить, если сокет уже закрыт; добавить страховочный таймер на максимальное время удержания слота, чтобы любая незамеченная ветка не удерживала бюджет вечно.

**Доказательство.** Решение проекта: «Освобождение — по событию 'close' на reply.raw» и одновременно «Заголовки ставятся ТОЛЬКО непосредственно перед send, после всей способной упасть работы». Клиентский таймаут приёма — 15 с (Config.h: kReceiveTimeoutMs = 15'000), то есть обрывы на медленном канале штатны.

### Д4. [КРИТИЧНО] [эксплуатация] Бюджет 128 МиБ резервирует одну копию из трёх-четырёх реально живущих одновременно, и делает это в Buffer'ах вне V8-heap, а лимита памяти у контейнера api нет.

**Сценарий.** Пик запусков заполняет бюджет: 42 запроса по 3 МБ = 128 МиБ «по учёту», а фактическое потребление сверх базы — 350-500 МБ, потому что на каждый запрос приходится минимум plaintext + ciphertext, а при промахе кэша ещё и удвоение на Buffer.concat. Это Buffer'ы, то есть external memory: они не ограничены --max-old-space-size и не вызовут управляемый OOM в V8 — процесс убьёт OOM-killer хоста. Дополнительно учёт врёт в обратную сторону при обрывах: release по 'close' отпускает бюджет, а чтение из хранилища и шифрование продолжаются (AbortSignal никуда не проброшен), то есть память ещё занята, а слот уже выдан следующему.

**Правка.** Резервировать k×size (k≈3) либо вести учёт по фактическим аллокациям (инкремент при concat и после encrypt); прокинуть AbortSignal от reply.raw в GetObjectCommand и в цикл чтения, чтобы обрыв реально прекращал работу; выставить контейнеру api жёсткий лимит памяти и --max-old-space-size, чтобы промах в расчётах давал предсказуемый рестарт, а не убийство хоста.

**Доказательство.** Решение: «Резервация делается ПОСЛЕ чтения строки PayloadBuild (размер известен из БД)» — резервируется size открытого текста. Реально в этот же момент живут: массив чанков плюс результат Buffer.concat (пик 2×N при склейке), запись LRU с открытым текстом, отдельный ArrayBuffer ciphertext от subtle.encrypt (тег отрезается subarray, но сам буфер новый), плюс копия в буфере записи сокета при медленном клиенте. docker-compose.yml, сервис api (строки ~150-185) — ни mem_limit, ни deploy.resources.

### Д6. [ВАЖНО] [крипто] Обоснование «соль HKDF = серверный IV конструктивно исключает повтор пары (ключ, IV)» ложно: свойство целиком обеспечивается серверной генерацией IV и держится при ЛЮБОЙ соли, а salt=IV дополнительно схлопывает ключ и нонс в один и тот же 12-байтовый выход randomBytes.

**Сценарий.** Берём ровно тот сценарий, ради которого сделан выбор — сборка загрузчика со статическим sessionKey. Design A (salt=IV): key = HKDF(sk, IV), пара (key, IV) повторяется тогда и только тогда, когда повторяется IV. Design B (salt = фиксированная константа): key постоянен, пара (key, IV) повторяется тогда и только тогда, когда повторяется IV. Условие идентично — тот же birthday-порог на 96 битах (~2^-32 при 2^32 ответов). То есть выигрыш ровно нулевой, а «физически не может» — неверное утверждение. Дальше salt=IV начинает вредить: ключ и нонс теперь оба выводятся из ОДНОГО вызова randomBytes(12). Восстановление контейнера api из VM/CRIU-снимка, клонирование инстанса с уже проинициализированным состоянием ГПСЧ, форк после засева — и два разных ответа одному клиенту (тому самому, что переиспользует sessionKey) получают одновременно одинаковый ключ И одинаковый нонс. При независимой соли дублирующийся IV дал бы РАЗНЫЕ ключи и катастрофы не было бы. Результат при salt=IV: XOR двух открытых текстов и восстановление ключа аутентификации GHASH — ровно «полная потеря стойкости», описанная в комментарии crypto.service.ts:75-77. Отдельно: угроза статического sessionKey уже перекрыта проверкой SET NX (400 SESSION_KEY_REUSED), то есть KDF решает задачу, которая решена дважды и которую он всё равно не решает.

**Правка.** Убрать из документа утверждение про «конструктивное исключение повтора» — реальные гарантии дают (а) серверная генерация IV и (б) правило «один ключ — одно сообщение», обеспечиваемое проверкой свежести sessionKey, а не солью. Соль оставить любую (salt=IV допустима как RFC-корректная), но записать честно, что она не даёт защиты от переиспользования sessionKey. Единственная работающая реакция на сломанный клиент — отказ (SESSION_KEY_REUSED), а не надежда на KDF. Дополнительно зафиксировать в runbook запрет на восстановление api-контейнера из снапшота памяти и требование к энтропии при клонировании инстансов.

**Доказательство.** apps/api/src/common/crypto/crypto.service.ts:75-77 (комментарий про повтор IV в GCM); решение «соль = IV» в разделе про HKDF; решение про SET NX EX payload:sk:<sha256(sessionKey)>

### Д7. [ВАЖНО] [крипто] AAD не защищает от того противника, ради которого введён: тот, кто может переписать заголовок X-Payload-Sha256, терминирует TLS и потому видит sessionKey в теле запроса — он выводит тот же ключ и переподписывает ответ целиком.

**Сценарий.** Пользователь ставит свой корневой сертификат (сценарий признан рабочим в TZ-LAUNCHER.md:96-99) или трафик идёт через инспектирующий корпоративный прокси. Запрос и ответ едут по ОДНОМУ TLS-соединению, значит любой узел, способный изменить заголовок ответа, уже прочитал тело запроса и знает sessionKey (64 hex). Он выполняет HKDF-SHA256(salt=свой новый IV, ikm=sessionKey, info='lp/payload/v1') — вся спецификация публична и реализована в самом клиенте — шифрует ЛЮБОЙ выбранный payload, ставит свой X-Payload-Nonce/Tag и любые X-Payload-Sha256/Size/Version. Клиент проверяет тег — сходится, сверяет sha256 — сходится, принимает подменённый payload как подлинный. Заявленный в обосновании сценарий «посредник переворачивает дайджест, не умея расшифровать тело» не наступает: такому посреднику незачем переворачивать дайджест. Класс противника, против которого AAD реально работает (меняет заголовки ответа, но не видит тела запроса), в этой схеме не существует. При этом цена AAD вполне реальна и уже названа автором: любое расхождение канонизации значений заголовков проявляется исключительно как провал тега без диагностики.

**Правка.** AAD оставить (домен-разделение и защита от случайного рассогласования стоят дёшево), но вычеркнуть из обоснования сценарий с подставленным корнем и снять утверждение, что §7.2.3 «перестаёт быть декорацией». В документ записать прямо: против противника, терминирующего TLS, целостность ответа payload НЕ обеспечивается ничем — ни AAD, ни sha256, ни подписью (секрет подписи извлекаем из бинарника, это уже признано в signature.guard.ts). Если целостность против такого противника нужна, это отдельная задача (закреплённый в бинарнике асимметричный ключ сервера и подпись заголовков ответа), и её надо ставить явно, а не считать закрытой.

### Д8. [ВАЖНО] [крипто] Серверная сверка байтов с эталонным sha256 привязана к моменту ЗАПОЛНЕНИЯ кэша, а заголовки и AAD берутся из свежепрочитанной строки БД: между ними нет связи, и устаревшая запись кэша выдаётся под новым эталоном.

## Известные ограничения — записать, не маскировать

- ГЛАВНОЕ, ЧЕГО СХЕМА НЕ ДЕЛАЕТ. Лицензиат получает открытый payload целиком и всегда: он сам сгенерировал sessionKey, выводит тот же ключ, что и сервер, а если поленится — снимет расшифрованный буфер из памяти своего процесса. Ни HKDF, ни AAD, ни no-store этому не мешают. Шифрование лишает противника УДОБСТВА (нет ссылки, которую можно переслать) и убирает открытые байты из промежуточных узлов; продавать это как защиту контента нельзя.
- Шифрование не защищает и от чтения канала: sessionKey едет в теле того же TLS-соединения, что несёт ответ. Любой, кто расшифровал TLS (корпоративный инспектирующий прокси, MitM-шлюз), видит sessionKey и выводит ключ. Против такого противника ECDH дал бы реальную стойкость, а схема из §7 — нет. Это цена дизайна, зафиксированного в ТЗ, и её надо записать, а не замаскировать.
- Шаринг лицензии эндпоинтом не предотвращается. Один аккаунт, двадцать человек по очереди, у каждого валидная сессия и валидная подпись — для сервера это нормальная работа. Всё, что мы можем, — увидеть корреляцию в payload_issues по hwidHash/IP и сделать дороже лимитом.
- 426 UPDATE_REQUIRED защитой не является: X-Client-Version полностью контролируется противником. Единственный работающий рубеж — отзыв X-Api-Key сборки (revokedAt → 403 SIGNATURE_INVALID), и он существует уже сегодня.
- Неаутентифицированный запрос за payload'ом получает 401 ДО проверки подписи: JwtAuthGuard и PermissionsGuard глобальные (auth.module.ts:52-58, rbac.module.ts:22), SignatureGuard — на классе контроллера, а Nest вызывает глобальные раньше. Следствие: перебор подписей без токена невидим для антифрода — recordFraudEvent просто не вызывается. Проект НЕ меняет порядок guard'ов (это правка глобальной конфигурации auth-слоя, риск несопоставим с выигрышем), но слепая зона должна быть записана в документацию: до-аутентификационное прощупывание видно только в access-логе nginx.
- Открытый payload живёт в памяти воркера Node (LRU) и не может быть исключён из core dump средствами приложения — аналога WerRegisterExcludedMemoryBlock для процесса Node нет. Дамп упавшего API содержит payload открытым текстом. Закрывается настройкой контейнера (RLIMIT_CORE=0, запрет heap snapshot в проде), а не кодом, и должно попасть в runbook.
- Конкуренция за пул libuv с Argon2: @node-rs/argon2 при логине уходит на тот же пул, что и асинхронное AES-GCM. Всплеск запусков будет деградировать ВХОД В СИСТЕМУ, и без метрик по стадиям связь между этими явлениями никто не найдёт. Митигация — UV_THREADPOOL_SIZE=16, зафиксированный в compose и README.
- Расхождение KDF или AAD между Node и C++ проявляется ИСКЛЮЧИТЕЛЬНО как провал GCM-тега — состояние без всякой диагностики, неотличимое от порчи данных. Единственная реальная митигация — контрольные векторы, сгенерированные серверной реализацией и потребляемые тестом на C++, ДО написания клиентского кода.
- AAD аутентифицирует ЗНАЧЕНИЯ заголовков, поэтому промежуточный узел, добавивший пробел или изменивший регистр hex, ломает расшифровку. Контракт обязывает обе стороны канонизировать значения (обрезка с двух сторон, hex нижнего регистра, десятичное без ведущих нулей); правка right-trim в Http.cpp:239-244 — часть этого требования, а не косметика.
- Клиент на C++ сегодня физически не примет ответ: кап 2 МиБ зашит литералом в Send() (Http.cpp:389), переопределить его на уровне запроса нечем, и ответ больше него оборвётся в ResponseTooLarge с частично заполненным телом. До правки Http.h/Http.cpp/Config.h сквозная проверка возможна только скриптом.
- 3 МБ за 15 секунд требуют от канала минимум ~1.6 Мбит/с (Config.h:48). На потолке контракта пользователи с узким каналом будут ловить таймаут приёма как «сервер не отвечает». Митигация — per-request receiveTimeoutMs, но она перекладывает проблему на терпение пользователя.
- Fire-and-forget UPDATE api_keys на каждом подписанном запросе (signature.guard.ts:97-102): 500 одновременных запусков дают 500 сериализованных апдейтов ОДНОЙ строки и 500 захватов слота пула Prisma, а payload удваивает число подписанных запросов на запуск. Троттлинг включён в объём работ; без него это упрётся раньше всего остального.
- Заявленный в шапке LauncherService и в ТЗ §6.2.1 Redis-кэш результата проверки НЕ реализован (CHECK_CACHE_PREFIX только удаляется, invalidate() не вызывается нигде — проверено). Значит payload, обязанный проверять лицензию на каждый запрос, жёстко зависит от Postgres, и обещанная устойчивость к его кратковременной недоступности на этом эндпоинте не существует.
- Дефект неизменяемости релиза остаётся вне этого эндпоинта: versions.confirmUpload не проверяет isPublished и принимает произвольный objectKey (versions.service.ts:193-214), то есть у опубликованной версии можно подменить файл и эталонный sha256 одновременно. Новый payload-путь этот класс дефекта не повторяет и вдобавок сверяет прочитанные байты с эталоном, но подмену И объекта, И эталона через админский API это не поймает. Чинить в products отдельной задачей.
- Отступление от буквы §7.3: сервер отдаёт детальные коды лицензии вместо LICENSE_INVALID, плюс 404 PRODUCT_NOT_FOUND / 404 LICENSE_NOT_FOUND, 403 LICENSE_NOT_BOUND, 403 API_KEY_SCOPE и 400 на кривой sessionKey — этих кодов в §7.3 нет вовсе. Требуется синхронная правка таблицы ошибок на клиенте, иначе они попадут в ветку «неизвестная ошибка».
- Метрик в проекте нет вообще (проверено: prom-client в зависимостях отсутствует, /metrics нет). Без разбивки длительности по стадиям (db / s3 / encrypt / send) на первый же вопрос при деградации — «это хранилище, база или шифрование?» — ответить будет нечем. MetricsModule вынесен в отдельную задачу, но алерты (cache hit ratio, admission_rejected > 0, event loop lag) обязаны появиться ДО включения эндпоинта в проде.
- «Пустой scopes = все» — сознательный fail-open ради обратной совместимости существующих ключей, ровно тот паттерн, который комментарий в auth.module.ts справедливо критикует. Обязан сопровождаться WARN на старте и планом миграции, иначе останется навсегда.
