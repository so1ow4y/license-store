# Контрольные векторы шифрования payload'а

Сгенерировано `apps/api/scripts/generate-payload-vectors.ts` из серверной
реализации `CryptoService`. Реализация на C++ обязана давать те же значения
байт в байт.

Файл не редактируется руками: он перегенерируется скриптом.

> Зачем он нужен. Расхождение KDF или канонизации AAD между Node и C++
> проявляется ИСКЛЮЧИТЕЛЬНО как провал GCM-тега — у клиента нет ни кода
> ошибки, ни подсказки, что именно разошлось. Векторы разбивают эту
> неразличимую точку отказа на отдельно проверяемые шаги: HKDF, AAD,
> шифрование. Пока вектор не сошёлся на обеих сторонах, писать интеграцию
> бессмысленно.

---

## Схема

```
key  = HKDF-SHA256(ikm = sessionKey(32 байта), salt = IV(12 байт),
                   info = ASCII "lp/payload/v1", L = 32)
AAD  = "lp/payload/v1" \n productSlug \n sha256 \n size \n version
тело = AES-256-GCM(key, IV, AAD, открытый текст), тег 16 байт отдельно
```

- `IV` генерирует СЕРВЕР на каждый ответ и отдаёт в `X-Payload-Nonce` (24 hex).
- Тег уходит в `X-Payload-Tag` (32 hex), к телу НЕ приклеивается.
- В AAD поля разделены ОДНИМ `0x0A`, завершающего перевода строки НЕТ.
- Все значения — ASCII: hex в нижнем регистре, size десятичный без ведущих нулей.
- Клиент обязан обрезать значение заголовка с ОБЕИХ сторон перед сборкой AAD.

Чего схема НЕ даёт — чтобы никто не рассчитывал на несуществующее:

- Соль, равная IV, не защищает от клиента, переиспользующего `sessionKey`.
  Повтор пары (ключ, IV) исключает серверная генерация IV, и это свойство
  держится при ЛЮБОЙ соли. Реакция на сломанный клиент — отказ
  `400 SESSION_KEY_REUSED`, а не KDF.
- AAD не защищает от противника, терминирующего TLS: он видит `sessionKey`
  в теле запроса, выводит тот же ключ и переподписывает ответ целиком.
  AAD ловит НАШЕ рассогласование заголовков и тела, и только его.
- `X-Request-Id` в AAD не входит и подменяем — доверенной ссылкой
  на инцидент он не является.

## 2. Вывод боевого ключа

Те же параметры, что в бою: `info` фиксирована, `L` = 32, соль — серверный IV.

| Поле | Значение |
|---|---|
| sessionKey (IKM, 32 б) | `00112233445566778899aabbccddeeff00112233445566778899aabbccddeeff` |
| IV = salt (12 б) | `a1a2a3a4a5a6a7a8a9aaabac` |
| info | ASCII `lp/payload/v1` (13 б) |
| info в hex | `6c702f7061796c6f61642f7631` |
| L | `32` |

**PRK = HMAC-SHA256(key = IV, msg = sessionKey):**

```
86bec3e9b7328e988a37ccfd4d79c75613d624dc0c757757e009be8572aad260
```

**Ключ AES-256 = OKM = HMAC-SHA256(key = PRK, msg = info || 0x01):**

```
6dfd3f5a2cd07f5518162733cd71044aa99cf7bc23ccfc8585a62cf1a2aaabaa
```

При `L` = 32 = длине хеша Expand это РОВНО одна итерация: на C++ два вызова
`HmacSha256` и ноль циклов. Скрипт при генерации сверяет это разложение
с результатом `crypto.hkdf` — если они разойдутся, вектор не выпустится.

## 5. Отрицательный вектор — подменённый productSlug

Тот же вектор A, но AAD собран со слагом `fc27`. Проверяет, что AAD
действительно входит в тег, а не лежит рядом.

| Поле | Значение |
|---|---|
| Тег при productSlug `fc26` | `d1dc56d7ff5ea4397e6e7b15e96c7220` |
| Тег при productSlug `fc27` | `617be9d879bddd1328846fc683c7a929` |
| Шифротекст | одинаковый в обоих случаях |

Шифротекст не зависит от AAD по определению GCM — расходится только тег.
То же самое обязано происходить при подмене любого из `X-Payload-Sha256`,
`X-Payload-Size`, `X-Payload-Version`.

## 6. Канонизация полей

Заголовки и AAD выводятся сервером из ОДНОГО выражения
(`CryptoService.buildPayloadBinding`). Разъехаться они не могут по
построению; таблица показывает, что именно уходит на провод.

| Что лежит в сборке | Значение в заголовке и в AAD |
|---|---|
| version `1.2.0 ` (хвостовой пробел из копипаста) | `1.2.0` |
| version ` 1.2.0` (пробел слева) | `1.2.0` |
| sha256 в ВЕРХНЕМ регистре | `abababababababababababababababababababababababababababababababab` |
| size как BigInt `614400n` | `614400` |
| size со строкой `007` | `7` |

Что отвергается на сервере — вместо того чтобы уехать клиенту и провалить тег:

| Что лежит в сборке | Результат |
|---|---|
| version `1.2.0 beta` | отказ, выдача остановлена (500 + строка в логе) |
| version пустая | отказ, выдача остановлена (500 + строка в логе) |
| sha256 из 63 символов | отказ, выдача остановлена (500 + строка в логе) |
| productSlug `FC26` | отказ, выдача остановлена (500 + строка в логе) |
| productSlug с переводом строки внутри | отказ, выдача остановлена (500 + строка в логе) |
| size = 0 | отказ, выдача остановлена (500 + строка в логе) |

## 7. Порядок проверки на стороне клиента

1. `HkdfExtract`/`HkdfExpand` против раздела 1 — пока не сошлось, дальше не идти.
2. Вывод ключа против раздела 2 — тот же `sessionKey` и тот же IV.
3. Сборка AAD против раздела 3: сравнивать БАЙТЫ, а не строку. Хвостовой
   пробел в значении заголовка виден только в hex.
4. Расшифровка вектора A и B, сверка sha256 открытого текста.
5. Раздел 5: подменить слаг в AAD и убедиться, что расшифровка ПАДАЕТ
   и в выходном буфере не остаётся ни байта открытого текста.
