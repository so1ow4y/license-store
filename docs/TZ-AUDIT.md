## Считается сделанным, но не сделано

Самая ценная часть проверки: то, на что можно положиться по ошибке.

### 1. ЛИЦЕНЗИИ КЭШИРУЮТСЯ В REDIS — НЕТ. Докстринг launcher.service.ts:14-21 обещает бюджет 150 мс за счёт кэша и то, что кратковременная недоступность Postgres «не останавливает всех пользователей разом». Кэша не существует: CHECK_CACHE_PREFIX (launcher.service.ts:24) используется только в del() внутри invalidate() (:353); ни одного SET/GET. Каждая проверка лицензии идёт в Postgres целиком. Сам invalidate() не вызывается никем — проверено грепом. Опасность на будущее: код выглядит корректным, и когда кэш допишут, тест на отзыв лицензии будет проходить даже в сломанном виде.

### 2. АДМИНКА ЕСТЬ — НЕТ. Из 7 разделов п.8 через API достижимы 2 (продукты и версии). Нет модуля пользователей вообще: заблокировать пользователя можно только SQL — это видно прямо в рабочих скриптах владельца, scripts/add-user.ps1:70 и scripts/smoke-rbac-keys.ps1:186 делают UPDATE users SET status=... через psql. UI не существует ни в каком виде.

### 3. ЖУРНАЛ АУДИТА РАБОТАЕТ — ТОЛЬКО НАПОЛОВИНУ. Запись действительно есть и хорошая (audit.service.ts:133-190, 15 маршрутов + 12 прямых вызовов). Читать журнал через API нельзя: grep 'auditLog.' по всему src даёт РОВНО ОДНУ строку — audit.service.ts:135, и это create. Право audit.read не требует ни один маршрут. Журнал наполняется годами и доступен только psql'ем. Плюс: выход из системы не пишется вообще, ошибки не пишутся принципиально (audit.interceptor.ts:12-18).

### 4. НАСТРОЙКИ МЕНЯЮТСЯ ИЗ ПАНЕЛИ БЕЗ ПЕРЕДЕПЛОЯ — НЕТ. SettingsService.set() (settings.service.ts:151) и invalidateAll() (:199) не вызываются никем; контроллера настроек нет. Секретные настройки (digiseller.api_key, telegram.bot_token, discord.client_secret) в БД заполнить в принципе нечем — в is_secret надо класть шифротекст, которого руками не получить. Авторы сами это записали в settings.service.ts:92-93.

### 5. 2FA ЗАЩИЩАЕТ АККАУНТ — ОБХОДИТСЯ. Пользователь с включённой 2FA и привязанным Discord/Telegram входит одним POST /auth/telegram/callback без второго фактора: oauth.service.ts:305-318 зовёт completeLogin напрямую, минуя ветку twoFactorEnabled. Второй фактор обходится тем каналом, который сам пользователь считает вспомогательным. Отдельно: обязательность 2FA для админов не применяется — two-factor.service.ts:252 isRequiredForAdmins() не вызывается ниоткуда, хотя настройка security.2fa.required_for_admin=true засеяна.

### 6. ЛАУНЧЕР УМЕЕТ ОБНОВЛЯТЬСЯ — НЕТ. Сервер считает sha256, size и changelog (versions.service.ts:435-442), но launcher.service.ts:477-490 их выбрасывает и отдаёт клиенту только available/mandatory/version/versionCode. Ссылки на файл нет ни в ответе, ни отдельным маршрутом — createDownloadUrl (storage.service.ts:179) не вызывается никем. Дистрибутив лежит в S3 и недостижим по API. Загрузчику нечего скачивать и нечем проверить целостность. docs/TZ-LAUNCHER.md:604-618 обещает downloadUrl и sha256 в ответе.

## Порядок работ

## Порядок работ — что делать первым и почему именно так

Главный принцип: **нельзя рисовать админку над несуществующим API**, и нельзя чинить UX там, где отсутствует безопасность продакшена. Поэтому сначала — то, что делает систему пригодной к эксплуатации вообще, затем — API, затем — фронт.

### Волна 0. Блокеры продакшена (делать до всего остального, недели 1–2)

1. **HTTPS.** Сегодня канал — плоский HTTP на :80 (`default.conf.template:154,160`). Пока его нет, все остальные меры безопасности — JWT, Argon2, HMAC-подпись — защищают трафик, который читается по дороге. Зависимостей нет, делается за день.
2. **Резервное копирование БД + ключа шифрования.** Отдельно подчеркну: `ENCRYPTION_KEY` живёт в окружении, и без процедуры бэкапа ключа ВМЕСТЕ с базой восстановление `two_factor_secret_enc`, `signing_secret_enc`, `hwid_enc` не гарантировано. Потеря ключа = потеря 2FA и ключей подписи у всех.
3. **Прикладной rate limit.** `@nestjs/throttler` не подключён; зоны nginx — единственная защита, а вся разработка и все смоуки ходят мимо nginx. Как минимум: `/auth/login`, `/auth/2fa/verify`, `/auth/password-reset/confirm`, `/auth/redeem-key`, `/billing/digiseller/redeem`.
4. **Закрыть обход 2FA через OAuth** (`oauth.service.ts:305-318`) и включить `isRequiredForAdmins()` для админских ролей. Это дыра в уже оплаченной функции, а не новая работа.

### Волна 1. Фундамент админского API (недели 3–6) — от него зависит всё остальное

5. **Модуль пользователей** (`users.*`, 7 прав уже в сиде). Список, поиск, карточка, блокировка/разблокировка, редактирование. Почему первым: **сторона применения блокировки уже работает** (`auth.service.ts:782-807`), не хватает только стороны управления; сегодня владелец блокирует пользователей SQL-запросом. Плюс без этого модуля не построить п.10 (кабинет), п.9 (клиенты реселлера) и п.8 (дашборд).

**Примечания:**

- *Привязка автоматически при первом запуске* — Режим первой привязки решается ВНУТРИ bindOrVerify через opts.allowFirstBind (hwid.service.ts:107,122), а не предпроверкой у вызывающего — payload-путь (verify-only) физически не может стартовать оплаченный срок.
- *HWID состоит из Disk ID* — Отклонения нет: У-9 прямо описывает DeviceIoControl/IOCTL_STORAGE_QUERY_PROPERTY как источник.
- *Состав HWID пользователю не отображается* — Сделано строже ТЗ: колонка devices.hwid_enc ЗАПИСЫВАЕТСЯ (hwid.service.ts:142-147, :347-352), но ни один читатель её не расшифровывает (grep hwidEnc по apps/api/src даёт только записи и строку в списке редактируемых полей аудита common/audit/audit.service.ts:88). - *Ограничение: сброс не чаще одного раза в день* — Применяется ТОЛЬКО к самостоятельному сбросу (hwid.service.ts:242-294). Путь staff-reset кулдаун не проверяет вовсе.
