# ТЗ на загрузчик — контракт с сервером лицензирования

Спецификация клиент-серверного взаимодействия. Реализуется на стороне
существующего загрузчика (C++, Windows).

Документ описывает **только контракт**: что и в каком формате уходит на
сервер, что приходит в ответ и как клиент обязан на это реагировать.
Внутреннее устройство загрузчика — способ загрузки payload'а в память,
работа с процессом, UI — предметом этого документа не является.

**Версия контракта:** 1
**Базовый адрес:** `https://<домен>/api/v1`

---

## 1. Разделение ответственности

Принцип: **клиенту не доверяем ни в чём**. Всё, что можно решить на сервере,
решается на сервере. Загрузчик выполняет решения, но не принимает их.

| Решение | Кто принимает |
|---|---|
| Действительна ли лицензия | сервер |
| Совпадает ли HWID | сервер |
| Нужно ли обновление и обязательно ли оно | сервер |
| Выдавать ли payload | сервер |
| Истёк ли срок | сервер |
| Показать пользователю сообщение об ошибке | клиент, по коду от сервера |

Из этого следуют два практических правила:

**Загрузчик не хранит и не вычисляет состояние лицензии.** Никаких локальных
файлов вида «лицензия действительна до…», никакого кэша срока действия.
Единственный источник правды — ответ сервера на текущий запрос.

**Загрузчик не сравнивает HWID сам.** Он отправляет прочитанный Disk ID,
сервер сравнивает. Клиент не знает и не должен знать, какой HWID к лицензии
привязан (требование ТЗ платформы п.7: состав HWID пользователю не
отображается).

## 2. Общие правила запросов

### 2.1. Обязательные заголовки

| Заголовок | Пример | Когда |
|---|---|---|
| `Content-Type` | `application/json; charset=utf-8` | при наличии тела |
| `Accept-Language` | `ru` | всегда — определяет язык сообщений |
| `X-Client-Version` | `1.4.2` | всегда |
| `Authorization` | `Bearer <access_token>` | после входа |
| `X-Api-Key` | `lp_pk_a1b2c3d4` | всегда |
| `X-Timestamp` | `1785500000` | всегда |
| `X-Nonce` | `9f86d081884c7d65…` (32 hex) | всегда |
| `X-Signature` | `5e884898da2804…` (64 hex) | всегда |

### 2.2. Формат ошибок

Единый для всех эндпоинтов. Клиент обязан уметь разобрать это тело при
**любом** статусе 4xx/5xx:

```json
{
  "statusCode": 403,
  "code": "HWID_MISMATCH",
  "message": "Лицензия привязана к другому устройству",
  "requestId": "019fbacc-8bdc-706a-b032-d1eb512286a6",
  "timestamp": "2026-08-01T00:45:33.023Z",
  "details": null
}
```

**Ветвиться нужно по `code`, а не по `message`.** Текст локализуется и
меняется; код — часть контракта.

`requestId` показывается пользователю в окне ошибки. По нему поддержка
находит инцидент одним запросом.

### 2.3. Таймауты и повторы

- Таймаут соединения — 5 с, таймаут ответа — 15 с.
- Повторять можно **только** запросы, завершившиеся сетевой ошибкой,
  таймаутом, `502`, `503`, `504`.
- Повторы с экспоненциальной задержкой: 1 с, 2 с, 4 с, не более 3 попыток.
- **Каждая попытка — новые `X-Timestamp`, `X-Nonce` и `X-Signature`.**
  Повтор с теми же значениями будет отбит как воспроизведение (`REPLAY`).
- `429` повторять нельзя — показать пользователю сообщение и остановиться.

## 3. Подпись запросов

Требование ТЗ платформы п.14 («подпись запросов», «Replay Protection»).

TLS защищает канал, но не отвечает на вопрос «этот запрос действительно
сформировал наш загрузчик». На своей машине пользователь может подставить
свой корневой сертификат и читать весь трафик. Подпись привязывает запрос
к секрету, а метка времени и nonce — к моменту.

### 3.1. Алгоритм

Строка для подписи собирается из пяти полей, разделённых символом `\n`
(0x0A, ровно один, без `\r`):

```
METHOD \n PATH \n TIMESTAMP \n NONCE \n SHA256_HEX(BODY)
```

| Поле | Правила |
|---|---|
| `METHOD` | заглавными: `GET`, `POST` |
| `PATH` | **абсолютный** путь без схемы, хоста и query-строки: `/api/v1/launcher/license/check` — включая префикс `/api/v1` |
| `TIMESTAMP` | unix-время в **секундах**, десятичное, без ведущих нулей |
| `NONCE` | 16 случайных байт в hex нижнего регистра (32 символа) |
| `SHA256_HEX(BODY)` | SHA-256 сырого тела в hex нижнего регистра |

Для запроса без тела берётся хеш **пустой строки**:
`e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`

Подпись:

```
signature = HMAC-SHA256(signing_secret, строка)
```

Результат — hex **нижнего регистра**, 64 символа.

> **Подписываемый путь обязан буквально совпадать с путём в URL.**
> Если базовый адрес настроен как `https://domain/api/v1`, то к нему
> нельзя приклеивать тот же путь, что уходит в подпись, — получится
> `/api/v1/api/v1/...`. Хранить в клиенте нужно одно из двух: либо базу
> без префикса и абсолютный путь везде, либо базу с префиксом и
> относительный путь, из которого абсолютный собирается **только** для
> подписи. Смешение этих двух соглашений в одном поле даёт либо 404,
> либо `SIGNATURE_INVALID` на первом же запросе.

### 3.2. Пример

```
POST
/api/v1/launcher/license/check
1785500000
9f86d081884c7d659a2feaa0c55ad015
a1b2c3...  (SHA-256 тела)
```

### 3.3. Требования к nonce

- 16 байт из криптографического источника (`BCryptGenRandom`), **не** `rand()`.
- Уникален в пределах окна 5 минут. Практически — новый на каждый запрос.
- Повторный nonce с валидной подписью получает `403 REPLAY`.

### 3.4. Метка времени

Окно — 300 секунд в **обе стороны**. Часы клиента могут и отставать,
и спешить.

При `403 SIGNATURE_EXPIRED` загрузчик обязан однократно синхронизировать
время по заголовку `Date` из ответа сервера и повторить запрос. Второй
такой ответ подряд — показать пользователю «проверьте системное время».

### 3.5. Где лежит signing_secret

**ИСПРАВЛЕНО в ревизии 2.** В первой редакции здесь было сказано, что секрет
выдаётся при первом входе, а Приложение А одновременно требовало подписи
для `/auth/login`. Это замкнутый круг: подписать первый вход было нечем.
Ошибка спецификации, обнаружена при ревью реализации.

**Действующее правило: секрет один, и он один на сборку продукта.**

`signing_secret` — это секрет, соответствующий `X-Api-Key`. Он поставляется
вместе с загрузчиком и подписывает **все** запросы, включая вход. Отдельного
посессионного секрета нет.

Что чем занимается:

| Механизм | Что доказывает |
|---|---|
| Подпись запроса | запрос сформирован нашей сборкой и не воспроизведён |
| JWT | кто пользователь |
| HWID | на какой машине |

Третий секрет «на установку» не добавлял бы ни одного свойства сверх этих
и порождал бы проблему первого входа.

**Честная оговорка.** Секрет, лежащий в бинарнике, извлекаем — это данность,
а не недосмотр. Его задача не в стойкости к разбору клиента, а в том, чтобы
сервер отличал свою сборку от произвольного HTTP-клиента и мог отозвать
скомпрометированный ключ, не трогая остальных. Стойкость к анализу клиента
обеспечивается другими средствами и в этом документе не рассматривается.

В памяти секрет живёт минимальное время и затирается после использования;
на диск в открытом виде не пишется. Отзыв — через `api_keys.revoked_at`
на сервере, после чего сборка перестаёт обслуживаться и требует обновления.

## 4. HWID

### 4.1. Источник

Серийный номер накопителя, полученный через `DeviceIoControl` с
`IOCTL_STORAGE_QUERY_PROPERTY` (`StorageDeviceProperty`).

Берётся диск, на котором находится системный том.

**Не использовать** `GetVolumeInformation`: серийный номер тома слетает при
форматировании раздела и переустановке Windows, из-за чего пользователи
будут упираться в лимит сбросов, не меняя железо.

### 4.2. Нормализация

Перед отправкой Disk ID приводится к каноническому виду. Сервер делает
то же самое, но клиент обязан отправлять уже нормализованное значение —
это упрощает разбор инцидентов.

1. Убрать ведущие и хвостовые пробелы.
2. Убрать **все** внутренние пробельные символы.
3. Привести к верхнему регистру.

```
"  wd-wcc4n 1234567 \t"  →  "WD-WCC4N1234567"
```

Причина: в зависимости от контроллера и версии драйвера один и тот же диск
возвращает серийник с разным регистром и выравниванием пробелами. Без
нормализации та же машина после обновления драйвера считается новой.

### 4.3. Отказ чтения

Если Disk ID прочитать не удалось — **не подставлять запасной идентификатор**
(MAC-адрес, имя машины, GUID из реестра). Это создаёт вторую привязку
к тому же аккаунту и ломает учёт.

Правильное поведение: показать пользователю ошибку «не удалось определить
устройство» и предложить обратиться в поддержку.

## 5. Аутентификация

### 5.1. Вход

```
POST /api/v1/auth/login
```

```json
{
  "login": "user@example.com",
  "password": "…",
  "hwid": "WD-WCC4N1234567"
}
```

Ответ `200`:

```json
{
  "accessToken": "eyJhbGciOi…",
  "refreshToken": "rt_9f86d081…",
  "expiresIn": 900,
  "user": { "id": "019fb…", "username": "player", "locale": "ru" }
}
```

Ответ `200` при включённой 2FA — токенов **нет**:

```json
{
  "twoFactorRequired": true,
  "challengeToken": "ch_a1b2c3…",
  "expiresIn": 900
}
```

### 5.2. Второй фактор

```
POST /api/v1/auth/2fa/verify
```

```json
{ "challengeToken": "ch_a1b2c3…", "code": "123456" }
```

Ответ — та же пара токенов, что при обычном входе.

**Изменено в ревизии 2:** ранее здесь выдавался посессионный `signingSecret`.
Он отменён — подпись всегда идёт секретом API-ключа, см. 3.5.

### 5.3. Обновление токена

```
POST /api/v1/auth/refresh
```

```json
{ "refreshToken": "rt_9f86d081…" }
```

**Refresh-токены ротируются.** Каждое обновление выдаёт новую пару и гасит
предыдущий refresh. Из этого следуют жёсткие требования к клиенту:

- Новый refresh сохраняется **до** того, как старый будет использован повторно.
- Обновление выполняется **строго в одном потоке**. Два параллельных запроса
  с одним refresh — это предъявление уже потраченного токена, что сервер
  трактует как кражу и гасит **всю цепочку сессии**. Пользователь получит
  внезапный разлогин.
- Обновлять заранее, за 60 секунд до истечения `expiresIn`, а не по факту
  получения `401`.

### 5.4. Выход

```
POST /api/v1/auth/logout
```

Гасит текущую сессию. Локальные токены стираются независимо от кода ответа.

## 6. Проверка лицензии

```
POST /api/v1/launcher/license/check
```

```json
{
  "productSlug": "fc26",
  "hwid": "WD-WCC4N1234567",
  "clientVersion": "1.4.2"
}
```

Ответ `200`:

```json
{
  "status": "ACTIVE",
  "expiresAt": "2026-09-15T12:00:00.000Z",
  "productName": "FC 26",
  "planName": "30 дней",
  "update": {
    "available": true,
    "mandatory": false,
    "version": "1.5.0",
    "versionCode": 1005000
  },
  "notice": null
}
```

### 6.1. Реакция на статусы

| `code` в ошибке | HTTP | Что делает загрузчик |
|---|---|---|
| — (`status: ACTIVE`) | 200 | продолжает работу |
| `LICENSE_EXPIRED` | 403 | сообщение + ссылка на продление, работу не начинает |
| `LICENSE_BLOCKED` | 403 | сообщение «обратитесь в поддержку» |
| `LICENSE_REVOKED` | 403 | то же |
| `LICENSE_NOT_FOUND` | 404 | «нет лицензии на этот продукт» |
| `HWID_MISMATCH` | 403 | «лицензия привязана к другому устройству», кнопка сброса ведёт в личный кабинет |
| `UPDATE_REQUIRED` | 426 | принудительное обновление, работу не начинает |
| `RATE_LIMITED` | 429 | сообщение, без автоповтора |

### 6.2. Периодическая проверка — ОТСУТСТВУЕТ (ревизия 3)

**Решение владельца от 2026-08-02: периодической перепроверки нет.**

Ревизии 1 и 2 описывали здесь повтор проверки каждые `X-Recheck-After`
секунд. Живой прогон показал, что этого не происходит и произойти не может
в текущей архитектуре: загрузчик вставляет DLL и завершается, после чего
следить за лицензией уже некому. Выгрузить DLL из чужого процесса он не
может — это не его территория.

Развилка была такая, и она честная:

| Вариант | Цена |
|---|---|
| Ничего (**выбрано**) | забаненный аккаунт доигрывает сессию до конца |
| Загрузчик висит и убивает игру при отказе | сеть моргнула — честный игрок вылетел из матча |
| Загрузчик висит и только доносит на сервер | процесс живёт ради телеметрии, польза только для антифрода |

Выбран первый: **отзыв лицензии действует со следующего запуска.**

Практическое следствие, которое надо понимать: между баном и его
фактическим действием проходит одна игровая сессия. Для лицензионной
модели это приемлемо — человек уже заплатил за период, а отзыв обычно
означает шаринг или возврат средств, а не срочную угрозу.

Сервер по-прежнему считает и отдаёт `X-Recheck-After`: заголовок стоит
денег в ноль, а вернуть перепроверку без него было бы правкой обеих
сторон. `Session::Recheck()` в загрузчике реализован и проверен — он
просто никем не вызывается.

### 6.2.1. Поведение при недоступности сервера — СТРОГИЙ РЕЖИМ

**Офлайн-режим не предусмотрен.**

Нет связи с сервером — продукт не запускается. Никакого льготного периода,
никакого кэша последнего успешного ответа, никакой работы «по памяти».

Конкретно:

- Не удалось выполнить стартовую проверку — работа не начинается.
- Не удалось получить payload — работа не начинается.
- Результат проверки не кэшируется на диске **никогда**, ни в каком виде.

Заказчик осознаёт последствие: авария на сервере не даёт запуститься всем
пользователям одновременно. Уже запущенные при этом продолжают играть —
см. 6.2.

**Следствие для серверной части.** Раз клиенту льготный период не даётся,
устойчивость должна обеспечиваться на сервере, где ей можно управлять:

- горячий путь `/launcher/license/check` отвечает из кэша Redis и переживает
  кратковременную недоступность Postgres.
  **Не реализовано (разбор 2026-08-02).** `CHECK_CACHE_PREFIX` объявлен, ключ
  УДАЛЯЕТСЯ при отзыве и блокировке, но не записывается никогда — то есть
  `invalidate()` выглядит работающим и не работает. Пока это так, падение
  Postgres мгновенно останавливает запуск у всех, и заявленная тут
  устойчивость — обещание, а не свойство;
- эндпоинт проверки лицензии не делит пул соединений с админскими
  запросами, чтобы тяжёлый отчёт в админке не выбивал проверку лицензии;
- доступность этого эндпоинта мониторится отдельно от остального API.

Серверный кэш предпочтительнее клиентского льготного периода по простой
причине: клиентский кэш правится в памяти процесса за пять минут
и превращается в бессрочную лицензию, а серверный находится под вашим
контролем.

### 6.3. Поле `notice`

Строка либо `null`. Если не `null` — показать пользователю как уведомление.
Это замена push-канала: отдельного соединения загрузчик не держит,
поэтому адресные сообщения приходят ответом на очередную проверку.

## 7. Получение payload

Главный эндпоинт с точки зрения защиты. Payload **никогда не сохраняется
на диск** и не доступен пользователю.

```
POST /api/v1/launcher/payload
```

```json
{
  "productSlug": "fc26",
  "hwid": "WD-WCC4N1234567",
  "sessionKey": "<32 случайных байта в hex>"
}
```

`sessionKey` — ровно 64 символа hex **нижнего регистра**. Верхний регистр
отвергается на входе: одно представление — одно правило на C++.

Ответ `200`, `Content-Type: application/octet-stream`:

| Заголовок | Смысл |
|---|---|
| `X-Payload-Sha256` | SHA-256 **расшифрованного** содержимого, 64 hex нижнего регистра |
| `X-Payload-Size` | размер расшифрованного содержимого в байтах, десятичное без ведущих нулей |
| `X-Payload-Nonce` | 12 байт IV в hex (24 символа) |
| `X-Payload-Tag` | 16 байт GCM-тега в hex (32 символа) |
| `X-Payload-Version` | номер сборки payload'а — попадает в отчёт по §9 |
| `Cache-Control` | `no-store` |

Тело — шифротекст той же длины, что открытый текст: GCM потоковый, тег
уходит отдельным заголовком и **к телу не приклеивается**.

#### Схема шифрования (ревизия 3)

```
key  = HKDF-SHA256(ikm = sessionKey (32 байта),
                   salt = IV (12 байт, из X-Payload-Nonce),
                   info = ASCII "lp/payload/v1",
                   L    = 32)

AAD  = "lp/payload/v1" \n productSlug \n X-Payload-Sha256
                       \n X-Payload-Size \n X-Payload-Version

тело = AES-256-GCM(key, IV, AAD, открытый текст)
```

- Поля AAD разделены **одним** `0x0A`, завершающего перевода строки **нет** —
  тот же канон, что у подписи запроса (§3.1).
- **Каждый** заголовок `X-Payload-*` покрыт тегом, кроме `Nonce` и `Tag`:
  их GCM связывает сам. Значит подмена дайджеста посредником даёт честный
  провал тега, а не «повреждённые данные» с тикетом в поддержку.
- Значения заголовков перед сборкой AAD обрезаются **с обеих сторон**.
  Промежуточный узел, добавивший пробел, обязан ломать расшифровку
  предсказуемо, а не через раз.
- Соль — серверный IV. Клиент, нарушивший §7.2.1 и переиспользовавший
  `sessionKey`, не может вызвать повтор пары (ключ, IV): IV генерирует
  сервер. Это не делает переиспользование безопасным — оно остаётся
  дефектом клиента и ловится кодом `SESSION_KEY_REUSED`.

Контрольные векторы, посчитанные серверной реализацией, —
[PAYLOAD-VECTORS.md](PAYLOAD-VECTORS.md). Реализация на C++ обязана давать
те же байты. Пока вектор не сошёлся, писать интеграцию бессмысленно:
расхождение KDF или AAD проявляется **исключительно** как провал тега,
то есть без единого признака, по которому можно понять, что именно разошлось.

### 7.1. Требования к серверу

- Лицензия и HWID проверяются **на каждый запрос**, а не один раз при входе.
- Ответ не кэшируется ничем: ни CDN, ни прокси, ни клиентом.
- Ссылки на объектное хранилище (presigned URL) **не используются**:
  такую ссылку можно переиспользовать и скачать браузером, что обесценивает
  всю схему.
- Каждый ответ шифруется эфемерным ключом, производным от `sessionKey`
  клиента. Перехваченный ответ невозможно расшифровать без сессии,
  а повторно запросить — без валидной подписи и лицензии.

### 7.2. Требования к клиенту

1. `sessionKey` генерируется **на каждый запрос** заново через
   `BCryptGenRandom`. Переиспользование сводит на нет весь смысл схемы.
2. Тело расшифровывается в памяти AES-256-GCM. **Проверка тега
   обязательна** — при несовпадении содержимое отбрасывается целиком.
3. Считается SHA-256 расшифрованного содержимого и сравнивается
   с `X-Payload-Sha256`. Несовпадение — прекратить работу, отправить
   отчёт (раздел 9), показать «повреждённые данные».
4. Расшифрованный буфер **не записывается на диск ни при каких условиях**:
   ни во временные файлы, ни в дампы, ни в логи.
5. После использования буфер затирается нулями и освобождается.
6. Процесс должен исключать себя из создания дампов памяти
   (`WerRegisterExcludedMemoryBlock` для буфера payload'а).

### 7.3. Коды ошибок

**Ревизия 3.** Таблица приведена к тому, что сервер отдаёт на самом деле.
В ревизии 2 здесь стоял обобщённый `LICENSE_INVALID`; реализация различает
причины, потому что клиенту на каждую нужно своё действие, а слепить их в
один код значит показать пользователю «лицензия недействительна» там, где
достаточно было сказать «сначала запустите проверку».

Реализованные коды — `apps/api/src/modules/launcher/payload.service.ts`,
`launcher.service.ts`, `guards/api-scope.guard.ts`.

| `code` | HTTP | Значение | Что делает загрузчик |
|---|---|---|---|
| `SIGNATURE_MISSING` / `SIGNATURE_INVALID` / `SIGNATURE_EXPIRED` / `REPLAY` | 403 | подпись запроса (§3) | как в §3.4 |
| `API_KEY_SCOPE` | 403 | ключу сборки не выдан scope `launcher:payload` | остановиться, это дефект сборки |
| `LICENSE_EXPIRED` | 403 | срок вышел | ссылка на продление |
| `LICENSE_BLOCKED` | 403 | заблокирована | «обратитесь в поддержку» |
| `LICENSE_REVOKED` | 403 | отозвана | стереть секреты, повторный вход |
| `LICENSE_NOT_BOUND` | 403 | привязки нет | вызвать `/launcher/license/check` и повторить |
| `LICENSE_NOT_ACTIVATED` | 403 | привязка есть, но лицензия так и не активирована | вызвать `/launcher/license/check` и повторить |
| `HWID_MISMATCH` | 403 | привязка не совпадает | стереть секреты, предложить сброс |
| `DEVICE_BLOCKED` | 403 | устройство заблокировано | «обратитесь в поддержку» |
| `PRODUCT_NOT_FOUND` | 404 | нет такого продукта | остановиться, это дефект сборки |
| `LICENSE_NOT_FOUND` | 404 | лицензии на продукт нет | ссылка на покупку |
| `SESSION_KEY_REUSED` | 400 | `sessionKey` уже использовался | **дефект клиента**: ключ обязан быть новым на каждый запрос (§7.2.1) |
| `PAYLOAD_NOT_READY` | 409 | сборка не опубликована | повторить с задержкой |
| `UPDATE_REQUIRED` | 426 | версия ниже минимально допустимой | обновиться |
| `RATE_LIMITED` | 429 | превышен лимит выдач | ждать `Retry-After` |
| `SERVICE_UNAVAILABLE` | 503 | сервер сбрасывает нагрузку | повтор по §2.3 с `Retry-After` |
| `PAYLOAD_UNAVAILABLE` / `STORAGE_UNAVAILABLE` | 503 | авария на стороне сервера | повтор по §2.3 с `Retry-After` |
| `PAYLOAD_CORRUPT` | 503 | байты в хранилище разошлись с эталоном | повтор по §2.3; чинит человек |
| `ISSUE_NOT_RECORDED` | 503 | не записался журнал выдачи | повтор по §2.3 |

Три правила, без которых таблица не работает:

1. **Ветвиться только по `code`.** `message` локализован и меняется.
2. **`LICENSE_NOT_BOUND` и `LICENSE_NOT_ACTIVATED` — это не `HWID_MISMATCH`.**
   На `HWID_MISMATCH` загрузчик стирает сохранённые секреты и предлагает
   сброс привязки; для «просто ещё не вызвали `license/check`» это ложный
   совет, который отправит человека в поддержку на ровном месте.
3. **Все 503 повторяемы, все 4xx кроме 429 — нет.** `Retry-After` приходит
   на каждом 503 и на 429; уважать его обязательно, иначе повторы удваивают
   нагрузку ровно в тот момент, когда сервер её сбрасывает.

> `SESSION_KEY_REUSED` стоит здесь не против противника — тот тривиально
> рандомизирует ключ. Он ловит **нашу** ошибку: если в сборке загрузчика
> `sessionKey` окажется статическим (забыли вызвать `BCryptGenRandom`,
> закешировали, отладочная константа уехала в релиз), один перехваченный
> ключ расшифрует все будущие ответы этой сборки. Без этой проверки всё
> продолжает работать и никто ничего не замечает.

## 8. Обновление загрузчика

**Это другой поток, чем раздел 7, и путать их нельзя.** Здесь речь про
исполняемый файл самого загрузчика: он лежит на диске, пользователь его
запускает, и он вполне может отдаваться через CDN.

```
GET /api/v1/launcher/update?productSlug=fc26&versionCode=1004002
```

Ответ `200`:

```json
{
  "available": true,
  "mandatory": true,
  "version": "1.5.0",
  "versionCode": 1005000,
  "downloadUrl": "https://cdn.example.com/releases/launcher-1.5.0.exe",
  "sha256": "a1b2c3…",
  "size": 8421376,
  "changelog": "## 1.5.0\n\n- …"
}
```

Порядок действий клиента:

1. Скачать файл по `downloadUrl` во временный каталог.
2. Посчитать SHA-256 и сравнить с `sha256`. **Не совпало — удалить файл
   и прервать обновление.** Это единственная защита от подмены на CDN.
3. Проверить цифровую подпись исполняемого файла (Authenticode).
4. Запустить установку, завершить текущий процесс.

При `mandatory: true` работа без обновления не продолжается.

`versionCode` вычисляется как `major * 1_000_000 + minor * 1_000 + patch`.
Сравнивать нужно **его**, а не строку версии: `"1.10.0" > "1.9.0"`
лексикографически ложно.

## 9. Отправка логов и отчётов

```
POST /api/v1/launcher/logs
```

```json
{
  "kind": "crash",
  "clientVersion": "1.4.2",
  "summary": "integrity check failed after payload decrypt",
  "payload": "<текст лога, до 256 КБ>"
}
```

`kind`: `crash` | `error` | `diagnostic` | `user_report`.

### 9.1. Что нельзя класть в логи

Требование жёсткое, потому что логи хранятся и просматриваются людьми:

- пароли, токены, `signingSecret` — ни в каком виде;
- содержимое payload'а или его фрагменты;
- Disk ID в открытом виде — только признак «прочитан / не прочитан»;
- персональные данные, не относящиеся к инциденту.

### 9.2. Ограничения

- Не чаще одного отчёта в 60 секунд.
- Не более 256 КБ на отчёт.
- При недоступности сервера — не копить неограниченно, максимум 10 отчётов
  в памяти, старые вытесняются.

## 10. Хранение данных на клиенте

| Что | Где | Как |
|---|---|---|
| `accessToken` | только в памяти | не сохраняется никогда |
| `refreshToken` | DPAPI, привязка к пользователю | `CryptProtectData` |
| `signingSecret` | DPAPI, привязка к пользователю | там же |
| Логин пользователя | реестр или файл настроек | открытым текстом допустимо |
| Пароль | **нигде** | не сохраняется ни при каких «запомнить меня» |
| Состояние лицензии | **нигде** | всегда спрашивается у сервера |

При выходе и при получении `LICENSE_REVOKED` или `HWID_MISMATCH` все
сохранённые секреты стираются.

## 11. Чего загрузчик делать не должен

Список составлен по типовым ошибкам, каждая из которых уже встречалась
в подобных проектах:

1. **Кэшировать результат проверки лицензии дольше `X-Recheck-After`.**
   Локальный кэш — первое, что правится в памяти.
2. **Принимать решения о валидности самостоятельно.** Любая клиентская
   проверка обходится; сервер должен получать запрос и отвечать.
3. **Сохранять payload на диск** — даже во временный файл, даже на секунду.
4. **Подставлять запасной HWID** при неудачном чтении Disk ID.
5. **Повторять запрос с теми же nonce и timestamp.**
6. **Обновлять токен из нескольких потоков одновременно.**
7. **Показывать пользователю технические подробности ошибки** сверх
   `message` и `requestId`: коды и внутренние детали помогают тому,
   кто изучает защиту.
8. **Игнорировать несовпадение SHA-256** «потому что и так работает».

## 12. Открытые вопросы

Закрытые:

- ~~Поведение при недоступности сервера~~ — **строгий режим**, офлайн
  не предусмотрен (раздел 6.2.1).
- ~~Нужен ли офлайн-режим для каких-либо тарифов~~ — **нет**, ни для каких.
- ~~Периодическая перепроверка лицензии~~ — **её нет** (раздел 6.2,
  решение владельца от 2026-08-02). Отзыв действует со следующего запуска;
  запущенная сессия доигрывается до конца. Альтернативы — убивать игру или
  держать процесс ради телеметрии — отвергнуты осознанно.

- ~~Размер payload'а~~ — **около 600 КБ сейчас, потолок 3 МБ.**

  Следствия зафиксированы: потоковая расшифровка не нужна, буфера целиком
  достаточно и на клиенте, и на сервере. Лимит на тело ответа эндпоинта
  payload — **8 МБ**: запас над потолком, но не настолько большой, чтобы
  ошибка на сервере могла съесть память процесса. Лимит на JSON-ответы
  остаётся отдельным и составляет 2 МБ.

Требуют решения до соответствующего этапа:

1. **Интервал периодической проверки.** Определяет TTL кэша лицензии
   в Redis на сервере и нагрузку на запись. Ориентир — 300 секунд.
   При строгом режиме интервал напрямую задаёт, через сколько после
   аварии остановятся пользователи.
