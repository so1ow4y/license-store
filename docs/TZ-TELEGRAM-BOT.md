## 0. Восемь решений, из которых выведено всё остальное

| № | Решение | Почему именно так |
|---|---|---|
| **0.1** | Бот — **модуль внутри API** (`apps/api/src/modules/telegram-bot/`), а не отдельный сервис | Разом снимает три проблемы, каждая из которых по отдельности ломает бота: (1) API умеет только JWT Bearer, значит отдельный сервис обязан хранить пару токенов на каждого пользователя, а refresh одноразовый — два сообщения подряд в чате предъявят его дважды, получат `TOKEN_REUSED` и погасят сессию; (2) лимит Digiseller `attempts_per_ip_per_hour = 60`, а у внешнего бота IP один на всю аудиторию — 60 чужих неудач в час выключают активацию для всех; (3) `security.2fa.required_for_admin = true`, и внешний бот был бы вынужден спрашивать TOTP в чат. Внутри процесса бот собирает `AuthenticatedUser` сам, из БД, и зовёт сервисы напрямую — HTTP-слой и его гварды не участвуют. |
| **0.2** | Привязка чата — **одноразовый deep-link-токен, выданный в личном кабинете за уже аутентифицированной сессией**. Направление строго сайт → бот | `POST /auth/telegram/callback` (Login Widget) для этого не годится по четырём независимым причинам, разобранным в §3.1. Коротко: подпись виджета выводится из токена бота, то есть подписывающий и проверяющий — одно лицо; в апдейте от Telegram нет ни `hash`, ни `auth_date`; Telegram не отдаёт почту, поэтому `resolveLogin` уйдёт в «создать новый аккаунт» и у человека появится второй пустой аккаунт на первом же пользователе; и на выходе получается сессия, а не связь «по `telegram_user_id` найди, кому написать». |
| **0.3** | Бот **никогда не печатает полный ключ лицензии по своей инициативе**. Везде маска `FC26-****-****-****-9F3A` | Ключ — предъявительский секрет: загрузчик больше не спрашивает логин с паролем, ключ и есть всё право на запуск. Переписка Telegram хранится в облаке и на всех устройствах владельца аккаунта бессрочно, и владелец Telegram-аккаунта может смениться без нашего ведома (перевыпуск номера, SIM-swap). Значит: всё, что бот когда-либо написал, рано или поздно прочитает посторонний. |
| **0.4** | Бот **не принимает в переписке ни одного долгоживущего секрета**: пароль, TOTP-secret, коды восстановления, секрет подписи API-ключа | Помимо оседания в облаке — это тренирует аудиторию вводить пароль от pxcheats боту. Завтра появится `@pxcheats_support_bot`, и мы своими руками создали фишинговый рынок. Одноразовые коды (Digiseller, регистрационный ключ) принимать можно: они гасятся при использовании, но сообщение с ними бот всё равно удаляет. |
| **0.5** | «Продление» через бота **не продлевает лицензию, а создаёт новую** — и бот обязан сказать это прямым текстом | Факт из кода: `digiseller.redeem` → `licenses.issue` → всегда новая запись `License` (новый ключ, статус `PENDING`, `expiresAt = null`, собственный счётчик HWID). `POST /licenses/:id/extend` требует права `licenses.extend`, которого у роли `user` нет (`seed.ts:187`). Пока это не изменено на сервере, обещать продление — врать. |
| **0.6** | Бот — **второй канал, а не единственный**. Он никогда не должен стать последним способом достучаться до аккаунта | Любой канал восстановления доступа настолько же надёжен, насколько надёжен самый простой путь в него. Если бота можно получить, не имея почты и пароля, то бот — и есть самый простой путь. Отсюда: привязка только с сайта; при `register-with-key` из чата — обязательное предупреждение; отвязка последнего способа входа блокируется (`409 LAST_LOGIN_METHOD`). |
| **0.7** | Приём апдейтов — **webhook**, не long polling | Long polling требует постоянно живущего исходящего соединения из процесса API и плохо переживает несколько реплик (апдейт получит случайная). Webhook — обычный HTTP-эндпоинт, масштабируется тем же способом, что и остальной API, и не требует отдельного жизненного цикла. Цена — публичный URL и секрет; и то и другое у нас уже есть (HTTPS с сертификатом). |
| **0.8** | Telegram как **канал уведомлений** реализуется внутри уже существующей подсистемы `Notification`, а не отдельным механизмом | В схеме уже есть `NotificationChannel.TELEGRAM`, таблица-очередь, процессор с ретраями, шаблоны с локалями. Не хватает ровно двух вещей: разрешения получателя (`notification.service.ts:175-177` возвращает `null` → `enqueue` молча пропускает уведомление) и ветки отправки (`notification.processor.ts:137-139` бросает «канал ещё не реализован»). Делать параллельный механизм — значит завести второй источник правды по доставке. |

### 1.5 Где бот честно удобнее сайта

1. **Нет входа.** Привязка делается один раз, дальше стоимость обращения — ноль. Сайт требует логин или OAuth минимум раз в 30 дней (refresh TTL = 2 592 000 с).
2. **Push вместо pull.** Истечение срока, выдача, отзыв приходят сами. Сайт не умеет сообщить ничего, пока человек не зайдёт.
3. **Сброс HWID в момент паники.** Загрузчик не запустился — телефон в руке быстрее браузера. Сегодняшний путь: вспомнить про сайт → вспомнить логин → вспомнить пароль или идти в почту за сбросом → найти лицензию → найти кнопку.
4. **Поддержка с адресом.** У сообщения в боте уже есть привязанный аккаунт и список лицензий. Формы «связаться с поддержкой» на сайте нет вовсе.
5. **Двухшаговое подтверждение необратимого.** Сброс расходует 1 из 3 навсегда. В чате естественно показать «останется 2» и ждать явного тапа.

## 2. Архитектура

### 2.1 Расположение

Бот — модуль NestJS внутри существующего приложения API. Обоснование — решение 0.1. Развёртывание, миграции, логи, метрики, Redis, Postgres — те же, что у API. Отдельного процесса, отдельного репозитория, отдельного деплоя нет.

```
apps/api/src/modules/telegram-bot/
  telegram-bot.module.ts
  telegram-webhook.controller.ts   // приём апдейтов, @Public()
  telegram.api.ts                  // исходящие вызовы Bot API
  telegram-update.processor.ts     // разбор апдейта, маршрутизация
  bot-actor.service.ts             // telegram_user_id → AuthenticatedUser
  bot-state.service.ts             // FSM диалога в Redis
  bot-link.service.ts              // выпуск/гашение кодов, привязка, отвязка
  bot-notify.service.ts            // отправка уведомлений (вызывается процессором Notification)
  bot-support.service.ts           // треды поддержки
  screens/
    root.screen.ts  licenses.screen.ts  hwid.screen.ts
    activate.screen.ts  account.screen.ts  admin.screen.ts  support.screen.ts
  i18n/
    ru.ts  en.ts  index.ts
  dto/  guards/
```

### 2.2 Общение с API платформы

**Бот не ходит в собственный HTTP-API.** Он вызывает сервисы напрямую: `LicensesService`, `HwidService`, `DigisellerService`, `AuthService`, `ProductsService`, `RegistrationKeyService`.

Почему это не «нарушение слоёв», а осознанный выбор:

- **Глобальный `JwtAuthGuard`** — единственный механизм аутентификации пользовательского API. `@Public()` стоит только на каталоге, регистрации/входе и `/launcher/*`. Механизм `ApiKey` + `SignatureGuard` + `ApiScopeGuard` живёт **исключительно внутри модуля launcher** (`modules/launcher/guards/`), его scope'ы — `launcher:payload`, `launcher:update`, и в `/licenses`, `/billing`, `/auth` его никто не читает. То есть у бота, ходящего снаружи, нет ни одного варианта, кроме пары JWT на каждого пользователя.
- Пара JWT на пользователя означает: refresh одноразовый, повторное предъявление → `TOKEN_REUSED` и гашение всей сессии (`auth.controller.ts:132-134`). Обновление токена пришлось бы сериализовать мьютексом на пользователя. Ломается это тихо и массово: два быстрых тапа в чате — и человека выкинуло.
- Кроме того `JwtAuthGuard` кэширует права в Redis на 300 с, то есть блокировка пользователя доходила бы до бота с задержкой до 5 минут.

Прямой вызов сервисов снимает всё это разом. Взамен появляется обязанность собрать `AuthenticatedUser` корректно — этим занят `BotActorService` (§2.5).

Единственное исключение: **`GET /products` бот тоже зовёт сервисом**, не HTTP — просто для единообразия.

### 2.3 Приём апдейтов: вебхук

```
POST /api/v1/telegram/webhook/:secret
```

- Контроллер помечен `@Public()` — JWT здесь неоткуда взяться.
- `:secret` — значение `TELEGRAM_WEBHOOK_SECRET` **[НОВОЕ ENV]**, 32 байта CSPRNG в base64url. Это **не токен бота**. Путь с секретом нужен, чтобы отсечь мусорный трафик до разбора тела.
- Дополнительно проверяется заголовок `X-Telegram-Bot-Api-Secret-Token` (задаётся при `setWebhook` параметром `secret_token`). Два независимых проверяемых значения: путь защищает от сканеров, заголовок — от утечки URL из логов реверс-прокси.
- Сравнение обоих значений — **константное по времени** (`crypto.timingSafeEqual`). Расхождение → `404`, не `403`: `403` подтверждает существование эндпоинта.
- Ответ **всегда `200 OK`, всегда в пределах 1 секунды**, тело пустое. Никакой полезной работы в обработчике запроса нет: апдейт кладётся в очередь и обрабатывается асинхронно. Telegram при таймауте ретраит апдейт и при систематических таймаутах снижает частоту доставки.
- **Идемпотентность обязательна.** Ключ — `update_id`. `SET NX tg:upd:<update_id> 1 EX 3600` в Redis; если ключ уже есть — апдейт молча отбрасывается. Без этого один ретрай Telegram может выполнить сброс HWID дважды.
- Разрешённые типы апдейтов ограничиваются при `setWebhook`: `allowed_updates: ["message", "callback_query", "my_chat_member"]`. Всё остальное Telegram даже не пришлёт.

**Регистрация вебхука** — разовая административная операция, выполняется скриптом при развёртывании, а не автоматически при старте процесса (иначе каждая реплика при рестарте будет перерегистрировать вебхук):

```
POST https://api.telegram.org/bot<TOKEN>/setWebhook
{
  "url": "https://pxcheats.com/api/v1/telegram/webhook/<TELEGRAM_WEBHOOK_SECRET>",
  "secret_token": "<TELEGRAM_WEBHOOK_SECRET>",
  "allowed_updates": ["message", "callback_query", "my_chat_member"],
  "max_connections": 40,
  "drop_pending_updates": true
}
```

`drop_pending_updates: true` при первой установке — чтобы накопившийся за время без вебхука мусор не обрушился на свежий обработчик.

### 2.4 Очередь обработки

Апдейты обрабатываются через тот же механизм, что и уведомления, — таблицу-очередь с `@Interval` и блокировкой в Redis (`notification.processor.ts:37-113`), либо через отдельный Redis-список. **[РЕШЕНИЕ ВЛАДЕЛЬЦА]** — какой из двух.

Аргумент за Redis-список: апдейты живут секунды, их не надо хранить, и таблица в Postgres будет расти мусором. Аргумент за таблицу: механизм уже написан, отлажен, имеет ретраи до 5 попыток и переживает рестарт процесса. **Рекомендация: Redis-список с TTL, потому что потерянный апдейт Telegram пришлёт повторно сам, а вот потерянное уведомление не пришлёт никто.**

Порядок обработки внутри одного чата **сериализуется**: `SET NX tg:chat-lock:<chatId>` на время обработки, TTL 10 с. Причина: пользователь может нажать «Подтвердить сброс» дважды за 200 мс, и без блокировки два обработчика прочитают одинаковое состояние FSM.

### 2.5 `BotActorService` — превращение чата в актора

```
resolve(telegramUserId: bigint): Promise<BotActor | null>
```

Шаги:

1. Найти `TelegramLink` по `telegramUserId`, где `revokedAt IS NULL`. Нет записи → `null`, бот работает в режиме «не привязан».
2. Проверить срок: `expiresAt` в прошлом → привязка считается истёкшей, бот предлагает перепривязаться (§3.6).
3. Загрузить `User` по `userId`. Если `deletedAt` не null или `status` ∈ {`BLOCKED`, `DELETED`} → возвращается актор со специальным флагом `blocked`; бот отвечает `msg.account_blocked` и закрывает все команды, кроме `/help` и `/support`.
4. Собрать права **тем же кодом, что и `JwtAuthGuard`** (роль → permissions). Дублировать логику нельзя: разойдётся при первой правке ролей.
5. Кэш в Redis: `tg:actor:<userId>`, **TTL 60 секунд**.

Почему 60, а не 300 как у JWT: у JWT есть собственный TTL 900 с, который естественно ограничивает лаг блокировки. У бота такого ограничителя нет вовсе — привязка живёт 90 дней. Если оставить 300 с, заблокированный пользователь ещё пять минут пользуется ботом. 60 с — компромисс между нагрузкой на БД и лагом. Дополнительно: **при блокировке пользователя ключ `tg:actor:<userId>` инвалидируется явно** — это делает бот-модуль, подписавшись на то же место кода, где выставляется `status = BLOCKED`.

### 2.6 Исходящие вызовы Bot API

`TelegramApiService`. Правила:

- Базовый URL `https://api.telegram.org/bot<TOKEN>/<method>`. Токен читается из `TELEGRAM_BOT_TOKEN` (уже объявлен в `env.schema.ts:227`) — **один источник правды, ENV**. Настройки в БД `telegram.bot_token` / `telegram.bot_username` / `telegram.admin_chat_id` (`seed.ts:329-331`) сегодня **не читаются никаким кодом**; их нужно либо задействовать, либо удалить из сида — см. §8-С8.
- Таймаут запроса — 10 с, ретраи только для сетевых ошибок и `5xx`, до 3 попыток с экспоненциальной паузой (1 с, 3 с, 9 с).
- **`429 Too Many Requests`**: читается `parameters.retry_after`, задача откладывается ровно на столько секунд. Свой лимитер: **не более 25 сообщений в секунду суммарно** и **не более 1 сообщения в секунду в один чат** — это ниже документированных лимитов Telegram (30/с и ~1/с), запас нужен, потому что лимит считается на стороне Telegram и мы не видим его состояния.
- **`403 Forbidden: bot was blocked by the user`**: выставляется `TelegramLink.chatBlocked = true`, все дальнейшие уведомления в этот чат **пропускаются без попытки отправки** (иначе очередь будет вечно долбиться в стену и жечь лимит). Флаг снимается автоматически при любом входящем апдейте от этого пользователя.
- **`400 Bad Request: chat not found`** — привязка помечается `revokedAt = now()`, на почту уходит письмо о разрыве.
- Все тексты отправляются с `parse_mode: "HTML"`, потому что HTML в Telegram не требует экранирования такого количества символов, как MarkdownV2, и `<code>` даёт копирование по тапу. **Любая подстановка пользовательских данных (username, название продукта, текст ошибки) проходит через `escapeHtml`.** Забыть один раз — значит получить сломанную вёрстку и потенциально инъекцию разметки от имени бота.
- `disable_web_page_preview: true` по умолчанию — иначе каждая ссылка на pxcheats.com разворачивается в карточку и занимает пол-экрана.

### 2.8 Если бот всё-таки будет отдельным сервисом

Вариант хуже по всем трём пунктам из 0.1, но если владелец выберет его **[РЕШЕНИЕ ВЛАДЕЛЬЦА]**, обязательны:

1. **Мьютекс на обновление токена, на каждого пользователя.** `SET NX tg:refresh:<userId> EX 30`. Без него два сообщения подряд предъявят один refresh дважды → `TOKEN_REUSED` → погашена вся сессия.
2. **Refresh хранится только зашифрованным** (AES-256-GCM, ключ в ENV/секрет-менеджере, не в той же БД). Access — только в памяти процесса, никогда на диск.
3. **Digiseller через бота выключается** либо на сервере появляется отдельная ось лимита для сервисного источника (§8-С2).
4. Честная оговорка, которую надо проговорить владельцу вслух: **компрометация БД такого бота = доступ к аккаунтам всех привязанных пользователей.** Это неустранимо, пока API не умеет сервисный путь. Смягчается только конечным сроком привязки.

## 3. Привязка аккаунта

Это основа всего: неверная привязка обесценивает и разграничение прав, и защиту ключей.

### 3.1 Почему не Telegram Login Widget

`POST /api/v1/auth/telegram/callback` существует и работает **[ЕСТЬ]** (`auth.controller.ts:237`, `oauth/telegram.provider.ts`, тесты `test/telegram.provider.spec.ts`, `smoke-oauth.ps1:88-121`). Для бота он не годится:

1. **Подпись ничего не доказывает.** Секрет проверки — `SHA256(bot_token)` (`telegram.provider.ts:53-58`). Токен бота есть у того самого сервиса, который будет звать эндпоинт. Подписывающий и проверяющий — одно лицо. Бот может подписать любой `id`, и проверка выродится в тождество.
2. **Нечего подписывать.** В `update.message.from` нет полей `hash` и `auth_date` — они бывают только у виджета. Бот может их только выдумать, см. п.1.
3. **Плодит дубли аккаунтов.** `resolveLogin` умеет автопривязку по подтверждённой почте, но Telegram почту не отдаёт (`profile.email = null`). Значит человек с существующим аккаунтом уходит в `createFromProfile` (`oauth.service.ts:229`) и получает **второй аккаунт** вида `grigorij_1` с `passwordHash: null`. Лицензия на старом, бот показывает новый и пустой. Это произойдёт на первом же пользователе, а не в редком случае.
4. **Выдаёт сессию, а не связь.** На выходе — пара токенов. А нужна запись «по `telegram_user_id` найди, кому написать».
5. **Нельзя отозвать, не сломав вход.** `DELETE /auth/oauth/TELEGRAM` вернёт `409 LAST_LOGIN_METHOD`, если Telegram — единственный способ войти. Пользователь оказывается в ловушке «либо бот, либо аккаунт».
6. **Привязка получается неявной и вечной.** Любой, кто завтра получит контроль над этим Telegram-аккаунтом, автоматически становится владельцем и чата, и входа на сайт. Нет отдельной сущности со сроком, которую можно отозвать.

Отдельно, важное для §6: `provider_user_id` из `oauth_accounts` для тех, кто входил виджетом, **численно совпадает** с `chat_id` личной переписки. То есть адрес доставки формально уже лежит в БД. Но **написать в личку нельзя, пока человек сам не нажал `/start`** — это ограничение Telegram, а не проекта. Виджет даёт идентификатор, но не даёт права писать. Собственная привязка нужна в любом случае.

### 3.2 Почему не пароль в чате

- Пароль — многоразовый секрет от всего аккаунта. Попав в переписку, он остаётся в облаке Telegram, в локальных БД клиента на всех устройствах, в бэкапах телефона, в пуш-уведомлении на локскрине и хотя бы на миг в памяти и потенциально логах бота.
- Тренирует пользователя вводить пароль от pxcheats боту → создаёт фишинговый рынок.
- На аккаунтах с 2FA бот вынужден спрашивать TOTP в чат, то есть становится обходом второго фактора. У админов 2FA обязательна (`security.2fa.required_for_admin = true`).
- Аккаунты, созданные через `POST /auth/register-with-key`, **пароля вообще не имеют** — механизм на них не работает в принципе.

### 3.3 Почему не короткий цифровой код

Шесть цифр = 10⁶ пространство. Работает, но: нужен строгий счётчик попыток **именно на аккаунт**, а не только на чат — иначе перебор распараллеливается по чатам; код всё равно оседает в переписке; UX не лучше ссылки. Та же цена, меньше энтропии — смысла нет.

### 3.4 Выбранная схема

**Одноразовый непредъявительский токен, выдаваемый в личном кабинете за уже аутентифицированной сессией, доставляемый через deep link. Направление привязки — строго сайт → бот.**

Шаги:

1. В ЛК кнопка «Подключить Telegram».
2. **Если на аккаунте включена 2FA — требуется свежий step-up: ввод TOTP не старше 5 минут, до выдачи токена.** Иначе бот становится способом читать лицензии и сбрасывать HWID в обход второго фактора, ради которого его и включали.
3. Сервер выпускает `link_token`: **32 байта CSPRNG → base64url = 43 символа**. Это влезает в лимит 64 символа для `start`-payload Telegram, запас 21 символ.
4. В БД хранится **только SHA-256 от токена** (`TelegramLinkCode.codeHash`), рядом — `userId`, `scope`, `expiresAt = now + 600 с`, `usedAt = null`, `createdIp`. Сам токен не хранится: утечка дампа не должна давать возможность привязать чужой чат.
5. Сайт показывает кнопку `https://t.me/pxcheats_bot?start=<token>` и её же текстом (для мобильных, где кнопка иногда не срабатывает).
6. Пользователь жмёт → в чат уходит `/start <token>`.
7. Бот берёт `update.message.from.id`, зовёт `BotLinkService.confirm(token, from, chat)`. Сервер **атомарно** гасит код:
   ```sql
   UPDATE telegram_link_codes
      SET used_at = now()
    WHERE code_hash = $1 AND used_at IS NULL AND expires_at > now()
   RETURNING user_id, scope
   ```
   Ноль строк → код неверен, использован или протух; бот отвечает одним и тем же текстом на все три случая (различать их — значит давать оракул).
8. Создаётся `TelegramLink`.
9. **На почту уходит письмо** «Telegram подключён к вашему аккаунту, чат id …, если это не вы — вот ссылка на отзыв». Почта — независимый от Telegram канал; это единственный способ узнать о тихом захвате.
10. Бот **немедленно удаляет входящее сообщение `/start <token>`** (`deleteMessage`). Токен уже погашен и бесполезен, но не оставлять его в истории дешевле, чем объяснять.

Токен виден в истории чата как текст `/start …` до момента удаления. Это осознанно допустимо: он одноразовый, живёт 10 минут, после гашения бесполезен.

**Состояние диалога (FSM) — не в БД, а в Redis:** `tg:state:<chatId>` → JSON, TTL равен TTL состояния (§5.0). Причина: состояние обязано протухать само, и его потеря не должна быть аварией. Состояние в БД пришлось бы чистить кроном и оно бы переживало рестарт дольше, чем нужно человеку.

`BigInt` для `telegramUserId` и `chatId` — обязательно. Telegram уже выдаёт id за пределами 2³¹, и в перспективе выйдет за 2⁵³; `Number` в JS сломается молча.

### 3.6 Правила связки

| Правило | Обоснование |
|---|---|
| **Один `telegram_user_id` → максимум один аккаунт** (`@unique`) | Иначе один чат становится пультом для фермы аккаунтов. |
| **Один аккаунт → максимум один чат** (`userId @unique`) | Иначе один аккаунт превращается в рассылку на N чатов, и отзыв доступа перестаёт быть однозначной операцией. |
| Новая привязка **вытесняет старую**: старая помечается `revokedAt`, в старый чат уходит прощальное сообщение, на почту — письмо | Тихая замена привязки — идеальный способ угона. Оба канала должны узнать. |
| **Только приватный чат**, `chat.type == "private"` и `chat.id == from.id` | В группе `from.id ≠ chat.id`, и ответ бота увидят все. При апдейте `my_chat_member` о добавлении в группу — `leaveChat` без сообщений. |
| Идентификатор — **только числовой `telegram_user_id`** | `@username` меняется в один клик и не является идентификатором ни при каких условиях. Хранится только как кэш для показа админу. |
| **Срок привязки USER — 90 дней**, дальше требуется повторное подтверждение с сайта | Молча продлевать «раз он активен» нельзя: активность — это ровно то, что имитирует угонщик. За 90 дней до истечения бот присылает напоминание с кнопкой на сайт. |
| **Срок привязки ADMIN — 30 дней** | Админская привязка даёт блокировку лицензий и staff-сброс HWID. Цена компрометации выше, срок короче. |
| Лимит выпуска кодов — **5 на аккаунт в час**, счётчик по `TelegramLinkCode.createdAt` | Ограничивает и случайный спам кнопкой, и попытку набрать пул токенов. |
| Ключ лицензии **никогда** не является доказательством владения аккаунтом | Ключ предъявительский; вор ключа получал бы ещё и право сбросить HWID, то есть отобрать лицензию окончательно. |

### 3.7 Отвязка

Три пути, все ведут к `revokedAt = now()`:

1. **Из чата:** `/unlink` → подтверждение → отвязка. После неё бот отвечает только на `/start` и `/help`. На почту — письмо.
2. **С сайта:** кнопка «Отключить Telegram» в ЛК. В чат уходит прощальное сообщение.
3. **Автоматически:** истёк `expiresAt`; получен `403` от Bot API (`bot was blocked`) — здесь не отвязка, а `chatBlocked = true`; получен `400 chat not found` — отвязка; пользователь заблокирован или удалён — привязка считается неактивной.

**Важно:** отвязка бота **не трогает** `OAuthAccount` с провайдером `TELEGRAM`. Это разные сущности, и в этом весь смысл решения 0.2: можно выключить бота, не сломав вход на сайт, и наоборот.

### 3.8 Смена владельца Telegram — что мы видим и чего не видим

| Событие | Что происходит | Что видим | Что делаем |
|---|---|---|---|
| Аккаунт удалён и создан заново (в т.ч. по неактивности) | новый `user_id` | привязка не срабатывает | ничего — fail-closed, это правильно |
| **Перевыпуск номера / SIM-swap** | тот же `user_id`, другой человек, **вся история чата в облаке доступна ему** | **ничего, Telegram не присылает события** | ничего не можем. Это главный аргумент за §7.2: считать, что всё написанное ботом рано или поздно прочитает посторонний |
| Доступ к незалоченному телефону | то же, временно | ничего | то же |
| Пользователь заблокировал бота | `403` при отправке | видим при первой отправке | `chatBlocked = true`, уведомления пропускаются |
| Пользователь удалил чат | ничего не меняется на нашей стороне | не видим | ничего |

Из невозможности увидеть смену владельца вытекают три вещи, каждая из которых уже заложена выше: конечный срок привязки (90/30 дней), маска ключа по умолчанию (0.3), запрет долгоживущих секретов в переписке (0.4).

### 3.9 Админская привязка

`scope = ADMIN` выдаётся тем же механизмом, но:

- код выпускается только пользователю с ролью, содержащей `licenses.create.any`;
- **step-up 2FA обязателен всегда**, независимо от настроек (для админов 2FA и так обязательна);
- `expiresAt = now + 30 дней`;
- админские команды дополнительно проверяют право **в момент вызова**, а не только при привязке — роль могли снять;
- админский чат получает алерты категории `ADMIN` (§6.1).

Отдельно: `TELEGRAM_ADMIN_CHAT_ID` — это чат для системных алертов, он может быть тем же личным чатом владельца или отдельной группой. Если группа — бот в ней **не отвечает на команды**, только пишет; правило «только приватный чат» для команд остаётся в силе.

## 4. Команды и экраны

### 4.1 Принципы интерфейса

1. **Одно сообщение — один экран.** Навигация построена на `editMessageText` поверх одного сообщения, а не на потоке новых сообщений. Исключения, где сообщение всегда новое: показ ключа (его надо удалить отдельно), уведомления, ответы поддержки.
2. **Кнопки, а не ввод текста.** Текстовый ввод остаётся ровно в четырёх местах: код Digiseller, номер заказа + почта, регистрационный ключ, текст обращения в поддержку. Причина: каждая точка свободного ввода — это точка, где пользовательская строка может уехать в лог или в API-параметр.
3. **Поиск по лицензиям — только кнопками из фиксированного списка.** Пользовательский ввод **не прокидывается** в `GET /licenses?search=`: для не-админа этот параметр ищет по подстроке ключа (`licenses.service.ts:375-379`, `key: { contains: search }`). Утечки нет (`where.AND` по владельцу), но бот превращается в оракул по собственным ключам и начинает логировать фрагменты ключей как «поисковые запросы».
4. **Необратимые действия — два шага**, второй шаг с явно названной ценой («останется 2 из 3»).
5. Максимум **6 кнопок на экран**, по 1–2 в ряд. На узком телефоне длинные подписи переносятся и ломают вёрстку.

### 4.2 Двуязычность

- Хранение языка: `TelegramLink.locale`. До привязки — временный ключ Redis `tg:locale:<chatId>`, TTL 24 ч.
- Определение при первом контакте: `message.from.language_code` → `ru`/`uk`/`be`/`kk` → `ru`, всё остальное → `en`. Почему украинский и белорусский в `ru`: аудитория читает по-русски, а украинской локали у нас нет и не планируется — отправлять её в английский было бы хуже.
- Смена: `/language` или кнопка в «Аккаунте». **Смена языка в боте пишет и в `User.locale`** — чтобы письма и Telegram-уведомления говорили на одном языке. Обратное тоже: смена языка на сайте меняет `TelegramLink.locale`.
- `setMyCommands` вызывается дважды: без `language_code` (английские описания — язык по умолчанию для всех) и с `language_code: "ru"`.

## 5. Сценарии по шагам

### 5.0 Машина состояний

Состояние в Redis `tg:state:<chatId>`:

```json
{ "s": "awaiting_digiseller_code", "since": 1754800000, "ctx": { "nonce": "a1b2c3d4" } }
```

| Состояние | TTL | Чем завершается |
|---|---|---|
| `idle` | — | (отсутствие ключа) |
| `awaiting_digiseller_code` | 300 с | текстовое сообщение, `/cancel`, таймаут |
| `awaiting_order_data` | 300 с | то же |
| `awaiting_registration_key` | 300 с | то же |
| `awaiting_support_text` | 900 с | то же |
| `awaiting_hwid_confirm` | 120 с | callback, `/cancel`, таймаут |
| `awaiting_key_confirm` | 120 с | то же |

**Любая команда из меню сбрасывает состояние в `idle`.** Это важно: человек, застрявший в «пришлите код», должен уметь выйти, нажав `/licenses`, а не только `/cancel`.

**По таймауту бот ничего не пишет.** Написать «время вышло» через 5 минут молчания — значит разбудить уведомлением того, кто уже ушёл.

### 5.1 Первый контакт без привязки

1. `/start` без payload → экран **E-00**.
2. `/start <token>` → §5.2.
3. Любое другое сообщение или команда от непривязанного → `err.not_linked` + кнопка «Подключить аккаунт».

**Обрывы:** сообщение пришло не из приватного чата → `leaveChat`, ничего не отвечаем. Апдейт `my_chat_member` о добавлении в группу → `leaveChat`.

### 5.2 Привязка по deep link

**Успешный путь.**

1. Пользователь в ЛК жмёт «Подключить Telegram».
2. Если 2FA включена и step-up старше 5 минут → сайт просит TOTP.
3. `POST /api/v1/auth/telegram/link/init` **[СЕРВЕР, §8-С4]** → `{ token, deepLink, expiresAt }`.
4. Сайт показывает кнопку и текст ссылки. Таймер 10 минут.
5. Пользователь открывает Telegram, жмёт «Start» → апдейт `/start <token>`.
6. Бот проверяет: приватный чат, `chat.id == from.id`; иначе выход.
7. `BotLinkService.confirm`:
   - `codeHash = sha256(token)`;
   - атомарный `UPDATE … WHERE used_at IS NULL AND expires_at > now() RETURNING user_id, scope`;
   - ноль строк → `err.link_invalid`, счётчик неудач `tg:linkfail:<chatId>` +1;
   - есть строка → проверить, что у `userId` нет активной привязки к **другому** чату; если есть — вытеснение (§3.6);
   - проверить, что у `telegramUserId` нет активной привязки к **другому** аккаунту; если есть — вытеснение;
   - создать `TelegramLink`, создать `TelegramNotificationPref` со всеми категориями `enabled = true`;
   - `enqueue` письма `telegram.linked` на почту **[СЕРВЕР, §8-С5: шаблон]**;
   - записать в `AuditLog`.
8. Бот удаляет входящее сообщение с токеном, шлёт **E-01**.

**Обрывы и ошибки.**

| Ситуация | Поведение |
|---|---|
| Токен протух (> 10 мин) | `err.link_invalid`. Не «протух», а общий текст — иначе даём оракул по существованию токенов |
| Токен уже использован | `err.link_invalid`, тот же текст |
| Токен неверный / мусор после `/start` | `err.link_invalid`, тот же текст |
| Больше 5 неудач с одного чата за час | `err.link_rate`, `tg:linkfail:<chatId>` TTL 3600 |
| Больше 5 выпусков кода на аккаунт за час | сайт отвечает `429`, бот не участвует |
| У пользователя уже есть привязка к этому же чату | не ошибка: обновляем `expiresAt`, отвечаем E-01 с текстом «подключение продлено» |
| Пользователь заблокирован | `err.account_blocked`, привязка **не создаётся** |
| Пользователь нажал Start, но чат ранее был в `chatBlocked` | флаг снимается, привязка обновляется |
| Апдейт продублирован Telegram | отсечён по `update_id` (§2.3) |

### 5.3 Сброс HWID — главный сценарий

1. `/licenses` → **E-03**. Данные: `LicensesService.list(actor, { take: 25 })`.
2. Тап по лицензии → **E-04**. Данные: `LicensesService.findById` + `HwidService.statusFor(licenseId, userId)`. Второй вызов даёт готовые `bound`, `boundAt`, `resetsUsed`, `resetsLeft`, `lastResetAt`, `nextResetAvailableAt` — считать ничего не надо.
3. Кнопка «Сбросить привязку» показывается **только** при `bound === true && resetsLeft > 0 && nextResetAvailableAt === null`. Если условия не выполнены — вместо кнопки строка в тексте (`cooldownLine`).
4. Тап → **E-05**, состояние `awaiting_hwid_confirm`, `nonce` в контексте.
5. Тап «Да, сбросить»:
   - проверка `nonce`; несовпадение → `err.expired_action`;
   - `SET NX tg:hwid-lock:<licenseId> EX 30` — защита от двойного тапа; занято → игнорируем молча (`answerCallbackQuery` без текста);
   - `HwidService.resetSelf(licenseId, actor)`;
   - успех → **E-06**; состояние → `idle`.
6. Сброс сам ставит в очередь письмо `hwid.reset` (`hwid.service.ts:564-565`) — пользователь получит и ответ в чате, и письмо. Дублирование безвредное и даже полезное: письмо — независимый канал уведомления о необратимом действии.

**Ошибки от `HwidService`:**

| Код | Экран |
|---|---|
| `409 HWID_RESET_COOLDOWN` | `err.hwid_cooldown` + кнопка «К лицензии» |
| `409 HWID_RESET_LIMIT` | `err.hwid_limit` + кнопка «Поддержка» |
| `409 NOT_BOUND` | `err.not_bound` + перерисовать E-04 (состояние устарело) |
| `403 FORBIDDEN` | `err.server` + запись в лог с `licenseId` и `userId` — это означает рассинхрон, а не пользовательскую ошибку |
| `404 NOT_FOUND` | `err.expired_action` |

**Важно про `GET /licenses/:licenseId/hwid`:** метод строго для владельца — админ тоже получит `403` (`hwid.service.ts:457`). В админских сценариях используется `GET .../hwid/history` и `staff-reset`, а не `statusFor`.

### 5.4 Активация кода Digiseller

1. `/activate` → **E-08**.
2. «Код с Digiseller» → `screen.activate.ask_code`, состояние `awaiting_digiseller_code`.
3. Пользователь присылает текст:
   - **сразу `deleteMessage` входящего** — до любой обработки и до любого логирования;
   - обрезка до 128 символов, `trim`;
   - если строка похожа на ключ лицензии (регулярка `^[A-Z0-9]{2,6}(-[A-Z0-9]{4}){4}$`) → **не отправляем в API**, отвечаем: `Это похоже на ключ лицензии, а не на код с Digiseller. Ключ лицензии активировать не нужно — он уже ваш.` Причина: без этой проверки бот отправит ключ лицензии в лог Digiseller-сервиса как «неудачную попытку».
4. `DigisellerService.redeem(code, actor, ctx)`.
5. Из ответа `{orderId, orderNumber, licenseId, licenseKey}` **поле `licenseKey` вырезается немедленно**, до логирования и до передачи в рендер экрана. Дальше работаем с `licenseId`.
6. Успех → **E-09** (`screen.activate.success`) с маской.

**Ошибки:**

| Ситуация | Экран |
|---|---|
| Код не найден / не наш | `err.digiseller_invalid` |
| Код уже использован | `err.digiseller_used` |
| Заказ есть, но не подтверждён площадкой | `err.digiseller_pending`; заказ попадает в `pending`, владелец получит алерт (§6.1) |
| Превышен лимит `attempts_per_hour` (30 на пользователя) | `err.digiseller_rate` |
| Превышен лимит `attempts_per_ip_per_hour` (60 на адрес) | **проблема, см. §8-С2.** При боте-модуле IP берётся из вебхука Telegram и одинаков для всех. Обязательный обход: передавать в качестве оси лимита `telegram:<telegramUserId>` вместо IP |
| У пользователя нет пароля (аккаунт из `register-with-key`) | `err.password_required` + кнопка на сайт. Это реальный случай: без пароля лицензия не выдаётся |
| Таймаут API Digiseller | `err.server`, попытка **не** повторяется автоматически: повтор может выдать вторую лицензию |

### 5.5 Активация по номеру заказа

Отличия от 5.4: состояние `awaiting_order_data`, ожидаются две строки. Разбор: первая непустая строка — номер заказа (цифры), вторая — почта (простая проверка на `@`). Не разобралось → повтор просьбы с примером, максимум 3 раза, потом `/cancel`.

Вызов `DigisellerService.redeemByOrder({ orderNumber, email }, actor, ctx)`.

**Почта здесь — чужая персональная данность в переписке.** Входящее сообщение удаляется так же, как и с кодом.

### 5.6 Просмотр и раскрытие ключа

1. E-04 → «Показать ключ» → **E-07 confirm**, состояние `awaiting_key_confirm`, `nonce`.
2. Проверка лимита: `tg:keyreveal:<chatId>` — скользящее окно, **не более 3 раскрытий в час**. Превышено → `err.key_reveal_limit`.
3. «Открыть на сайте» → одноразовая ссылка **[СЕРВЕР, §8-С3]**. Это **предпочтительный путь** и он стоит первым в списке кнопок.
4. «Показать здесь» → `LicensesService.findById` → `license.key` → **новое** сообщение только с ключом → `setTimeout 90 000` → `deleteMessage`.
5. Факт раскрытия пишется в `AuditLog`: `licenseId`, `userId`, `via: telegram`. **Значение ключа в аудит не пишется.**

**Честно про `deleteMessage`:** это гигиена, а не защита. Он не отменяет пуш-уведомление, которое уже показало ключ на локскрине; не отменяет скриншот; не отменяет пересылку. Именно поэтому путь через сайт стоит первым.

### 5.7 Регистрационный ключ

`POST /auth/redeem-key` **[ЕСТЬ]**, требует JWT (у нас — актора). Состояние `awaiting_registration_key`, входящее удаляется, ответ содержит `licenseKey` — вырезается так же, как в 5.4.

**Про `POST /auth/register-with-key`** (`@Public()`, создаёт аккаунт без почты, сразу отдаёт токены и, если ключ несёт продукт+тариф, лицензию): это единственный путь создать аккаунт прямо из чата. **В первой версии он в боте не используется** — обоснование ниже, §8-С6 и 0.6: получившийся аккаунт не имеет ни почты, ни пароля, и бот становится единственным способом до него достучаться. Если владелец захочет включить **[РЕШЕНИЕ ВЛАДЕЛЬЦА]**, обязателен экран-предупреждение:

> `⚠️ Аккаунт будет создан без почты и без пароля. Если вы потеряете доступ к этому Telegram, восстановить аккаунт и лицензии будет невозможно. Задайте почту и пароль в кабинете сразу после создания.`

### 5.8 Поддержка

1. `/support` → `screen.support.ask`, состояние `awaiting_support_text`.
2. Текст (до 2000 символов, обрезка) → бот формирует сообщение в админ-чат:
   ```
   💬 Обращение #{{ticketNo}}
   Пользователь: {{username}} (id {{userId}})
   Telegram: {{tgUsername или id}}
   Лицензий: {{n}} · {{списком: продукт · статус · маска ключа · привязка}}

   {{text}}
   ```
3. Создаётся `TelegramSupportThread` с `adminMessageId`.
4. Владелец **отвечает реплаем** на это сообщение в админ-чате → бот находит тред по `(adminChatId, adminMessageId)` из `reply_to_message` → пересылает текст пользователю с префиксом `💬 Ответ поддержки:` / `💬 Support reply:`.
5. Пользователь может ответить ещё раз через `/support` — это создаёт **новый** тред. Диалог с сохранением контекста в первой версии не делается: цена (хранение состояния диалога, разбор «кому адресовано») не окупается на текущем объёме.

**Ограничения:** не более 3 обращений в час на пользователя (`tg:support:<userId>`); превышение → `Вы уже отправили три обращения за час. Дождитесь ответа.`

**Что бот вырезает из текста обращения перед отправкой в админ-чат:** ничего. Владелец должен видеть ровно то, что написал человек. Но текст **не логируется** в общий лог приложения — только в `TelegramSupportThread`, и только если владелец решит хранить тексты **[РЕШЕНИЕ ВЛАДЕЛЬЦА]**; по умолчанию текст не сохраняется вовсе, он живёт только в админ-чате.

**Чего в админской части бота нет и не будет:** выпуск API-ключей (`POST /auth/api-keys` — секрет возвращается один раз), загрузка payload, управление продуктами/тарифами/версиями. Формы на десять полей и файлы — это сайт.

### 5.13 Общая таблица «ошибка API → поведение бота»

| HTTP / код | Поведение |
|---|---|
| `400` с известным `code` | соответствующий текст из §4.5 |
| `400` с неизвестным `code` | `err.server` + лог с кодом и `licenseId`/`userId` |
| `401` | невозможно при боте-модуле; если случилось — `err.server` + алерт владельцу, это дефект |

| `404 NOT_FOUND` | `err.expired_action` + возврат на список |
| `409` | по конкретному коду (см. §5.3, §5.4) |
| `429` | `err.digiseller_rate` / `err.link_rate` по контексту |
| `5xx`, таймаут | `err.server`. **Автоповтора нет** для операций, изменяющих состояние |
| исключение в самом боте | `err.server` + полный стек в лог **после** прогонки через редактор ключей (§7.6) |

### 6.2 Как Telegram становится каналом

Две точки, обе в существующей подсистеме:

**1. Разрешение получателя** — `notification.service.ts:175-177`:

```ts
// сейчас:
// Discord и Telegram появятся вместе с OAuth: адресом станет
// provider_user_id из oauth_accounts.
return null;
```

Комментарий устарел и вводит в заблуждение: OAuth давно готов и покрыт тестами. Но и предложенный им дизайн неверен для бота: `provider_user_id` из `oauth_accounts` — это id того, кто входил виджетом, а не того, кто нажал `/start`. Писать по нему нельзя.

Правильно:

```ts
if (params.channel === NotificationChannel.TELEGRAM) {
  const link = await this.prisma.telegramLink.findFirst({
    where: { userId: params.userId, revokedAt: null, chatBlocked: false },
    select: { chatId: true },
  });
  return link ? String(link.chatId) : null;
}
```

**2. Ветка отправки** — `notification.processor.ts:137-139`: вместо `throw` вызывается `BotNotifyService.send(recipient, rendered)`.

**3. Постановка в очередь.** Все шесть существующих `enqueue` жёстко указывают `channel: EMAIL`. Нужен **веер по каналам**: одно событие → письмо всегда + Telegram, если есть активная привязка и категория включена. Реализуется методом `enqueueMulti(params)`, который сам решает набор каналов; шесть точек вызова переключаются на него. **[СЕРВЕР, §8-С5]**

**4. Шаблоны.** Для каждого ключа нужен вариант `channel: TELEGRAM` в локалях `ru` и `en`. Уникальность `@@unique([key, locale, channel])` в схеме уже это допускает. Telegram-варианты **короче** письменных: письмо можно прочитать вдумчиво, уведомление читают на бегу.

Пример `license.expiring`, TELEGRAM, ru:
```
⏳ Лицензия на {{productName}} истекает через {{daysLeft}} дн. — {{expiresAt}}.
```
`hwid.reset`, TELEGRAM, ru:
```
🔓 Привязка сброшена {{resetAt}}. Осталось сбросов: {{resetsLeft}}.
```

**Правило: ни один Telegram-шаблон не содержит `{{licenseKey}}`.** Шаблон `license.issued` в EMAIL его содержит (`seed.ts:~460`, `Order {{orderNumber}} … License key: {{licenseKey}}`) — и это нормально для почты. Telegram-вариант получает `{{maskedKey}}`, которая формируется на этапе `enqueue`.

### 6.3 Подписки

`TelegramNotificationPref` на связку `(linkId, category)`. По умолчанию все включены.

- `SECURITY` **не отключается** — это единственный способ узнать о чужом доступе.
- `ADMIN` доступна только при `scope = ADMIN`.
- **Настройки бота не влияют на письма.** Письма идут всегда. Причина: почта — независимый канал, и она же единственный якорь восстановления. Дать возможность отключить письма из бота — значит дать угонщику чата способ обрубить единственный канал, где владелец увидел бы тревогу.

### 6.4 Частота и тихие часы

| Правило | Значение | Почему |
|---|---|---|
| Дедупликация | один и тот же `(userId, templateKey, licenseId)` — не чаще **1 раза в 6 часов** | защита от штормов при повторных прогонах крона |
| Потолок на пользователя | **10 уведомлений в час**, сверх — молча отбрасываются с записью в лог | никакое штатное событие не даёт больше; превышение означает дефект |
| Тихие часы | **23:00–08:00** по локали пользователя — отправка откладывается до 08:00 | напоминание об истечении срока не стоит того, чтобы будить |
| Исключение из тихих часов | категория `SECURITY` | «бот подключён к вашему аккаунту» ночью — это ровно то, что человек должен увидеть немедленно |

| Глобальный лимитер | 25 сообщений/с суммарно, 1 сообщение/с в чат | ниже лимитов Telegram, с запасом |

### 6.5 Отказ доставки

`403` → `chatBlocked = true`, уведомление помечается `FAILED` **без ретраев** (иначе очередь будет вечно долбиться). `429` → откладывается на `retry_after`. `5xx`/сеть → штатные ретраи процессора (до 5 попыток). `400 chat not found` → отвязка + письмо.

## 7. Безопасность: решения и обоснования

### 7.1 Модель угроз в одном абзаце

Бот — публично доступная дверь в приватный API, у которой нет ни пароля, ни IP-ограничений, ни капчи. К ней может подойти кто угодно, кто нашёл `@pxcheats_bot` в поиске. За дверью: ключи лицензий (предъявительские секреты), необратимый расход сбросов HWID (3 на всю жизнь лицензии) и активация покупок Digiseller (лимит по IP, общий на всех). Плюс два свойства Telegram, которые нельзя изменить: **переписка хранится в облаке и на всех устройствах владельца бессрочно**, и **владелец Telegram-аккаунта может смениться без нашего ведома**.

### 7.2 Сводка решений

| # | Решение | Почему | Что ломается, если сделать иначе |
|---|---|---|---|
| 1 | Привязка только с сайта, deep link, одноразовый токен, хранится SHA-256 | §3.1–3.4 | Пароль в чате: один слитый бэкап телефона компрометирует аккаунт целиком и обходит 2FA. ### 7.3 Ключ лицензии: три уровня

**Что защищаем.** Ключ — предъявительский секрет загрузчика. Но у него есть вторая граница — привязка к железу. Отсюда уточнение угрозы:

- **Утечка до первого запуска — тяжёлая.** Вор привязывает своё железо первым, владелец жжёт сбросы (их всего 3) в войне за собственную лицензию.
- **Утечка после привязки — заметно легче.** Вор не запустится, а сброс требует прав владельца (`hwid.reset.self`, строго владелец — админ и тот получает `403`, `hwid.service.ts:457`).

Значит самый опасный момент — **выдача ключа**, и это ровно тот момент, когда `redeem` возвращает `licenseKey` прямо в ответе (`digiseller.service.ts:355, 701, 978`).

**Уровень 0 — маска везде.** `maskKey(key) = key.slice(0,4) + '-****-****-****-' + key.slice(-4)`. Последние 4 символа — различитель, чтобы человек понимал, о какой лицензии речь.

**Уровень 1 — одноразовая ссылка на сайт**, TTL 5 минут. В переписке остаётся ссылка, которая через 5 минут мусор. **[СЕРВЕР, §8-С3]**

**Уровень 2 — разовый показ в чате**, отдельным сообщением, только ключ, автоудаление через 90 с, лимит 3/час, запись факта в аудит. Честно: `deleteMessage` — гигиена, не защита.

**Сопутствующие обязательства.** Ключ не сохраняется в БД бота ни в каком виде. Ключ не попадает в логи — ни в логи запросов, ни ошибок, ни трейсов. Поле `licenseKey` вырезается из ответа `redeem` **до** любого логирования.

### 7.4 Аудит

В `AuditLog` пишутся: привязка, отвязка, вытеснение привязки, сброс HWID через бота, раскрытие ключа (факт, не значение), активация Digiseller (без кода и без ключа), любое админское действие. Поле `actorType` — `USER`, поле источника — `telegram`.

### 7.6 Логирование

- В логгер модуля ставится **редактор**: регулярка `/\b[A-Z0-9]{2,6}(-[A-Z0-9]{4}){4}\b/g` → `***`. Ставится в **сериализаторе** логгера, а не в местах вызова: место вызова однажды забудут.
- Не логируются: тексты обращений в поддержку, коды Digiseller, регистрационные ключи, почты покупателей, `link_token`.
- Логируются: `update_id`, `telegramUserId`, `userId`, `licenseId`, имя экрана, код ошибки, длительность.
- Проверка перед релизом: грепнуть логи за сутки нагрузочного прогона регуляркой ключа. Ноль совпадений — обязательное условие выпуска.

### 7.7 Что уже исправлено на сервере — важная поправка

Отчёт по требованиям ТЗ (`TZ-AUDIT.md`, находка №5) утверждает, что **вход через Telegram обходит 2FA**. **На текущем коде это неверно — исправлено.** Проверка второго фактора перенесена внутрь `AuthService.completeLogin` (`auth.service.ts:400-420`) и срабатывает по умолчанию для **всех** вызывающих, включая `oauth.service.ts:310`; пропустить её можно только осознанно, передав `twoFactorSatisfied: true` (законный обход ровно один — `verifyTwoFactor`). Комментарий на `auth.service.ts:378-398` описывает и дефект, и починку. Это стоит учесть при планировании: пункт закрыт, переделывать нечего.

### 9.0 Общие настройки для всех генераций
