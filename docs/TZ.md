# Техническое задание

Исходный документ заказчика. Изменения фиксируются в конце файла разделом
«Уточнения», сам текст ТЗ не правится — чтобы всегда было видно, от чего
отклонились и почему.

---

## 1. Цель проекта

Веб-платформа для управления лицензиями программных продуктов с поддержкой:
авторизации пользователей, управления лицензиями, привязки к ПК (HWID),
самостоятельного и административного сброса HWID, панели администратора,
панели реселлера, личного кабинета пользователя, API для лаунчера, системы
обновлений, интеграции с Digiseller и криптовалютными платежами.

## 2. Основные роли

**Super Admin** — полный доступ: управление пользователями, администраторами,
реселлерами, ролями, продуктами; просмотр логов; настройки безопасности;
настройки API; управление обновлениями; управление лицензиями; публикация
новостей.

**Reseller** — доступ только к собственным клиентам: продажа лицензий,
продление, просмотр клиентов, просмотр статистики, сброс HWID клиентов,
просмотр истории операций.

**User** — просмотр лицензий, срока действия, истории входов, истории покупок;
самостоятельный сброс HWID; скачивание последней версии лаунчера; управление
безопасностью аккаунта.

## 3. Поддержка продуктов

Несколько продуктов; несколько версий одного продукта; отдельные лицензии для
каждого продукта; несколько лицензий у одного пользователя.
Примеры: FC 26, FC 27, GTA V.

## 4. Лицензии

Типы: 1 день, 7 дней, 30 дней, 90 дней, 180 дней, Lifetime.

Для каждой лицензии хранится: ID, пользователь, продукт, дата создания, дата
окончания, статус, HWID, история HWID, количество сбросов, дата последнего
входа, IP, версия клиента.

## 5. Регистрация

Через сайт, через Discord, через Telegram, по ключу.

## 6. Авторизация

Email + пароль, логин + пароль, Discord OAuth, Telegram OAuth, 2FA.

## 7. Работа HWID

Привязка автоматически при первом запуске. HWID состоит из Disk ID.
Состав HWID пользователю не отображается.

Администратор может: сбросить HWID, изменить HWID вручную, посмотреть историю.
Пользователь может: самостоятельно выполнить сброс, посмотреть дату последнего сброса.
Реселлер может: сбросить HWID только своих клиентов.

Ограничения самостоятельного сброса: не чаще одного раза в день; ограничение
общего количества; администратор может игнорировать ограничения.

## 8. Панель администратора

**Dashboard:** активные лицензии, заблокированные, онлайн, новые регистрации,
продажи, истекающие лицензии, ошибки авторизации, последние действия.

**Пользователи:** поиск, создание, удаление, редактирование, блокировка,
просмотр истории.

**Продукты:** создание, редактирование, архивирование, управление версиями.

**Версии:** номер, дата, changelog, обязательность обновления, файл, SHA-256.

**Лицензии:** создать, удалить, продлить, изменить тариф, заблокировать,
разблокировать, поиск, массовые операции.

**Логи:** полный аудит — вход, выход, изменение лицензии, удаление, создание,
изменение ролей, публикация новости, загрузка файлов, сброс HWID, ошибки.

**Новости:** Markdown, изображения, закрепление, планирование публикации.

**Настройки:** API, безопасность, SMTP, Telegram, Discord, Digiseller,
криптокошельки.

## 9. Панель реселлера

Управление своими лицензиями, управление клиентами, продление, статистика,
сброс HWID, история операций, продажи.

## 10. Кабинет пользователя

**Главная:** статус лицензии, продукт, дата окончания.
**История входов:** дата, IP, страна, устройство, версия клиента.
**Покупки:** заказ, стоимость, способ оплаты.
**HWID:** текущая привязка, количество сбросов, кнопка сброса.
**Скачать:** загрузка последней версии лаунчера.

## 11. Лаунчер

Авторизация, проверка лицензии, проверка HWID, обновление, отправка логов,
проверка целостности файлов.

## 12. Обновления

Администратор публикует новую версию. Лаунчер: проверяет наличие, скачивает,
проверяет SHA-256, устанавливает, запускает. Обновление может быть обязательным.

## 13. API

Authentication API, Launcher API, License API, Product API, Admin API,
Reseller API, Statistics API, Notification API.

## 14. Безопасность

HTTPS, JWT, Refresh Token, подпись запросов, Replay Protection, Argon2,
шифрование токенов, RBAC, CSRF, SQL Injection Protection, XSS Protection,
Rate Limit, CAPTCHA, журнал аудита, резервное копирование.

## 15. Антифрод

Обнаружение: массовые попытки входа, слишком частые запросы, подозрительные IP,
входы из новых стран, использование VPN/Proxy (при наличии сервиса определения),
повторные запросы, изменение HWID.

При обнаружении: уведомить администратора, отправить письмо, запросить повторную
авторизацию, записать событие в лог.

## 16. Уведомления

Email, Discord, Telegram, Push лаунчера, внутренние уведомления.

## 17. Платежи

Digiseller, криптовалюты, ручная выдача лицензий.
После успешной оплаты: создать заказ, создать лицензию, отправить уведомление,
записать событие в журнал.

## 18. Статистика

Dashboard: продажи, новые пользователи, активные лицензии, онлайн, истекающие
лицензии, популярные продукты, версии клиентов, ошибки авторизации, сбросы HWID,
эффективность реселлеров.

## 19. Локализация

Русский, английский, немецкий, французский, испанский. Архитектура должна
позволять добавлять новые языки без изменения исходного кода.

## 20. Структура базы данных

Users, Roles, Permissions, Products, ProductVersions, Licenses, Devices,
HWIDHistory, Sessions, RefreshTokens, APIKeys, Resellers, Orders, Payments,
DigisellerOrders, CryptoPayments, Files, Updates, News, Notifications,
LoginHistory, AuditLogs, Settings.

## 21. Требования к производительности

- Не менее 10 000 зарегистрированных пользователей.
- Не менее 1 000 одновременных онлайн-сессий.
- Среднее время ответа API — до 300 мс.
- Проверка лицензии — до 150 мс при штатной нагрузке.
- Возможность горизонтального масштабирования.

## 22. Рекомендуемый стек технологий

**Backend:** ASP.NET Core 9 (C#) или NestJS (TypeScript). REST API. JWT + Refresh Tokens.
**База данных:** PostgreSQL. **Кэш:** Redis. **Очереди:** RabbitMQ (или аналог).
**Frontend:** React + TypeScript, Tailwind CSS, Shadcn/UI.
**Хранилище файлов:** S3-совместимое (или локальное с возможностью миграции).
**Инфраструктура:** Docker, Nginx, HTTPS.

# Уточнения, принятые в ходе разработки

Решения, отклоняющиеся от буквы ТЗ. Каждое согласовано с заказчиком.

### У-1. Платёжный канал — только Digiseller

Отменяет прямой приём криптовалюты из п.1 и п.17. Крипта принимается **через
Digiseller** как один из способов оплаты внутри площадки.

*Следствие:* сущность `CryptoPayments` из п.20 не создаётся — крипта это
`payments.method = CRYPTO`. На сервере не остаётся горячего кошелька, что
убирает целый класс атак. Настройка «криптокошельки» из п.8 неприменима.

*Риск, принятый заказчиком:* единственный платёжный канал означает, что
продажи доступны ровно настолько, насколько доступен Digiseller.

### У-2. Backend — NestJS + TypeScript

Выбран из двух вариантов п.22. Причины: Node уже в окружении, единый язык
с фронтендом, общие типы DTO через shared-пакет.

### У-3. Архитектура — модульный монолит

П.21 требует горизонтального масштабирования, но не микросервисов.
Stateless-монолит за nginx масштабируется репликами и закрывает требование,
не создавая распределённых транзакций при выдаче лицензии после оплаты.
Границы модулей соблюдаются, разрезание на сервисы возможно позже.

### У-4. Сущность `Updates` не создаётся

«Обновление» из п.12 — это `product_versions` с `is_published = true`.
Отдельная таблица дублировала бы все поля версии и разъехалась бы с ней.

### У-5. Тарифы вынесены в таблицу `license_plans`

Сроки из п.4 (1/7/30/90/180/lifetime) — не перечисление в коде, а строки в
БД со сроком, ценой и привязкой к товару Digiseller. Иначе изменение линейки
тарифов требует миграции БД.

### У-7. Счётчик сбросов HWID — общий

Сброс расходует лимит пользователя независимо от того, кто его сделал:
сам пользователь, админ, поддержка или реселлер. Раздельных счётчиков нет.

*Обоснование:* раздельные счётчики превращают поддержку в канал безлимитных
сбросов — достаточно каждый раз писать «не запускается, сбросьте привязку».

*Компенсация:* право `hwid.counter.adjust`. Сбросив привязку по вине системы,
поддержка возвращает счётчик на прежнее значение; действие пишется в аудит.

### У-8. Канал `LAUNCHER_PUSH` удалён

Загрузчик написан на C++ и обращается к API по HTTP без постоянного
соединения — доставлять push нечем. Адресные уведомления отдаются полем в
ответе на очередную проверку лицензии. Осталось четыре канала из п.16:
email, Discord, Telegram, внутренние.

### У-9. Источник HWID — серийный номер накопителя

Загрузчик читает Disk ID через `DeviceIoControl` с
`IOCTL_STORAGE_QUERY_PROPERTY`. Идентификатор переживает форматирование
раздела и переустановку Windows, поэтому лимит в 3 самостоятельных сброса
адекватен и в поддержку по поводу переустановки системы обращаться не будут.

### У-10. Очередь — таблица `notifications`, а не RabbitMQ

П.22 называет брокер рекомендацией с прямо разрешённой заменой: «Очереди:
RabbitMQ (**или аналог**)». Аналогом выступает сама таблица `notifications`,
спроектированная под это с самого начала: `status`, `attempts`, `error`,
`sent_at`. Отдельный обработчик разбирает её по расписанию.

*Обоснование.* Уведомление ставится в очередь **внутри** транзакции
бизнес-операции — выдачи лицензии, смены пароля, сброса привязки. С брокером
это двойная запись, и она разъезжается при первом же сбое между коммитом и
публикацией: опубликовать до коммита — отправить письмо о лицензии, которой
не будет; после — потерять письмо при падении процесса между двумя шагами.
С таблицей такого класса ошибок нет вовсе: запись живёт в той же транзакции,
что и лицензия.

Дополнительно: п.16 требует историю уведомлений в админке — это ровно та же
таблица. Брокер не отменил бы её, а добавился бы сверху.

*Следствие для эксплуатации:* контейнер `rabbitmq` в `docker-compose`
и переменная `RABBITMQ_URL` остаются как заготовка, но в коде не используются
ни одной строкой. Перед выкладыванием контейнер стоит убрать — в покое он
занимает около 150 МБ, больше всех остальных сервисов вместе взятых.

*Когда вернуться к брокеру:* когда появится веерная рассылка по нескольким
каналам разом или отправка станет упираться в опрос таблицы. На объёмах
«единицы покупок в сутки» опрос дешевле и надёжнее.

### У-6. Добавлены сущности сверх п.20

`OAuthAccounts` (п.5-6), `RegistrationKeys` (п.5), `LicensePlans` (п.4),
`NotificationTemplates` (п.16), `NewsTranslations` + `Locales` +
`Translations` (п.19), `ResellerTransactions` (п.9), `AntiFraudEvents` (п.15),
join-таблицы `RolePermissions` и `UserRoles` (п.2).

Каждая закрывает конкретное требование ТЗ, которое иначе пришлось бы
реализовывать через JSON-поля или хардкод.
